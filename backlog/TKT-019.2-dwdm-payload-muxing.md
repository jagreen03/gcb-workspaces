# Objective

**Resumes after [[TKT-019.3]] (deskew/CDC scaling) per the Architect's
re-prioritisation** — the physical receiver bottleneck is characterised and
the CDC-capable sibling is built; this story writes the **logical
abstraction** layer TKT-019.3's own out-of-scope list deferred: muxing the
ratified [[GCB-034]] **logical result payload** (Mode A `q_tile`+`q_scale`,
Mode B `acc_tile` partial sum) onto the **physical `color_word_t` /
`N_LAMBDA` transport** [[TKT-019.1]] and [[TKT-019.3]] built.

## The gap this story closes

Reading the existing RTL (not assumed): `gcb_dwdm_tx_packager` /
`gcb_dwdm_deskew` / `gcb_wavelength_router` already move a fixed-shape
`color_word_t` (136 b: two 64 b INT4-packed operand lanes + sidebands) across
`NUM_COLORS` / `N_LAMBDA` channels — but that existing ingress
(`gcb_dwdm_tx_packager`) is wired for a **different use case**: broadcasting
ONE flat INT4 operand tile (`host_a`/`host_b`, `NUM_COLORS*LANES_PER_COLOR`
elements) by slicing it evenly across the enabled channels — the
photonic-MAC operand-broadcast path this repo was originally built for.

[[GCB-034]]'s ratified contract payload is a **different logical object
entirely** — a post-`gcb_tile_requantize` or post-K-split-accumulate
**result** (Mode A ≈ 271 B INT8, Mode B 1024 B INT32), carrying the **D4
header mode bit**, and — per [[GCB-037]]'s link-budget finding — the two
modes don't spread the same way: **Mode A serialises in time on ~1 λ**
(throughput regime); **Mode B spreads in space across ≈ 60 λ** per
transaction (latency regime). Nothing in the repo today takes that logical
payload, frames the mode bit, and chunks/distributes it onto
`color_word_t` words the right way for either regime — that is the missing
"payload muxing" layer.

## Design

**In-band framing, not a sideband wire.** [[GCB-034]] itself says "header
mode bit" — so the mode bit travels *inside* the payload, not as an extra
RTL control signal the receiver must somehow already know (true to an
optical receiver's actual information: it only has the data that arrived on
the fibre). A 3-byte header — `byte0 = {7'b0, mode_b}`, `byte1..2 =
payload_len` — is prepended to the logical payload before chunking; the
receiver reads it back out of the first chunk to recover both the mode and
the exact byte count (so zero-padding to a whole number of 16 B chunks / a
whole number of lanes never gets mistaken for payload).

**One muxing engine, two lane counts.** `CHUNK_BYTES = 16` (`packed_a` +
`packed_b`, the two 64 b fields `color_word_t` already carries). A
transaction uses `LANES_USED = mode_b ? MODE_B_LANES : 1` contiguous lanes
(`0..LANES_USED-1`); `WORDS_TOTAL` (framed length, rounded up to a whole
number of chunks) is further rounded up to a whole multiple of `LANES_USED`
so every cycle of the transaction drives the *same* lane set — `lane_enable`
is quasi-static for the whole transaction, matching how `channel_enable` is
already documented as control-plane state in `gcb_dwdm_deskew` /
`gcb_dwdm_deskew_cdc`. `is_tile_final` (already a `color_word_t` field) is
stamped on the last lane of the last cycle; the demuxer treats "I saw
`is_tile_final`" as the one thing it needs to know the transaction is
complete — it doesn't need to be told `WORDS_TOTAL` in advance.

**New RTL, additive — nothing frozen or already-shipped is touched:**

* `rtl/gcb_dwdm_payload_mux.sv` — logical payload (`mode_b`, `payload_len`,
  flat `payload_data`) → framed, chunked, lane-distributed `color_word_t`
  stream (`tx_color[NUM_COLORS]` / `tx_valid[NUM_COLORS]` / `lane_enable`),
  wired straight into `gcb_dwdm_deskew.in_color` / `.in_valid` /
  `.channel_enable` exactly like `gcb_dwdm_tx_packager`'s egress is today.
* `rtl/gcb_dwdm_payload_demux.sv` — the inverse, consuming
  `gcb_dwdm_deskew`'s `out_color[NUM_COLORS]` / `aligned_valid`, reassembling
  the framed byte stream in lane order, and emitting `payload_valid` /
  `mode_b` / `payload_len` / `payload_data` once `is_tile_final` is seen.
* `gcb_dwdm_tx_packager`, `gcb_dwdm_deskew`, `gcb_wavelength_router`,
  `gcb_bitplane_tx_mapper`: **unchanged.** This is a second, parallel
  front/back-end onto the same physical transport, for the GCB-034
  result-transport use case — not a replacement of the existing INT4
  operand-broadcast path.

## Out of scope (separate tickets)

1. Wiring this into `gcb_dwdm_transceiver_top` or any host/orchestrator
   integration — this story delivers and verifies the mux/demux pair
   standalone, the same scoping precedent [[TKT-019.3]] set for
   `gcb_dwdm_deskew_cdc`.
2. The channel/BER model and the top-level link Cocotb TB (epic Green target
   items 3–4) — consumes this story's output, not built here.
3. `gcb-wiki/14` doctrine page — epic Green target item 5, not this story.
4. Re-deriving `MODE_B_LANES` from a live `P` (K-split fan-in); fixed at the
   GCB-034/GCB-037 ≈ 60 λ ceiling for this story, same treatment
   [[TKT-019.3]] gave `MAX_SKEW_CYCLES`.

## AI Orchestration Priorities (PBG Evaluation)

* **Green (target):** the mux/demux round-trip reconstructs the exact
  logical payload byte-for-byte, mode bit included, for both regimes, at
  both a cocotb bring-up lane count and the GCB-034 Mode B ceiling;
  `gcb_dwdm_tx_packager` / `gcb_dwdm_deskew` / `gcb_wavelength_router`
  untouched; `sim/lint.sh` and Yosys 0.68 latch-free at both geometries.
* **Yellow (reject):** a fixed-length-only muxer that can't carry both the
  ≈ 271 B and 1024 B shapes; passing the mode bit as an extra RTL wire
  instead of in-band framing (quietly assumes a receiver sideband the real
  optical link doesn't have).
* **Red (reject):** modifying `color_word_t`, `gcb_bitplane_tx_mapper`, or
  any already-shipped module's port list to make the muxing "simpler."

**Vector Summary:** `telemetry: {spec: 0.9, quality: 0.95, emergence: 0.65}`

* **Spec (0.9):** delivers exactly the logical-abstraction gap TKT-019.3
  deferred — a mode-bit-framed, dual-regime-shaped mux/demux pair, additive
  and unwired as scoped. Docked slightly short of 1.0 because `MODE_B_LANES`
  is fixed per-instance rather than derived from a runtime `P` (explicitly
  out of scope, same treatment as TKT-019.3's `MAX_SKEW_CYCLES`, but it does
  mean the story delivers the mechanism, not a live fan-in policy).
* **Quality (0.95):** `sim/lint.sh` 38/38 clean; cocotb `TESTS=3 PASS=3
  FAIL=0` covering both regimes plus a back-to-back stress case; Yosys 0.68
  bless 0 problems / latch-free at both the bring-up and GCB-034 ceiling
  geometry for both new modules.
* **Emergence (0.65):** two reusable findings beyond the ticket's own ask:
  (1) the in-band 3-byte header (mode bit + length) is a reusable framing
  convention for every future TKT-019.x stage that needs to carry GCB-034's
  D4 mode bit across the optical boundary; (2) a general elaboration-scaling
  lesson for any large-unrolled-loop RTL in this repo — sv2v/Yosys instantiate
  a function call, and any implicit cast inside it, once *per call site*
  rather than as shared logic, and an unpacked array driven by a large
  construction loop invites a "memory→register" conversion that scales badly
  — isolated methodically (shrink the offending parameter, watch the `proc`
  pass's own progress counter) and fixed with a general pattern (flatten to
  packed vectors, inline instead of calling, hoist casts out of loops) that
  the next payload-width-scaled module in this repo can reuse directly.
