# Objective

Implement a Python + Jinja2 generator in `gcb-python-orchestrator` that emits
the GDDR7 DMA's parameter package and CSR decode wrapper as **pure
SystemVerilog**, from a single data file that captures
`gcb-wiki/11_gddr7_tensor_dma_architecture.md`'s parameter set and CSR map. This
is the "parameterisation is Jinja2, not an HDL DSL" half of the EDA doctrine
(`gcb-wiki/10` §3) applied to the DMA: the hand-written datapath (`TKT-009`)
stays hand-written; the repetitive `localparam` derivations and the CSR
register file wrapping it are generated and committed.

## Context & Constraints

* **Current State:**
  * `gcb-wiki/10` §3 mandates the shape: banned — Chisel / Amaranth / SpinalHDL
    / Migen / any "describe hardware in language X, emit Verilog" layer.
    Required — Python + Jinja2 emitting standard SV, generated files committed
    with a `DO NOT EDIT — generated by <script> from <source>` banner, no
    constructs only the template understands. Precedent: `gcb-spec/regen.py`
    (one `registers.yaml` -> SV / C++ / Python / TS / Markdown).
  * `gcb-wiki/11` §0 and §7 enumerate what has to be derived / exposed:
    `VEC_BYTES` (from `OPERAND_BITS`), `ROW_STRIDE` (= `K_STEPS * VEC_BYTES`),
    `K_STEPS`, `GRID_DIM`, `N_TILE`, `M_BANDS`, `N_PASSES`, burst length, plus
    the CSR block (`DMA_VEC_BYTES`, `DMA_ROW_STRIDE`, `DMA_GRID_DIM`,
    `DMA_N_TILE`, `DMA_M_BANDS`, `DMA_N_PASSES`, `DMA_B_LAYOUT`, `DMA_CTRL`,
    `DMA_STATUS`, `DMA_IRQ_EN`) with the `UNDERRUN` / `ERR` / `CFG_ERR` /
    `RUNNING` / `A_BUSY` / `B_BUSY` fields.
  * EDA toolchain: the generated SV is lint-checked by Verilator 5 and
    elaborated by Yosys + Surelog/UHDM, same bar as hand-written RTL.
* **Sequencing:** soft-depends on `TKT-009` — the CSR wrapper wraps
  `gcb_tensor_dma_arbiter`, so its port list must be stable before the wrapper
  is finalised. The parameter package can be drafted from Doc 11 alone. This
  ticket is **deferred** behind the active silicon path (`TKT-009`) per the
  Architect; it captures orchestration debt, it does not block the RTL.
* **Constraint:** No new HDL language. The generator is Python; its output is
  standard SystemVerilog (`parameter` / `localparam` / `generate` / `case` — no
  macro soup). Generated files are committed, carry the banner, and re-running
  the generator on an unchanged source produces a **byte-identical** file
  (idempotent, CI-checkable). A checkout without Python still builds.

### AI Orchestration Priorities (PBG Evaluation)

Taxonomy: **Purple** = strategic net-new platform capability; **Blue** = solid
sustainable engineering on the target architecture; **Green** = gap cleanly
closed, in-spec, "done right"; **Yellow** = athletic / expedient workaround that
unblocks now but incurs architectural drift; **Red** = brittle technical debt,
high-maintenance, likely to regress; **Light-gray** = low-signal, deferrable, or
accept-the-limitation.

**The target for TKT-010 is Green:** one Jinja2 template + one data file + one
driver script, emitting pure SV that passes the same lint / elaboration bar as
hand-written RTL, committed with the DO-NOT-EDIT banner, idempotent on re-run.

* **Green (target):** `gen_dma_params.py` (or similar) in
  `gcb-python-orchestrator/scripts/`, a `dma_params.(yaml|toml)` source
  capturing Doc 11's parameter set + CSR map, a Jinja2 template, and the
  generated `gcb_tensor_dma_params_pkg.sv` + CSR wrapper checked into
  `gcb-wdm-transceiver/rtl/generated/` with the banner. Verilator-lint-clean,
  Surelog-elaboratable, byte-identical on re-run.

* **Yellow (reject):** A one-off script that string-concatenates SV (no real
  template), or generating the SV on the fly at build time instead of
  committing it (Doc 10: generated files are committed so a Python-less
  checkout builds).

* **Red (reject):** Introducing Chisel / Amaranth / any HDL-generator DSL
  (Doc 10's explicit ban), or a template that emits SV only the generator can
  round-trip (custom macros, non-standard constructs) — a second hidden
  language between the engineer and the tape-out netlist.

* **Purple / Light-gray:** A general RTL-generation framework is Purple / out of
  scope — this generates exactly the DMA wrapper. Hand-maintaining the derived
  `localparam`s forever (Light-gray) is the drift this prevents.

**Explicitly out of scope (separate tickets):**
1. The DMA datapath RTL — `TKT-009` (hand-written).
2. A general-purpose RTL codegen framework beyond this wrapper.
3. Regenerating any *other* module's parameters.
4. Wiring the generator into CI (a check that the committed file is current).

## The "Green" Target

1. `gcb-python-orchestrator/scripts/gen_dma_params.py` (Jinja2-based), a
   human-authored source file (`dma_params.yaml` or `.toml`) capturing Doc 11
   §0 / §7, and a `.sv.j2` template — all committed.
2. Generated output: `gcb-wdm-transceiver/rtl/generated/
   gcb_tensor_dma_params_pkg.sv` (the derived `localparam`s) and a CSR decode
   wrapper for `gcb_tensor_dma_arbiter`, each with the
   `DO NOT EDIT — generated by scripts/gen_dma_params.py from dma_params.yaml`
   banner.
3. The generated SV uses only standard constructs (`package` / `parameter` /
   `localparam` / `generate` / `case`); a reviewer reads it as ordinary RTL.
4. Re-running `gen_dma_params.py` on an unchanged source yields a
   byte-identical file (idempotent).
5. `bash sim/lint.sh` (with the generated files in the RTL list) exits 0;
   Yosys + Surelog/UHDM elaborate the generated package and wrapper.
6. `requirements.txt` gains `jinja2`; the script has a `--help` and a
   `--check` mode (exit non-zero if the committed output is stale).
7. Doc 10 is cited in the script header as the governing doctrine; no HDL DSL
   is introduced.
8. The diff is the script + source + template + generated files + a
   `requirements.txt` line — nothing hand-edited in `rtl/generated/`.
