# Objective

Implement and **experimentally verify** the [[TKT-019.7]]-selected implementation
direction against the exact [[TKT-019.5]] failure boundaries. [[TKT-019.7]]'s
preference is a trade-study conclusion, not a proof — this story's job is to
determine, by re-running [[TKT-019.5]]'s original adversarial test as a
**falsification attempt** (not a test whose expected answer is "pass"), whether
the selected mechanism actually closes the hole, and whether it introduces any
new failure. A "the mechanism looks right" outcome is not a finding; only a
re-run, adversarial result is.

## Implementation candidates (TKT-019.7-selected direction, not re-opened; not assumed correct)

1. **Epoch Isolation** — per-word epoch tagging + discard-on-mismatch pop.
2. **Integrity/Framing Protection** — CRC32 covering the payload, the header
   length field, and (candidate, to be architecturally checked before
   trusting — see Task 3) completion semantics (`is_tile_final`).
3. **Timeout Recovery** — a demux-local watchdog, distinct from the CDC
   barrier's own `ALIGN_TIMEOUT`.

These three are carried forward as the direction to implement and test, per
[[TKT-019.7]] — **not** as already-validated mechanisms. [[TKT-019.6]]'s
invariants (M1-M6, see that ticket) are not to be silently weakened or
reinterpreted to make implementation easier; any place the implementation
falls short of a [[TKT-019.6]] invariant is a finding to report, not a detail
to quietly smooth over.

## Required proof

**The exact [[TKT-019.5]] adversarial sequence, re-run as a falsification
test**: transaction N → forced `txn_void` (lane withheld) → late,
never-cleared transaction-N data still queued → transaction N+1 begins on the
same lane set, `channel_enable` untouched. Success is not assumed; the
invariant under test is *"no data belonging to a voided epoch can be
interpreted as valid data belonging to a subsequent epoch"* — measured, not
asserted. CRC32 must independently be shown, under the same adversarial
standard, to trap (not silently accept) every [[TKT-019.5]] Section B
corruption category; a corrupted transaction producing an undetected
successful completion is a failure regardless of which component theoretically
should have caught it.

## Out of scope

1. FEC, retry, optical BER/link-budget modelling — unchanged deferral from
   [[TKT-019.6]]/[[TKT-019.7]].
2. A dedicated hard-flush primitive — superseded by [[TKT-019.7]]'s finding.
3. `gcb-wiki/14` doctrine page.
4. Silicon feasibility, optical BER capability, FEC necessity, or physical
   receiver feasibility claims of any kind — nothing here is evidence for or
   against any of those; this is a digital RTL simulation result only.

## Task 3 — Pre-implementation architecture check

Traced directly against the RTL as it stood before this story's changes and
as modified so far (epoch tagging / CRC / watchdog already landed in
`gcb_dwdm_deskew_cdc.sv`, `gcb_dwdm_payload_mux.sv`, `gcb_dwdm_payload_demux.sv`
in an earlier working session, ahead of this re-check):

1. **Where the epoch originates:** `gcb_dwdm_payload_mux`'s free-running
   `tx_epoch` register (width `EPOCH_W=4`), incremented once per completed
   transmission (on the registered `done` pulse, one cycle after the final
   word is visible — not on `start`, to avoid a same-edge race on a
   1-cycle-EMIT transaction).
2. **Where it is attached to a transaction:** `tx_epoch`'s value at the start
   of a transaction is implicitly "this transaction's epoch" — it is NOT
   stamped into `color_word_t` itself; it travels as a separate signal
   alongside `tx_color`/`tx_valid` on the mux's egress port.
3. **How it travels through the async FIFO:** `gcb_dwdm_deskew_cdc` widens
   its OWN per-lane FIFO storage locally (`FDW = DW + EPOCH_W`,
   `wr_data = {in_epoch[c], color_word_t}`) — `color_word_t` and
   `gcb_dwdm_async_skew_fifo` are unmodified; the epoch rides in the same
   gray-code-synchronised queue entry as the word it tags, so it is
   intrinsically skew-immune (never a separate crossing that could itself
   skew relative to the data).
4. **How the receiving lane compares epoch identity:** combinationally, every
   cycle, per lane: `epoch_match[c] = (head_epoch[c] == expected_epoch)`;
   `lane_ready[c] = ~fifo_empty[c] & epoch_match[c]`.
5. **What happens to a mismatched head:** `epoch_discard[c] =
   channel_enable[c] & ~fifo_empty[c] & ~epoch_match[c]` drives an extra
   `rd_en` term — the stale head is popped and dropped, reusing the FIFO's
   existing pop path, one word per cycle, independently per lane. Confirmed
   by trace: this naturally drains an arbitrary number of stacked stale words
   on an arbitrary number of lanes, one pop per lane per cycle, with no
   special-casing required — each pop re-exposes the next head for the same
   check the following cycle.
6. **How a voided transaction prevents stale data from satisfying a later
   one:** `expected_epoch` advances (`+1`, wrapping mod `2^EPOCH_W`) on
   EITHER a `transaction_done` aligned pop OR a `txn_void` bounded-wait
   timeout. Once advanced, every lane's old-epoch head (whether it arrives
   before or after the advance) fails `epoch_match` and is discarded, not
   aligned.
7. **How CRC is generated, transported, and verified:** the mux computes a
   standard reflected CRC32 (poly `0xEDB88320`, init/final `0xFFFFFFFF`,
   Sarwate byte-table form) over `{3-byte header, payload[0..plen-1]}` and
   appends it as a 4-byte trailer in the framed byte stream, after the real
   payload, before any zero-padding. The demux recomputes the identical CRC
   over the DECODED header+payload-length range and compares against the
   received trailer (read at that same decoded offset).
8. **How completion is accepted:** `gcb_dwdm_payload_demux` sets
   `finalize_pending` when any currently-popped, enabled lane's word carries
   `is_tile_final` — **unconditionally on that bit alone**, with no
   independent check of `word_base` (accumulated word count so far) against
   the count the decoded `payload_len` implies. One cycle later, IF the
   recomputed CRC matches the received trailer, `payload_valid` fires;
   otherwise `integrity_fail` fires. The two are mutually exclusive outputs
   of the same event (never both, never neither) — so CRC failure can never
   produce a silent `payload_valid` on the SAME finalize event.
9. **How watchdog expiry transitions the demux into recovery:** a demux-local
   `watchdog_cnt` starts on a transaction's first accumulating pop and
   increments on every subsequent non-final pop and on every pop-less cycle
   while `word_base != 0`; at `REASSEMBLY_TIMEOUT`, it fires
   `reassembly_timeout`, forces `word_base<='0`, and clears the counter —
   independent of, and distinctly named from, the CDC's own
   `ALIGN_TIMEOUT`/`txn_void`/`stuck`.

### Finding A — `is_tile_final` is checked by exactly one mechanism, not the three [[TKT-019.6]] mandated

[[TKT-019.6]]'s M4 ("Protected Completion") specifies `is_tile_final` + an
explicit length-count check + CRC must **all** agree before `payload_valid` —
deliberately so no single signal is ever the sole arbiter. Bullet 8 above
shows the actual RTL: `finalize_pending` is driven by `is_tile_final` ALONE
(no independent word-count-vs-declared-length gate), and completion
acceptance then rests entirely on CRC as a second, but not third, check. CRC
catches an early/false final **indirectly** (the recompute reads a byte range
the real accumulation hasn't filled, so it mismatches almost certainly) — this
is a strong probabilistic argument, not the deterministic M3 length-check
[[TKT-019.6]] specified. This is a **silent narrowing of M3+M4 down to "CRC
alone,"** which Task 2 of this ticket explicitly said not to do. Reported here,
not silently patched.

### Finding B — `channel_enable` hold-between-transactions can desynchronise `expected_epoch` from `tx_epoch` (new failure mode, more severe than the one being fixed)

Traced directly in `gcb_dwdm_payload_mux.sv`: `lane_enable_q` is set at
`start` and **never deasserted** when a transaction finishes (`done`,
`state<=S_IDLE`) — it holds its value, unconditionally, until the *next*
`start` overwrites it. Per this module's own header comment and TKT-019.2's
original design intent, `lane_enable` wires straight into the deskew's
`channel_enable` in the real (non-testbench) integration.

`gcb_dwdm_deskew_cdc`'s bounded-wait condition is `waiting = (|channel_enable)
& ~aligned_valid` — it does not distinguish "mid-transaction, awaiting
in-flight data" from "idle between transactions, nothing incoming by design."
Consequence, traced, not assumed: if the real system sits idle for longer
than `ALIGN_TIMEOUT` cycles between transactions (a plausible, not contrived,
operating condition — e.g. waiting on the next compute tile), `channel_enable`
is still asserted (holding the *previous* transaction's lane mask),
`aligned_valid` is low (nothing new is arriving), and the CDC's bounded-wait
counter fires a **spurious `txn_void`** — which, since TKT-019.8 attached a
stateful consequence to `txn_void`, *also* advances `expected_epoch`, with
zero correlation to the mux's `tx_epoch` (which only advances once per actual
transmitted transaction). A sufficiently long idle gap can advance
`expected_epoch` an arbitrary number of times (including enough to wrap
`EPOCH_W=4`'s mod-16 space) while `tx_epoch` sits frozen. The next REAL
transaction is then tagged with a `tx_epoch` value that may no longer equal
`expected_epoch` — every one of its words is treated as stale and
**permanently discarded**, and the barrier never aligns it. This is a
denial-of-service-shaped failure mode this story's own mechanism introduces,
not one inherited from TKT-019.5, and it was not exercised by any existing
regression: the integration testbench drives `channel_enable` from an
independent Python "channel" layer (per TKT-019.4's explicit scope — the
real router/tx_packager/sync-deskew chain is excluded), never from the real
`gcb_dwdm_payload_mux.lane_enable` signal end-to-end, so this interaction has
never actually been exercised against real RTL-to-RTL wiring by any test in
this repo.

### Disposition

Per this ticket's Task 3 instruction ("if the proposed CRC/framing
arrangement leaves any single control bit capable of causing an undetected
successful completion, stop and report the architectural conflict before
implementing it... do not invent a fix silently"): **both findings are
reported here, unresolved.** Finding A is the control-bit-arbiter conflict
the instruction anticipated. Finding B is an additional, independently
discovered new failure mode with no surviving regression coverage (since no
test in this repo exercises real mux→CDC wiring with a realistic idle gap).
No RTL fix for either has been implemented in this revision. Execution Log
below reflects testing performed **before** this architecture re-check, under
conditions that happen not to trigger Finding B (transactions run close
together, no idle-gap exercised) and do not independently test Finding A
(the tested corruption categories are all caught by CRC in the tested cases,
which is consistent with both "M4 works as designed" and "M4 happens not to
have been defeated by the specific corruptions tested" — the two are not
distinguishable from a passing regression alone, which is exactly why Finding
A is reported as a structural gap rather than dismissed).
