# Objective

`TKT-019.19` compared five candidates for closing the data-plane reset-
aliasing gap and found Candidate C (reset-time physical drain) the
cheapest *if* its own contingent question resolves favourably — whether
`gcb_dwdm_async_skew_fifo`'s pointer-reachability argument, proven only
for the always-simultaneous reset this epic's own testbenches have
exercised since `TKT-019.3`, also holds under **independent, non-
simultaneous per-lane reset timing** (`TKT-019.13` §9.1's own flagged
`ARCHITECTURAL ASSUMPTION`, never tested). This ticket builds and runs
that test. **It does not assume the assumption is true or false** —
the desk analysis in §2 finds no structural hazard by reading the RTL,
but this epic's own discipline ("do not assume a mechanism is correct
before proving it," `TKT-019.16`'s own framing) applies here with equal
force: a clean reading of the RTL is not a proof. No PBG grade is
assigned on drafting, consistent with every prior `TKT-019.x` draft.

---

## 1. Architectural hypothesis

> If each lane's `wr_rst_n[c]` and the shared `rd_rst_n` are asserted
> and de-asserted at independently skewed times — not simultaneously —
> `gcb_dwdm_async_skew_fifo`'s pointer-based empty/full reachability
> argument still produces a consistent, correct result once each
> domain's own reset has individually completed, because reset safety
> is a **per-domain**, not a **cross-domain-simultaneity**, property of
> this specific design.

**Stated as a hypothesis, not a conclusion** — §2 gives the reasoning
that motivates it; §3 is what actually tests it.

## 2. Structural pre-analysis (desk reading, not a proof)

Re-inspected directly, not from memory: each of the four synchronizer
registers in `gcb_dwdm_async_skew_fifo.sv` is reset by **its own local
domain's** reset signal, never the other domain's:

| register | domain | reset signal |
|---|---|---|
| `wr_ptr_bin`/`wr_ptr_gray` | write | `wr_rst_n` |
| `rd_ptr_gray_sync1_w`/`sync2_w` (read ptr synced **into** write domain) | write | `wr_rst_n` |
| `rd_ptr_bin`/`rd_ptr_gray` | read | `rd_rst_n` |
| `wr_ptr_gray_sync1_r`/`sync2_r` (write ptr synced **into** read domain) | read | `rd_rst_n` |

**Why this matters:** `TKT-019.13` §9.1's own caution was that the
reachability argument needs "enough mutual overlap to also flush the
2-flop cross-domain synchronizer registers on both sides." Read
literally, that could be misunderstood as requiring the *other*
domain's reset to reach across and flush a synchronizer — but the
table above shows each synchronizer pair is flushed by its **own**
domain's reset, not the other's. If one domain's reset genuinely holds
its own flops at 0 for long enough (a single-domain timing question,
not a cross-domain one), that domain's half of the picture is correct
**regardless of what the other domain is doing**: a write domain that
exits reset while the read domain is still held in reset sees a
synced-read-pointer copy of 0 (since the read domain's own pointer
really is 0, frozen there by its own reset) and correctly computes
`full` from that; the reverse case is symmetric. `mem[]` itself carries
no reset by design, but since both pointers independently start at 0
once each domain's own reset completes, addressing stays consistent
regardless of *when* each domain got there.

**This analysis does not find a hazard — it is also not a proof.** It
has not been checked against: three or more lanes reset at mutually
different times (not just two domains); a lane whose recovered clock is
**absent entirely** during another domain's reset window (a different,
also-interesting question this module's own CDC rationale, `TKT-019.3`,
already flags as a real possibility for independently-recovered per-λ
clocks); or whether `gcb_dwdm_deskew_cdc`'s own `expected_epoch`/FSM
reset (a single register, reset by the shared `rd_rst_n` only) interacts
safely with per-lane FIFOs that come out of reset at different times
from each other and from that shared register.

## 3. Planned adversarial test matrix

Built in `sim/cocotb/test_wdm_link_integration.py`, reusing
`wdm_link_integration_tb_top.sv`'s already-exposed, independently-
driveable `c{i}_wr_rst_n` ports (no new RTL or tb_top port needed — the
testbench has simply always driven them in lockstep since `TKT-019.3`;
this ticket is the first to drive them apart). Cases, none assumed safe
or unsafe in advance:

* **A. Read-domain-first:** `rd_rst_n` de-asserts while every
  `wr_rst_n[c]` is still held low; lanes release staggered, one at a
  time, afterward.
* **B. Write-domain-first:** every `wr_rst_n[c]` de-asserts (lanes begin
  writing) while `rd_rst_n` is still held low; `rd_rst_n` releases last.
* **C. Staggered across lanes:** each of the `NUM_COLORS` lanes'
  `wr_rst_n[c]` de-asserts at a distinct, randomized time, `rd_rst_n`
  de-asserting somewhere in the middle of that spread — the realistic
  case for independently-recovered per-λ clock/CDR domains, not just a
  two-domain ordering question.
* **D. Clock-absent-during-reset:** one lane's `c{i}_wr_clk` simply
  does not start toggling until well after that lane's own
  `wr_rst_n[c]` has already de-asserted (modelling a CDR that has not
  yet locked) — distinct from cases A-C, which all assume the clock is
  already running when reset releases.
* **E. Reset re-assertion mid-skew:** a second reset pulse arrives while
  case C's staggered release is still in progress, before every lane has
  individually settled — tests whether a second reset can be safely
  layered on top of an already-in-progress, not-yet-complete first one.

**For every case, check:** no word is silently dropped that
`do_wr = wr_en & ~full`'s own documented behaviour didn't already
predict; no word is corrupted (FIFO order/value exactness, the same
standard `TKT-019.3`'s own `test_async_fifo_correctness` already uses);
`fifo_empty`/`fifo_full` never produce a transient value that would let
a stale, pre-reset word be accepted as current once normal (post-reset)
traffic resumes; `gcb_dwdm_deskew_cdc`'s own `expected_epoch`/`CDC_IDLE`/
`CDC_ACTIVE` state settles to the same clean values this epic's
existing (always-simultaneous-reset) tests already confirm.

## 4. What this ticket does and does not conclude in advance

**Possible outcomes, not predetermined:**

1. The hypothesis holds under every case tested — `TKT-019.19`
   Candidate C's contingency is discharged, and reset-time physical
   drain becomes the leading candidate for closing data-plane reset
   aliasing, at lower cost than per-word session tagging (Candidate A).
2. The hypothesis fails under one or more cases — a genuine new finding
   to report and hold for disposition, per standing discipline, not
   patched inside this ticket. If so, Candidate A's per-word tagging
   (and its own unresolved wire-format cost, `TKT-019.9` vs. `TKT-019.7`,
   still unreconciled) becomes harder to avoid, not merely one option
   among several.
3. The hypothesis holds for cases A-C but not D or E — a partial result,
   narrowing rather than fully closing or fully reopening the question.

**No RTL change is made by this ticket regardless of outcome.** Any
defect found is reported and held, exactly as `TKT-019.8`'s own Findings
A/B were before `TKT-019.10` resolved them — this ticket characterizes,
it does not fix.

### 5-case adversarial suite, built in `test_wdm_link_integration.py`

All five cases (§3 A-E, renumbered 1-5 below to match the Architect's task
list) reuse `wdm_link_integration_tb_top.sv`'s already-exposed, independently
driveable `c{i}_wr_rst_n` ports — no new RTL or tb_top port was needed. Each
case traps or pushes deliberately-adversarial "stale" words via a new
`_trap_stale_words()` helper and observes the post-reset transaction through
a new `_run_post_reset_diagnostic()` helper (see Testbench findings below for
why both needed to be built carefully, not taken at face value on first
green run).

### Result per case (deterministic across 2 independent full-suite runs)

| # | Case | Outcome | Verdict |
|---|------|---------|---------|
| 1 | Read-domain reset deasserts before write-domain | `payload_valid`, byte-exact, `len==1024`, `mode==B` | **PASS — clean** |
| 2 | Write-domain reset deasserts before read-domain | `integrity_fail` | **FINDING — confirmed contamination, CRC-caught** |
| 3 | Staggered lane resets across the 60-lane ceiling | `length_mismatch` | **FINDING — confirmed contamination, length-check-caught** |
| 4 | Clock-absent/inactive during reset transition | `integrity_fail` | **FINDING — confirmed contamination, CRC-caught** |
| 5 | Reset reassertion mid-skew, in-flight data trapped | `payload_valid`, byte-exact | **PASS — clean** |

Framework-level result both runs: `TESTS=22 PASS=22 FAIL=0`. **This is not
the same as "5/5 clean"** — the cocotb test *functions* for Cases 2-4 were
written to assert that contamination is *detected* (not silently passed),
so a framework "PASS" on those three cases means "the predicted finding
reproduced and was caught," not "no hazard exists." This distinction is
deliberate and is why the per-case outcome column above, not the bare
`PASS=22` line, is the ticket's real result.

**Case 1 detail.** Stale words trapped on lanes `[0,1,2]` before the reset
sequence; `rst_n` (read domain) released first, held 10 edges, then all
`wr_rst_n[c]` released. `_all_fifo_empty(dut)` and `expected_epoch==0` both
confirmed before issuing the post-reset transaction (Mode A, 271 B). Clean,
byte-exact reconstruction.

**Case 2 detail — the core finding.** All `wr_rst_n[c]` released first
(write domains live); one `c0_wr_clk` edge later, `_trap_stale_words(dut,
chan, [3,4,5], epoch_tag=0)` pushes a stale, epoch-0-tagged word into three
lanes *during the skew window itself* — after those lanes' own write-side
reset has completed but before the read domain's reset (and `expected_epoch`)
settles. `rst_n` released last. Mechanism: a lane's `wr_ptr_bin` has already
advanced past address 0 by the time `rd_ptr_bin`/`expected_epoch` reach 0,
so the stale word sits at address 0, FIFO-ordered *ahead of* the next
legitimate write, tagged with the exact epoch value (0) the reset is about
to hand the next real transaction — breaking the "overwrite-before-read"
property that makes *simultaneous* reset safe (`TKT-019.13` §9). Logged
telemetry: `outcome=integrity_fail, stuck=0x0, fifo_empty=0x0fffffffffffffff,
lanes-nonempty-as-predicted=True`. **Confirmed, not patched, held for
disposition**, per standing discipline.

**Case 3 detail.** Per-lane write-reset release times drawn as integer
picoseconds, `release_delay_ps = {l: randint(0,20000) for l in 60 lanes}`;
shared `rd_rst_n` releases at `10000 ps`. 27 of 60 lanes released before the
read domain ("early"); trapped lanes `[0,5,7]` drawn from that early set.
Outcome: `length_mismatch` — the same Case-2 mechanism reproducing under a
realistic, fully-staggered, many-lane pattern rather than a hand-picked
two-lane ordering. **Confirmed, not patched.**

**Case 4 detail.** Lane 7's clock withheld entirely through the whole
reset-assert/release sequence (every other lane and the shared `clk`
proceed normally, simultaneous); only once both `rst_n` and every other
`wr_rst_n` have already released does lane 7's clock start, and the first
activity on it is a trapped stale word. Outcome: `integrity_fail` — the
same write-after-read-reset-settles condition Case 2 found, reached via
clock absence rather than deliberate reset-signal skew, confirming this is
one mechanism with (at least) two distinct triggering paths. **Confirmed,
not patched.**

**Case 5 detail.** Same staggered-release structure as Case 3, but at
`t=8 ns` (mid-spread) the test re-asserts `rst_n=0` and every `wr_rst_n[c]=0`
— interrupting the first, partial release attempt and whatever had already
been trapped by it — holds 15 ns, then performs one final, clean,
simultaneous release. Outcome: clean, byte-exact. Re-asserting reset
mid-skew correctly re-froze every lane and discarded the partial first
attempt's effects.

### Testbench findings (construction discipline applied to this ticket's own tests, not just the RTL)

Two genuine testbench bugs were found and fixed before the result above
could be trusted — both recorded here per this epic's standing practice of
documenting debugging discoveries, not just final results:

1. **First full run of all 5 cases passed cleanly with zero findings** —
   contradicting the structural prediction in §2. Root cause, confirmed by
   re-reading `gcb_dwdm_deskew_cdc.sv` directly: `wr_en = in_valid[c] &
   channel_enable[c]`. The first version of `_trap_stale_words()` never
   asserted `channel_enable` for its target lanes, so every "trapped" word
   was silently dropped at the write-enable gate — nothing was ever
   actually written. The entire adversarial construction was a no-op, not
   a clean result. Fixed by making the helper read-modify-write
   `dut.cdc_channel_enable` (asserting the target mask, restoring the
   prior value after); for Cases 3/5 the mask is asserted once up front,
   before spawning the concurrent per-lane release tasks, specifically to
   avoid a read-modify-write race between tasks touching the same shared
   bus.
2. After fix #1, Cases 2-4 began throwing `SimTimeoutError` inside the
   original bare `try/except` around the shared `run_clean_txn()` helper.
   That helper only watches for `payload_valid` and cannot distinguish a
   genuine undetected hang from the demux/CDC correctly raising
   `integrity_fail`/`length_mismatch`/`reassembly_timeout`/`cdc_txn_void`
   instead — all of which equally prevent `payload_valid` from firing and
   so would have produced an identical, undifferentiated "timeout," which
   would have understated the actual result (detected-and-rejected, not
   hung). Fixed by building `_run_post_reset_diagnostic()`, a proper
   multi-outcome waiter watching all five terminal signals and snapshotting
   `stuck`/`fifo_empty` in the same cycle the terminal condition fires.

Both fixes were confirmed testbench-side before being corrected — no RTL
was touched, consistent with the explicit "do not patch RTL during this
run" instruction and this epic's standing discipline of separating
testbench bugs from RTL/architectural findings.

## Telemetry & Evaluation

No PBG grade assigned — this is an architecture/RTL-experiment ticket, not
a deliverable implementation, consistent with every `TKT-019.x` ticket of
this kind since `TKT-019.6`. `telemetry_color: pending` stands unchanged.

**Answering §4's own pre-stated outcome options:** outcome 3 occurred —
the hypothesis holds for the two cases where one domain's reset release is
strictly ordered before the other transitions with no write activity
injected into the skew window itself (Cases 1, 5), but **fails** for every
case where a write lands in the skew window before the read domain's reset
settles (Cases 2, 3, 4) — a partial result that narrows, rather than fully
closes or fully reopens, `TKT-019.19`'s Candidate C contingency. The
pointer-reachability argument in §2 is **not wrong as stated** — it
correctly describes what each domain's own pointers do once *that*
domain's own reset has completed — but it is **insufficient**: it says
nothing about a write that occurs *before* the read domain's reset has
completed, and that gap is exactly where all three confirmed findings
live. Existing CRC32 (`integrity_fail`) and length-check (`length_mismatch`)
mechanisms (from `TKT-019.8`/`.10`) caught all three findings this run —
but detection-after-corruption is a materially weaker property than
prevention, and this is one seed/one run per case, not an exhaustive
sweep. See the Architect-facing report for the explicit, non-overclaiming
answer to whether this closes the in-band-nonce question.

**Final State:** `closed | falsified-partial` — hypothesis falsified for
Cases 2-4, confirmed for Cases 1 and 5. Disposition (Candidate A vs. C vs.
other, per `TKT-019.19`) remains the Architect's to make, per §Out-of-scope
item 2.
