# Objective

`TKT-019.13`'s central finding was not "reset needs a wider counter" — it
was that **no distributed identity-authority contract exists at all**:
the sender owns `tx_epoch`, the receiver independently evolves
`expected_epoch`, and a receiver-side `txn_void` is not propagated back
to the sender (confirmed by direct port-list inspection, not inferred).
This ticket defines the **transaction lifecycle, retirement semantics,
identity authority, and reset/quiescence contract** that must exist
*before* `TKT-019.15` can select an identity width — **not** a width
itself. **This ticket does not assume it will produce a finite
identity-width requirement.** If a required bound remains unavailable
at the end, §10 says so exactly, not approximately. **No RTL is
modified, staged, or committed.** No PBG grade is assigned, consistent
with `TKT-019.6`/`TKT-019.7`/`TKT-019.12`/`TKT-019.13`'s own precedent.

## 3. Identity authority — who owns transaction identity?

Each candidate is evaluated against all eight requested fields. The
explicit instruction governing this section: **two independently
advancing counters are not a valid synchronized identity model unless
an explicit reconciliation mechanism exists** — today's architecture
is exactly two independently advancing counters with no reconciliation
path, and is not treated as "model 3" (shared/synchronized) below; it
is the unlabeled baseline every candidate is measured against.

### 3.1 Sender-authoritative identity

| field | answer |
|---|---|
| Who allocates identity | Sender (`tx_epoch`, `+1` on own `done`) |
| Who observes identity | Receiver, by reading the tag off incoming words (`in_epoch`) — never told independently |
| How receiver learns *current* identity | Only by inference from the data itself — it has no way to ask "what is the sender's value right now" before data arrives |
| How `txn_void` propagates | It doesn't — under a pure sender-authoritative model the receiver has no standing to unilaterally retire anything; `TKT-019.3`'s own bounded-wait watchdog (built specifically to replace an *unbounded* wait) has nothing authoritative to retire *to* unless paired with a sender heartbeat |
| How success propagates | Implicitly — the receiver infers success from `aligned_valid`+`transaction_done`, not from an explicit sender signal |
| Disagreement | Receiver has no mechanism to correct the sender, and no authority to declare the sender wrong — it can only stop aligning locally |
| Authoritative after timeout | **Neither, ambiguously** — the sender believes its own state is current (it was never told otherwise); the receiver has locally declared the generation void but has nothing to declare it *to* |
| Convergence | **Not established** — there is no path back to agreement, only independent drift, identical in structure to today's architecture |

### 3.2 Receiver-authoritative identity

| field | answer |
|---|---|
| Who allocates identity | Receiver (`expected_epoch`) |
| Who observes identity | Sender — but only via a **new port that does not exist today** (confirmed absent, `TKT-019.13` §3 preamble) |
| How receiver learns *current* identity | Trivially — it's the receiver's own state |
| How `txn_void` propagates | Trivially on the receiver side; reaching the sender requires the same new port |
| How success propagates | Same — requires the sender to read the receiver's state before stamping the *next* transaction, not merely the retirement event |
| Disagreement | Cannot happen for the **value** by construction, once the wire exists — **can** still happen for **timing**, if the sender latches a stale copy before a fresh one propagates (a `T_propagation < T_txn_min` proof obligation, not free) |
| Authoritative after timeout | Receiver, unambiguously — this is the one candidate where "authoritative" has a clean, single answer |
| Convergence | By construction, **provided** the propagation-timing obligation above is independently proven — not automatic just because the wire exists |

### 3.3 Explicit shared/synchronized transaction identity

| field | answer |
|---|---|
| Who allocates identity | Neither side alone — a third, shared register/counter both sides read and write |
| Who observes identity | Both, symmetrically, by design |
| How receiver learns *current* identity | Same read both sides use — **not** an independently-maintained local copy (the explicit condition this model must meet to be distinct from today's baseline) |
| How `txn_void` propagates | The shared state changes once; both sides see the *same* changed value on their next read — **not** two separate local updates that happen to agree |
| How success propagates | Same mechanism |
| Disagreement | Should be structurally impossible for the value itself — but the shared resource must cross into **every** clock domain involved (sender's `clk`, receiver's `rd_clk`, and — if independently recovered — each lane's `wr_clk[c]`), which **does not eliminate the CDC problem, it relocates it** to a new shared resource needing the identical cross-domain-consistency proof this epic has chased since `TKT-019.3` |
| Authoritative after timeout | The shared state itself — but only if its own crossing is proven, which is an unevaluated, potentially equally hard, new proof burden |
| Convergence | Only as strong as the new shared resource's own (unbuilt, unverified) CDC correctness — explicitly **not** a shortcut past this epic's core difficulty |

### 3.4 Receiver NACK/ABORT propagating retirement to sender

| field | answer |
|---|---|
| Who allocates identity | Sender, unchanged (`tx_epoch`, `+1`) — this model changes *when* advancement is permitted, not *who* generates the value |
| Who observes identity | Sender still generates; receiver observes via the tag, as today |
| How receiver learns *current* identity | Unchanged from today — it still infers from incoming data for the *matching* case; the new signal only concerns the *abort* case |
| How `txn_void` propagates | Via one new receiver→sender signal (reusing `txn_void` or an equivalent retire pulse) — the smallest wiring delta of any candidate here |
| How success propagates | **Not addressed by this candidate at all** — it is specifically an abort-path mechanism; the clean-completion path is unaffected and remains purely sender-local (`done`) |
| Disagreement | Can still occur if the retirement signal is delayed past the sender's next `start` — narrows the open proof obligation to a single latency bound (`T_backchannel_max < T_txn_min`), the same obligation as 3.2, now attached to an event instead of a value |
| Authoritative after timeout | Receiver declares abort; sender decides the *next value* — an explicit **split** authority, not a single owner, worth naming precisely since it is neither 3.1 nor 3.2 in pure form |
| Convergence | Converges **if** the latency bound above holds; diverges silently (reproducing today's exact gap) if the signal is lost or arrives late — see §8's backchannel-reliability analysis, this is not free of its own contract |

### 3.5 Explicit transaction-start handshake

| field | answer |
|---|---|
| Who allocates identity | Negotiated per transaction — proposed by one side, confirmed by the other, before payload transmission begins |
| Who observes identity | Both, by construction — neither proceeds without having seen and accepted the same value |
| How receiver learns *current* identity | Through the handshake itself, not by inference from data |
| How `txn_void` propagates | Naturally — abort is "the negotiated ID is retired," observable to both since both participated in establishing it |
| How success propagates | Same handshake-completion channel, or an equivalent close-out message |
| Disagreement | Cannot reach the payload phase while disagreeing — disagreement **blocks progress**, it does not silently alias |
| Authoritative after timeout | Neither — the transaction simply never starts (or never completes) until negotiation concludes; "authority" is not the right frame for this model |
| Convergence | Strongest of the five — agreement is a **precondition** of the transaction existing, not a property that must hold *afterward* |

### 3.6 Other materially different mechanisms

* **Timestamp/real-time identity** — trades a finite-counter-wrap
  problem for a clock-synchronization problem across independently
  recovered domains; not simpler.
* **Content-addressed/nonce identity** — trades a structural
  (provable-by-construction) argument for a probabilistic one — a
  different epistemic category; mixing it into the same `PROVEN`
  vocabulary as the others without saying so would itself be an
  overreach.
* **Hybrid** (coarse session marker + fine per-transaction identity,
  composed with one of 3.1-3.5 for the per-transaction axis) — **not**
  a sixth alternative; an orthogonal composition, covered fully under
  §7 (reset) and §11.F, not a substitute for deciding §3 on its own.

**No mechanism is selected.** §11 carries the cost/benefit comparison
forward.

## 4. Formal transaction lifecycle

```
NEW → ACTIVE → { SUCCESS | ABORTED } → RETIRED → REUSE
```

**`RETIRED` is not a software state label — it is a claim that must be
backed by specific evidence, and the current architecture does not
produce that evidence.** The five terms are defined separately because
the RTL, as built, **conflates several of them into one register
update**, which is itself part of the defect this ticket formalizes:

* **Completion** — the transaction's payload was correctly delivered.
  Evidence today: `aligned_valid & transaction_done` (CDC) /
  `payload_valid` with `integrity_fail`/`length_mismatch` both clear
  (demux). This is a genuine, well-evidenced event.
* **Abort** — the transaction was declared unsuccessful. Evidence
  today: `txn_void` (CDC bounded-wait) / `integrity_fail` /
  `length_mismatch` / `reassembly_timeout` (demux). Also genuinely
  evidenced — **but abort is not retirement.**
* **Retirement** — the specific claim this ticket is built around:
  **no word or control state still attributable to this generation can
  subsequently reach any acceptance point.** Evidence today: **none
  exists as a distinct event.** The RTL advances `expected_epoch` in
  the *same* cycle `txn_void` fires, which looks like retirement but is
  not backed by any observation that the physical backlog is actually
  drained (`TKT-019.12` §6/§7, `TKT-019.13` §6's `D ≤ I` analysis — the
  entire reason that derivation was necessary is that retirement is
  *assumed*, not *evidenced*, at the moment of abort).
* **Transport quiescence** — every physical path that could still
  deliver a word belonging to this generation (lane FIFOs, in-flight
  writes not yet crossed into the read domain, anything upstream of
  the mux this architecture does not own) has gone empty and stayed
  empty long enough that nothing more is coming. This is a **stronger**
  claim than "the FIFOs I can see are empty right now" — it requires a
  bound on how long the sender could still legitimately be emitting
  old-generation data, which (§6/§8) this architecture does not
  currently establish.
* **Identity reuse** — the numeric value that was retired becomes
  eligible to be assigned to a new generation. Today this happens
  **unconditionally**, in the same cycle as abort, with **none** of the
  preceding evidence checked.

**Are these necessarily the same event? No — and the current RTL's
central defect, restated precisely, is that it treats `{Abort,
Retirement, Transport Quiescence, Identity Reuse}` as one event,
simultaneous with `txn_void`, when only `Abort` is actually evidenced
at that instant.** `TKT-019.6`'s original M2 (explicit
quarantine) would have separated Abort from Retirement with an
observable window; `TKT-019.7` superseded M2 specifically on
verification-cost grounds for the *within-run* `txn_void` case, without
re-examining whether collapsing these events was itself safe once
identity-space exhaustion (not just the Ghost-Payload mechanism M2 was
built to stop) was considered — it was not yet a known question at the
time `TKT-019.7` was written.

## 5. Formal retirement invariant

> Once transaction N reaches **RETIRED**, no word or control state
> belonging to N can subsequently reach any acceptance point where it
> could be interpreted as a valid transaction.

**`txn_void` does not establish this invariant.** It declares the
transaction `ABORTED`, and (per §4) is the only evidenced event at that
instant — the architecture must not treat it as `RETIRED` without
separate evidence. Per the task's own classification rule: since stale
data remains physically capable of arriving after `txn_void` (every
item below), **the correct classification of the post-`txn_void` state
is `ABORTED`, not `RETIRED`.**

### States inspected for violation, each against the RTL directly

| state | could it violate the invariant? | basis |
|---|---|---|
| **Sender TX queue/registers** (`word_a_flat`, `word_b_flat`, `tx_color`, `tx_valid`) | **No evidence of a violation found** — the mux has no multi-transaction queue (`state_e {S_IDLE, S_EMIT}` is strictly sequential); `tx_valid` is only asserted during `S_EMIT`, and the data registers are overwritten at the start of each new `S_EMIT` sequence. Not independently re-verified by simulation in this ticket — a desk-level reading, not a `PROVEN` claim. |
| **CDC lane FIFOs** (`gcb_dwdm_async_skew_fifo`, instantiated inside `gcb_dwdm_deskew_cdc`) | **Yes — the primary, already-demonstrated vector.** `TKT-019.11`'s multi-lane/backlog tests and `TKT-019.12`/`.13`'s derived drain-race both operate here. |
| **Deskew FIFOs** | Same module as above — not a separate instance in the CDC path; the original single-clock `gcb_dwdm_skew_fifo`/`gcb_dwdm_deskew` are a parallel, unrelated sibling path not wired into this chain. |
| **Lane-local state** (`stuck`) | **No evidence of a violation** — `stuck` is informational (sticky until the next `aligned_valid`), not read by any accept-path logic; it cannot itself cause acceptance. |
| **Demux/reassembly state** (`word_base`, `word_a_flat`/`word_b_flat` accumulators) | **Partially self-healing, with an unaddressed upstream dependency.** Confirmed by inspection: `reassembly_timeout` resets `word_base <= '0` (`gcb_dwdm_payload_demux.sv`), and decode only ever reads up to the *current* transaction's own `word_base` — mirroring the async FIFO's own pointer-reset-without-memory-clear safety argument. **But** this only protects the demux's *own* register; it says nothing about whether the *data feeding it* (`aligned_valid`/`in_color` from the CDC) is itself retired — the demux has no visibility into the CDC's `txn_void`/`stuck` at all (its port list carries only `in_color`, `aligned_valid`, `lane_enable` — confirmed, `TKT-019.13` §3 preamble). A CDC-side violation propagates straight through. |
| **Watchdog state** (`wait_cnt`, `CDC_IDLE`/`CDC_ACTIVE`) | **No evidence of a violation** — resets cleanly on `txn_void`, confirmed directly in the RTL (`TKT-019.13` §9). |
| **Completion state** (`done`, `payload_valid`, `aligned_valid`) | **No evidence of a violation** — all are one-cycle pulses, not held state. |
| **Pending control state** (`busy`) | **No evidence of a violation** — purely combinational off `state` (`assign busy = (state == S_EMIT)`), confirmed by inspection; no separate register to get stuck. |

**Conclusion: the CDC lane FIFOs are confirmed (by `TKT-019.11`'s own
adversarial tests) to be the load-bearing violation vector; the demux's
own local state is self-healing but structurally blind to whether its
CDC-side input is actually safe.** No other inspected state shows an
independent violation path — stated as a desk-level finding, not as a
simulation-backed `PROVEN` result for the "no violation" rows.

## 6. The retirement barrier — what actually establishes `NO_OLD_DATA_CAN_STILL_ARRIVE`

| mechanism | finite, provable bound? | basis |
|---|---|---|
| **1. Explicit ACK/retirement handshake** | Finite **iff** the handshake's own round-trip latency is independently bounded — a genuine, but *localized* (not circular), unproven quantity |
| **2. Physical transport drain** (wait for `fifo_empty[c]` on every enabled lane, directly observed — not inferred from `expected_epoch`) | **The strongest candidate available without adding a new CDC primitive** — `fifo_empty[c]` already exists as a signal (`gcb_dwdm_async_skew_fifo`'s own output, already proven correct by `TKT-019.3`'s verification). Bounded above by `D` cycles worst-case drain (`TKT-019.12` §7.F, `PROVEN — DIGITAL SIMULATION, TESTED CONDITIONS` for the cap on queue depth). **But** a single "it's empty now" snapshot is not sufficient by itself — see the race below |
| **3. FIFO flush** | Same staleness-gap caveat `TKT-019.7` already found for the `txn_void` case — the read domain only ever holds a *synchronized, slightly stale* copy of the write pointer; a naive single-pulse flush only discards what had already crossed at the instant of the pulse |
| **4. Quarantine until stale state expires** | Finite only if "expires" is bounded by a proven `T_stale_max` — circles back to `TKT-019.12` §7.H's structural circularity, **not** resolved by renaming the wait a "quarantine" |
| **5. Sequence/generation transition with explicit acknowledgment** | Same strength class as #1, applied at the generation level rather than per-transaction — combines identity-authority model 3.5 with a reset-style generation boundary |
| **6. Reset barrier** | Finite **only if** reset itself drains correctly, which (`TKT-019.13` §9.1) is conditional on every reset domain overlapping sufficiently — an `ARCHITECTURAL ASSUMPTION`, not independently verified for non-simultaneous per-lane resets |
| **7. Other — composing #1 and #2** | **The most defensible direction surfaced by this analysis, not a selection:** use `fifo_empty[c]` (#2) as the primary, already-proven-correct observation, but **do not trust a single snapshot** — a lane observed empty could be re-filled by a straggler the sender has not yet been told to stop emitting. The observation must be held across (or re-confirmed after) a bounded backchannel round-trip that tells the sender to stop — i.e. #2's structural strength plus #1's latency bound, not either alone |

**On the instruction not to use a testbench timeout as physical proof:**
`ALIGN_TIMEOUT`/`REASSEMBLY_TIMEOUT` **are** part of the architecture
contract (real RTL parameters the hardware actually counts against,
not testbench-only artifacts) — but their **numeric values** are
`TKT-019.3`'s own stated, unmeasured placeholders. They may be used as
*the contract's own* bound (the hardware genuinely behaves this way),
but any retirement-barrier proof built on them inherits their
`UNPROVEN`-as-a-physical-number status and must say so, not borrow
their authority as RTL parameters to imply a validated time bound.

## 7. Reset semantics

### The required invariant, restated precisely for this ticket

```
old generation N in flight → reset → new generation starts
  → old delayed data arrives
```

must never result in acceptance, **regardless of what numeric tag the
old data carries and what tag the new generation is assigned** —
`TKT-019.13` §5 already established this cannot be phrased purely in
terms of tag-space exhaustion, because reset does not consume any of
the identity space; it restarts both `tx_epoch` and `expected_epoch` at
the fixed value 0 unconditionally (confirmed directly in both modules'
reset branches). **Reset requires a distinct identity namespace from
ordinary transaction sequencing** — re-confirmed here, not merely
repeated: ordinary wraparound is a *within-namespace exhaustion*
problem (the counter keeps counting and eventually repeats); reset is
a *namespace-reset* problem (the counter is told to forget how far it
had counted). A fix for one is not automatically a fix for the other,
and nothing in this ticket's re-inspection of the reset branches
changes that conclusion.

### Candidate mechanisms

| | Physical drain/quiescence before restart | Reset handshake | Explicit new-session generation | Persisted generation | Session nonce | Combination |
|---|---|---|---|---|---|---|
| **Mechanism** | Hold post-reset idle for ≥ the (still unproven) stale-data bound before accepting traffic | Sender and receiver explicitly exchange a "starting fresh" acknowledgment at reset time, before any payload resumes | A coarse counter incremented once per reset, prefixed to the ordinary per-transaction tag | The generation marker above, surviving power loss | A random/monotonic value drawn fresh at session start | §6's composed direction (drain-observation + backchannel), applied at reset time specifically |
| **Provable bound?** | Only as strong as the same unproven `T_stale_max`/quiescence-duration number — **does not escape §6's circularity** | Yes, structurally, same class as §3.5/§6 item 1 | Yes, by construction — no dependence on any time bound | Yes, by construction, **and** survives power cycling | Probabilistic, not structural — same epistemic caveat as §3.6 | Yes, combining drain's structural strength with handshake's bounded latency |

### Persisted generation, analyzed along all seven requested axes

* **Storage location:** not present in any form today — would require
  either non-volatile storage (new hardware dependency) or a
  host/firmware-maintained value re-loaded via CSR write after every
  boot (new interface dependency). Neither exists in this repo.
* **Persistence guarantees:** a plain register has **none** across a
  power cycle (`rst_n` is the same signal ordinary reset uses, and is
  typically tied to power-on reset too) — "persisted" is not free
  just by declaring it; it requires genuinely different storage.
* **Power-loss behavior:** undefined for a write interrupted mid-
  update unless the storage has its own torn-write protection (a
  checksum, a redundant copy, or an atomic-write guarantee) — a new,
  unanalyzed failure mode this epic has not previously had to model.
* **Width:** orthogonal to persistence itself — could be small (a
  32-bit boot counter is astronomically safe against wraparound across
  any realistic service life, unlike a per-transaction counter).
* **Eventual wrap:** not eliminated, only pushed to a vastly longer
  timescale — stated precisely rather than claimed absolute.
* **Corruption/failure behavior:** **if the persisted value is lost or
  corrupted, the system falls back to exactly today's unsafe default**
  (restart at a fixed/undefined value) — not a degraded-but-still-
  safer state. This is the load-bearing finding of this subsection.
* **Does persistence become a new safety dependency?** **Yes,
  explicitly.** The system's identity-safety now depends on a
  component (the persistence mechanism) this architecture has never
  had and has not validated.

**Not assumed: persistence is not automatically superior to a physical
barrier.** A meaningful, non-obvious asymmetry, stated as reasoning
rather than doctrine: a physical drain/quiescence barrier's failure
mode is a **liveness** failure (the system takes longer than expected
to resume, but does not silently accept bad data) — a physical drain
that hasn't actually finished simply keeps the system waiting.
Persisted generation's failure mode, if the persistence mechanism
itself fails, is a **silent correctness** failure — the marker quietly
reverts to its unsafe default and nothing downstream is told anything
changed. All else equal, a mechanism whose failure mode is observable
and safe (fail-blocked) is architecturally preferable to one whose
failure mode is silent and unsafe (fail-open) — but "all else equal"
is doing real work in that sentence, since the physical barrier's own
bound (`T_stale_max`) is itself unproven (§6), so neither candidate is
currently a complete answer on its own.

## 8. Backchannel contract

**Minimum control path required**, per condition (confirmed absent
today for every row, `TKT-019.13` §4):

| condition | must reach sender? |
|---|---|
| `txn_void` | Yes |
| integrity failure | Yes |
| length mismatch | Yes |
| lane loss (`stuck`) | Yes, at minimum as a contributing cause when `txn_void` fires — `stuck` alone without `txn_void` context is not separately actionable |
| watchdog timeout (**two distinct watchdogs** — the CDC's `ALIGN_TIMEOUT` and the demux's `REASSEMBLY_TIMEOUT`; confirmed as separate mechanisms with separate outputs, not one signal) | Yes, and the sender must be able to tell which of the two fired, since they bound different failure classes (`TKT-019.6` M6's own reasoning for keeping them distinctly named) |
| successful retirement | **Yes — not just failure.** Per §3's candidate analysis, several models (3.2, 3.5) require the sender to learn of *success* too, not only abort; today's architecture only has the sender infer success from its own `done`, which is sufinci ent **only** under a pure sender-authoritative model (3.1) — any receiver-influencing model needs this path either way |
| reset | Yes — both sides must agree a reset occurred before resuming, not just independently notice their own reset deasserted (§7) |

### Required properties — determined, not assumed

* **Reliable (guaranteed eventual delivery):** **Required.** If a
  retirement/abort notification under the NACK model (3.4) is lost,
  the sender never learns to skip the aborted value and will
  eventually **reuse the exact same `tx_epoch` value for a legitimate
  later transaction** — reproducing the aliasing defect through
  message loss instead of counter wraparound. A best-effort (lossy)
  channel does not satisfy this.
* **Ordered:** Required if more than one retirement event could be
  in flight to the sender concurrently; the CDC's own sequential,
  single-register `txn_void` generation likely avoids *reordering at
  the source*, but the channel carrying it to the sender must not
  reorder it either — a transport-layer requirement, not assumed free.
* **Self-tagged (generation/epoch-identified):** **Required, and this
  is the finding the task specifically asked this ticket to surface:**
  a bare pulse or level signal with no identity of its own is
  ambiguous the instant more than one generation could plausibly be
  "the one this message is about." See the stale-message analysis
  below — without tagging, the control plane reconstructs the exact
  aliasing problem it exists to solve, one layer up.
* **Acknowledged:** Required **unless** the channel is independently
  proven reliable and ordered by some other means — in the absence of
  such a channel (none is specified in this repo today), the safe
  default assumption is that an ack-based reliability layer is needed.
* **Protected against stale control messages:** Required — analyzed
  explicitly next.

### Stale `txn_void`/ACK arriving after a new transaction has started

Consider: receiver fires `txn_void` for generation N; the notification
is delayed (by its own, separately-unproven propagation path); the
sender, having heard nothing, proceeds and completes generation N+1 on
its own local pacing; **only then** does the delayed notification
arrive. If the notification carries **no identity of its own** (a bare
pulse, "something voided"), the sender has no way to tell whether it
concerns the *already-superseded* N or some *other* concern — it might
incorrectly skip/retire N+1 (which actually succeeded), corrupting a
transaction that was otherwise fine. **This is the control-plane
analogue of exactly the data-plane aliasing problem this entire
ticket chain exists to solve**, and the task's own framing is correct
to flag it explicitly: **a backchannel that is not itself generation-
tagged, and whose tag is not itself checked against the sender's
current state before acting, does not solve the identity problem — it
relocates it into the control plane, where the finite-width-tag
argument applies all over again** (a control-plane tag that itself
wraps inherits the identical `I`-vs-`N_reuse_max` question this ticket
chain has been chasing in the data plane). Designing a correct
backchannel is therefore not "add a wire" — it requires either (a) a
provably-bounded delivery latency strictly less than `T_txn_min`
(avoiding the ambiguity by construction, timing-wise), or (b) its own
generation-tagging-and-check discipline exactly mirroring the data
plane's, or (c) a full acknowledged, retried, ordered protocol — each
of which is a real, nontrivial design problem in its own right, not a
footnote to the data-plane fix.

## 9. FIFO / identity interaction

`TKT-019.12`/`.13`'s result, carried forward **exactly as scoped, not
promoted to a universal condition:**

```
D ≤ I    (for the single-burst, single-lane-backlog case only)
```

### Additional assumptions required beyond the single-burst case

* **Sustained traffic (not one-shot fill):** a word's relevant wait is
  not "time to drain the current backlog" but "time from when it,
  personally, was written until it, personally, reaches the head" —
  under continuous arrival-while-draining, this can exceed the simple
  `D-1`-cycle bound. **Not derived in `TKT-019.12`/`.13`; not derived
  here either — remains `OPEN`**, flagged again rather than silently
  inherited as solved.
* **Multiple outstanding transactions:** the current architecture has
  no concept of more than one generation "in flight" at a time at the
  CDC (one `expected_epoch`, one barrier) — but the *sender* could, in
  principle under some future pipelining change, begin preparing a
  next transaction while the prior one is still draining receiver-side.
  Not modeled by `D ≤ I`'s derivation, which assumed a single
  generation's backlog draining against a single advancing counter.
* **Multiple stale words per lane, across multiple past generations**
  (exactly `TKT-019.11`'s own multi-lane test construction): each
  still individually subject to the same per-position `k`-cycles-to-
  examine bound; the *aggregate* risk across a `D`-deep, multi-
  generation backlog is bounded by the same `D ≤ I` relationship, since
  `k ≤ D-1` regardless of how many distinct stale generations populate
  the backlog — **this specific aggregate case does not require a new
  condition beyond `D ≤ I`**, a narrower, positive finding this ticket
  is able to state with the same confidence as `TKT-019.13` §6's
  original derivation.
* **Distributed lanes:** each lane's discard path is independent
  (confirmed, `TKT-019.11`), so `D ≤ I` applies per lane; no
  cross-lane compounding was found or is expected — lanes do not share
  `wait_cnt`/drain state with each other.

### Can a retirement barrier make the FIFO/identity relationship irrelevant?

**Yes, directly — this is the single most useful structural conclusion
of this section.** `D ≤ I`'s entire purpose is to bound how long a
buried word can sit **without being correctly recognized as stale** by
the **passive, tag-equality-only** mechanism. A retirement barrier per
§6 (item 2/7 — observe `fifo_empty[c]` directly, not inferred from tag
comparison) does not need the counter to "outrun" anything: it
verifies **physical emptiness** before permitting reuse, which is true
or false independent of `EPOCH_W`. **If a retirement barrier is
adopted, `D ≤ I` becomes unnecessary** for the drain-race class of risk
specifically (it would still need to independently handle the
sustained-traffic case above, which is a `fifo_empty`-based barrier's
own open question, not resolved by this observation alone) — but it
removes the single derived mathematical condition this ticket chain
has spent two prior tickets establishing, which is worth stating
plainly rather than burying: **a sufficiently strong retirement
barrier makes identity-space sizing a secondary concern, not the
primary one** `TKT-019.12` originally framed it as.
