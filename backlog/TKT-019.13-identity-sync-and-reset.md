# Objective

`TKT-019.12` found that no finite `EPOCH_W` can currently be proven
sufficient, and identified two prerequisite gaps neither width nor any
of its own candidates close on their own: **(1)** `tx_epoch` (sender)
and `expected_epoch` (receiver) are unwired, independently-incrementing
counters, and **(2)** reset unconditionally restarts both at the fixed
value 0. This ticket's job is to determine **whether a finite,
defensible `N_reuse_max` can be established at all**, by answering the
architectural question TKT-019.12 left open: **who owns transaction
identity, how does retirement propagate, and what must reset mean?**

**This ticket does not assume an answer exists.** `FINITE N_reuse_max
NOT CURRENTLY PROVABLE` is an acceptable, and per §7 the actual, outcome
— the task is to show *exactly* why, not to manufacture a number that
satisfies the question. **No RTL is modified, staged, or committed by
this ticket.** No PBG grade is assigned, consistent with
`TKT-019.6`/`TKT-019.7`/`TKT-019.12`'s own precedent for architecture/
trade-study work.

## 3. Identity authority — who owns transaction identity?

**Ground truth, confirmed by inspection, before evaluating any
candidate:** `gcb_dwdm_payload_mux`'s complete port list is `clk,
rst_n, mode_b, payload_len, payload_data, start, busy, done, tx_color[],
tx_valid, lane_enable, tx_epoch`. There is no input port of any kind
carrying receiver state. `gcb_dwdm_payload_demux`'s complete port list
is `clk, rst_n, in_color[], aligned_valid, lane_enable, payload_valid,
mode_b, payload_len, payload_data, integrity_fail, reassembly_timeout,
length_mismatch` — note the demux does not even receive the CDC's own
`txn_void`/`stuck`, only `aligned_valid`; its three fault outputs are
demux-local and connect to nothing. **The current architecture is
therefore not cleanly describable as any of the five models below — it
is an unstated, de-facto "independent dual authority": the sender
assigns tag *values*, but the receiver maintains its *own*, separately-
evolving notion of which value is current, and nothing reconciles the
two.** Each model is evaluated against this baseline.

### 3.1 Sender-authoritative identity

* **Who creates identity:** the sender (`tx_epoch`, incremented on its
  own `done`).
* **How the other learns it:** the tag rides with every word
  (`in_epoch`); the receiver reads it off incoming data, not from a
  side channel.
* **How `txn_void` propagates:** it doesn't, by construction — under a
  *pure* sender-authoritative model the receiver has no standing to
  unilaterally retire a generation; it may only refuse to align
  (withhold `aligned_valid`). This is a genuine redesign from today's
  RTL, where `txn_void` is entirely receiver-local.
* **How both sides agree a transaction is retired:** only the sender
  knows — which means the receiver's own bounded-wait/watchdog
  mechanism (`TKT-019.3`'s entire reason to exist — an unbounded wait
  was the original defect) has nothing authoritative to retire *to*.
  This model, taken literally, **conflicts with the watchdog's own
  purpose** unless paired with an explicit sender heartbeat the
  receiver can use to detect sender silence (a new mechanism, not
  free).
* **How a new transaction begins:** sender's own pacing (`S_IDLE`→
  `S_EMIT`), unchanged from today.
* **If sender/receiver disagree:** the receiver has no mechanism to
  correct the sender and no authority to declare the sender wrong —
  it can only time out locally, which (per above) doesn't retire
  anything the sender recognizes.
* **Can stale data be accepted under the wrong generation?** Yes,
  identically to today — this model does not, by itself, change the
  comparison primitive at all; it only clarifies (does not fix) who
  "should" be right when they disagree.

### 3.2 Receiver-authoritative identity

* **Who creates identity:** the receiver (`expected_epoch`); the
  sender must be *told* what value to stamp.
* **How the other learns it:** requires a **new wire**, sender input
  port, currently **absent** (CONFIRMED BY INSPECTION, §3 preamble).
* **How `txn_void` propagates:** trivially — it's the same local event
  that already updates `expected_epoch`; the new wire need only expose
  the current value (or a retirement pulse) outward.
* **How both sides agree a transaction is retired:** by definition —
  the receiver's view is authoritative, so there is nothing to
  reconcile, **provided** the sender actually reads the new wire
  before stamping the *next* transaction (a timing requirement, not a
  free guarantee — see §4).
* **How a new transaction begins:** the sender must either poll the
  wire or be handed the value at `start`-time — either way, a new
  dependency on the receiver being ready/responsive before the sender
  can proceed, which did not exist before.
* **If sender/receiver disagree:** cannot happen by construction
  **for the tag value itself** — but *can* still happen for *timing*:
  if the sender latches the old value before the new one propagates,
  it reintroduces the exact race this model exists to prevent (a
  `T_propagation < T_txn_min` proof obligation, not automatically
  satisfied just because the wire exists).
* **Can stale data be accepted under the wrong generation?** Only via
  the timing race just described — structurally much narrower than
  today's "no wire at all" gap, but not zero without that timing proof.

### 3.3 Explicit synchronized/shared generation

* **Who creates identity:** neither side alone — both read/write a
  third, shared counter/register (e.g. a common CSR, a distributed
  epoch clock).
* **How the other learns it:** both sides observe the *same* shared
  state — in principle eliminating the "two independent counters"
  problem at its root.
* **How `txn_void` propagates:** the shared state is updated once,
  visible to both by the same read.
* **How both sides agree a transaction is retired:** by construction,
  if the shared state is the sole source of truth for both.
* **How a new transaction begins:** gated on the shared state, not
  either side's local pacing alone — a new coordination dependency.
* **If sender/receiver disagree:** should be structurally impossible
  for the *value itself* — **but the shared resource must itself cross
  from wherever it lives into both the sender's clock domain and the
  receiver's `rd_clk` domain (and, if per-lane clocks recover
  independently, into each of those too)**. This **does not eliminate
  the CDC problem — it relocates it** to a new shared resource that
  itself needs the identical class of cross-domain-consistency proof
  this whole epic has been chasing since `TKT-019.3`. Not a shortcut;
  a different instance of the same underlying hazard.
* **Can stale data be accepted under the wrong generation?** Only
  through a failure of the *new* shared-resource's own CDC correctness
  — an unevaluated, and potentially just-as-hard, new proof burden.

### 3.4 Receiver NACK/abort causing sender advancement

* **Who creates identity:** the sender, same as today (`tx_epoch`,
  increment-by-1) — this model changes **when** the sender is allowed
  to advance, not **who** generates the value.
* **How the other learns it:** the sender does not need to "learn" the
  receiver's value at all — it only needs to learn that a generation
  was retired, and bump its own counter in response, keeping the
  existing value-generation logic intact. Requires one new signal,
  receiver → sender (e.g. `txn_void`, or a dedicated `retire` pulse).
* **How `txn_void` propagates:** via that new signal, directly — the
  most minimal wiring change of any candidate here (one new port each
  side, reusing a signal the receiver already generates internally).
* **How both sides agree a transaction is retired:** the receiver
  decides *that* something retired; the sender decides *what the next
  value is* (still `+1`) — a genuine division of authority, not a
  single owner, which is worth naming explicitly since it's neither
  3.1 nor 3.2 in pure form.
* **How a new transaction begins:** sender's own `S_IDLE` pacing,
  **gated additionally** on having processed any pending retirement
  signal first — a new ordering requirement inside the mux's FSM.
* **If sender/receiver disagree:** can still happen **if the
  retirement signal itself is delayed past the sender's next `start`**
  — i.e. this model trades "no mechanism at all" for "a mechanism with
  its own latency bound that must be proven less than `T_txn_min`,"
  the **same** timing proof obligation as 3.2, now attached to an
  event rather than a value. Does **not** remove the obligation;
  narrows what must be proven.
* **Can stale data be accepted under the wrong generation?** Only
  through that same timing race — structurally the closest of the
  five to today's architecture (smallest wiring delta), and the one
  whose residual risk is the most precisely characterizable (a single
  new latency bound, not a value-propagation-plus-latency bound).

### 3.5 Explicit transaction-ID handshake

* **Who creates identity:** negotiated per-transaction — sender
  proposes, receiver confirms (or vice versa), before payload
  transmission begins.
* **How the other learns it:** by construction — the transaction
  cannot proceed until both sides have exchanged and acknowledged the
  ID.
* **How `txn_void` propagates:** naturally — abort is just "the
  negotiated ID is retired," observable to both sides since both
  participated in establishing it.
* **How both sides agree a transaction is retired:** the strongest
  guarantee of the five — agreement is a **precondition** of the
  transaction existing at all, not a property that must hold
  *afterward*.
* **How a new transaction begins:** only after a full round-trip
  negotiation — a **mandatory latency cost on every transaction**, not
  only on retirement, unlike every other candidate here.
* **If sender/receiver disagree:** cannot, by construction, reach the
  payload phase at all while disagreeing — disagreement blocks
  progress rather than silently aliasing.
* **Can stale data be accepted under the wrong generation?** Not via
  the identity-assignment path — residual risk would have to come from
  a *separate* defect in the negotiation protocol itself (e.g. its own
  CDC/timing hazard), not from the tag-equality problem this ticket is
  chasing.

### 3.6 Other materially different mechanisms

* **Timestamp/real-time identity:** trades a finite counter-wrap
  problem for a clock-synchronization problem across independently
  recovered per-lane domains — not simpler, a different hard problem.
* **Content-addressed / nonce identity:** trades a *structural*
  (provable-by-construction) safety argument for a *probabilistic*
  one (collision probability, not impossibility) — a different
  epistemic category entirely; mixing it into the same `PROVEN`
  vocabulary as the others without saying so would itself be an
  overreach this project's discipline exists to prevent.
* **Hybrid (coarse session/boot marker + fine per-transaction
  counter), composed with one of 3.1-3.5 for the per-transaction
  axis:** this is **not a sixth alternative to 3.1-3.5** — it is an
  orthogonal axis (addressed fully in §5) that must be composed
  *with* one of 3.1-3.5, not substituted for one. Naming it here only
  to flag that §3 and §5 are not independent choices to be picked one
  axis at a time without checking they compose correctly.

**No mechanism is selected here.** §8 carries the full trade-off
comparison forward; this section establishes what each one actually
requires before any cost/benefit judgment is made.

## 4. Backchannel semantics (receiver → sender)

**Confirmed by inspection (§3 preamble): no backchannel of any kind
currently exists.** Every one of the seven receiver-side conditions
below is therefore in the same state:

| receiver-side condition | currently reaches the sender? |
|---|---|
| `txn_void` (CDC bounded-wait timeout) | No |
| timeout (same signal, no distinct path) | No |
| lane loss (`stuck`, naming empty lane(s)) | No |
| integrity failure (`integrity_fail`, demux CRC32 mismatch) | No |
| length mismatch (`length_mismatch`, demux, `TKT-019.10` Finding A) | No |
| reassembly failure (`reassembly_timeout`, demux-local watchdog) | No |
| reset (either domain) | No |

> **`ARCHITECTURAL GAP — UNPROVEN`** is the requested label, and is
> applied here — but stated precisely: this is not a case of "a
> mechanism exists but has not been proven correct." It is **confirmed
> absent by direct port-list inspection** of both `gcb_dwdm_payload_mux`
> and `gcb_dwdm_payload_demux`. "Unproven" in the sense requested means
> "no proof obligation has even been defined yet, because there is
> nothing to prove a property of" — stronger than an ordinary open
> question, and should not be read as "might already work, just
> untested."

### Candidate backchannel mechanisms

| | Explicit NACK/ABORT | Transaction-complete/retired ACK | Sideband control channel | In-band control transaction | Mandatory sender quiescence |
|---|---|---|---|---|---|
| **Mechanism** | Receiver pulses a fault-specific signal the instant any of the 7 conditions fires | Receiver pulses a generic "this generation is closed" signal on *every* retirement (success or failure, not fault-specific) | A persistent, always-available receiver→sender bus, independent of the payload path, carrying richer state (current `expected_epoch`, fault code, etc.) | Retirement/fault info rides as an ordinary in-band transaction on the *existing* physical channel, interleaved with payload traffic | No new wire at all — the sender is *contractually* forbidden from issuing a new `start` within some fixed margin after any transaction, large enough to always exceed `TKT-019.12` §7's (unproven) `T_stale_max` |
| **Latency** | One signal-propagation delay (small, a few cycles, if same/adjacent clock domain — **unproven** if `wr_clk[c]`-domain crossing is involved, since this would be a **new** CDC crossing, same class of risk `TKT-019.10` Candidate 1 found the hard way) | Same class as NACK/ABORT | None added on the common path once the channel exists; the channel's own bring-up/training cost is a one-time, not per-transaction, cost (not quantified here — no spec for it exists) | Adds at least one extra transaction's worth of latency per fault event (the control transaction itself occupies lane time) | **Large and unconditional** — every transaction pays the quiescence margin whether or not anything went wrong; this is the worst of the five on latency specifically *because* it requires no new wire |
| **Bandwidth** | Calculable only once a signal width and a crossing-domain clocking decision are both fixed — **not calculable yet** (no width has been chosen, and the crossing-domain question above is itself open) | Same — not calculable yet | Not calculable — channel bandwidth, protocol overhead, and bring-up cost are all unspecified | Calculable in principle (one control-transaction's worth of lane-cycles, per occurrence) — but occurrence *rate* depends on fault rate, which this epic has no measured or modeled value for (the same BER/error-pattern deferral `TKT-019.6` already made for FEC/retry applies identically here) | Zero new bandwidth — this is its one clear advantage |
| **New CDC risk** | Yes — a new receiver-clock-domain signal reaching the sender's clock domain is a new crossing needing its own synchronizer and its own proof, not inherited from any already-verified path | Same | Yes, and worse — an entire new always-available channel is a larger new surface, not a single pulse | No *new* crossing if it reuses the existing physical channel's own already-proven synchronization, but does require the demux's fault logic to generate a *transmittable* message, which it does not currently do (it only drives output ports, not a re-injectable control frame) | **None** — its entire appeal is that it adds no new signal and therefore no new CDC obligation |
| **Verification risk** | Moderate — one new signal, one new crossing, testable in isolation, modeled directly on `TKT-019.11`'s own adversarial-test style | Moderate, same class | High — general-purpose channel correctness is a much larger test surface than one pulse | Moderate-high — must prove the control transaction can never itself be mistaken for payload, and vice versa (a **new** framing-ambiguity class this epic has not had to consider) | Low *mechanically* (no new RTL signal to get wrong) but **entirely dependent on an unproven number** (`T_stale_max`) to size the margin — the verification risk is displaced onto a number this ticket (and `TKT-019.12`) could not derive, not removed |

**Calculated only where the necessary assumptions are actually
available, per the task's own instruction:** none of the five rows
above can be given an actual bandwidth or latency *number* right now
— every one of them is gated on at least one currently-`UNPROVEN`
input (`T_stale_max`, a clocking decision, a fault-rate model, or a
channel spec that does not exist in this repo). Quiescence is the
partial exception: its *mechanism* cost is genuinely zero-wire, but
its *margin* is exactly as unproven as `T_stale_max` itself, which is
the number it would need to be set from.

## 5. Reset-generation semantics

### The required invariant

Across any reset, the architecture must guarantee:

```
∀ word w live (queued, in flight, or otherwise reachable) at the
  instant reset asserts, and ∀ transaction t issued after reset
  de-asserts: w must never be accepted as t's data, REGARDLESS of
  what numeric tag w carries and what numeric tag t's generation
  is assigned.
```

This is **deliberately not phrased in terms of tag values** — `TKT-019.12`
§9 already showed that phrasing it as "the post-reset tag sequence
must not repeat a pre-reset value `w` still carries" is insufficient by
itself, because **reset does not consume any of the identity space at
all**: both `tx_epoch` and `expected_epoch` restart at the fixed value
`0` unconditionally (confirmed directly in both modules' reset
branches). The dangerous case (`w.tag == 0`, reused by the very first
post-reset transaction) requires **zero** further transactions, not up
to `2^EPOCH_W - 1` of them.

### The requested sequence, analyzed explicitly

```
old generation N in flight → reset → new generation starts
  → old delayed data arrives
```

**What currently prevents acceptance: nothing beyond the same
`word.epoch == expected_epoch` comparison already shown insufficient.**
If `N == 0` (the common, worst case, since both counters always
restart there), the delayed word is indistinguishable from the very
first post-reset transaction's own data. If `N != 0`, the same
ordinary-wraparound analysis from `TKT-019.12` §6/§7 applies, now
timed from the reset instant rather than from power-on — no new
invariant fires either way; reset introduces a **second**, structurally
distinct aliasing opportunity (value 0, immediately) on top of the
ordinary wraparound one, not a mitigation of it.

### Does reset require a distinct identity namespace from ordinary sequencing? Yes, explicitly.

Ordinary wraparound is a **within-namespace** exhaustion problem — the
counter runs out of fresh values *while continuing to count*. Reset is
a **namespace-reset** problem — the counter is told to forget how far
it had counted and **start over from the same point every time**,
which is a different failure mode requiring a different fix. A
mechanism that only widens or re-paces the ordinary counter (any
`TKT-019.12` §10.1-10.3 candidate, unmodified) does not touch this at
all — confirmed again here, independently of `TKT-019.12`'s own
conclusion, because the reset branches inspected for this ticket show
literally no conditional logic of any kind gating what value is
restored on reset; it is an unconditional `<= '0` in both modules.

### Candidate reset mechanisms

| | Physical drain/quiescence | FIFO flush | Reset epoch/generation marker | Persisted generation | Boot/session nonce | Reset handshake |
|---|---|---|---|---|---|---|
| **Mechanism** | Hold reset (or a post-reset idle period) for at least `T_stale_max` before accepting new traffic | An explicit, active discard of all FIFO contents at reset time (`TKT-019.6`'s original M2, re-raised for the reset case specifically, not the `txn_void` case `TKT-019.7` already ruled on) | A separate, coarse counter incremented once per reset (not per transaction), concatenated with or prefixed to the ordinary per-transaction epoch, so "epoch 0 of generation 3" ≠ "epoch 0 of generation 1" | The generation marker above, but surviving power loss (non-volatile or externally-maintained) | A random or monotonic value drawn fresh at boot/session start, large enough that accidental repeat across sessions is vanishingly unlikely | An explicit sender↔receiver exchange, *at* reset time, establishing a freshly-agreed starting identity before any payload traffic resumes |
| **Correctness invariant delivered** | Prevents acceptance by **elapsed time alone** — does not depend on the tag space at all | Prevents acceptance by **removing the data**, same category of risk `TKT-019.7` already flagged for the `txn_void` case (the async FIFO's read-domain pointer is only ever a *synchronized, slightly stale* copy — the identical staleness gap applies here, not a new one) | Prevents acceptance **by construction** — the post-reset comparison can never numerically equal a pre-reset tag once the generation prefix differs, with no dependence on `T_stale_max` at all | Same as above, and additionally survives power cycling | Probabilistic, not structural — same epistemic caveat as §3.6's nonce candidate | Prevents acceptance by construction, same strength class as §3.5's per-transaction handshake, but paid once per reset instead of once per transaction |
| **Requires `T_stale_max`?** | **Yes — and it is the one candidate here that is entirely blocked on the same unproven number `TKT-019.12` could not derive** | No new dependency beyond `TKT-019.7`'s existing staleness-gap caveat | No | No | No | No |
| **New CDC/verification risk** | Low mechanically, but unverifiable without the missing number | Re-opens `TKT-019.7`'s rejected flush primitive, for a narrower (reset-only) case — smaller surface than the general `txn_void` case, but the identical sync-latency correctness question | Low — a wider counter with no new crossing, same verification shape as ordinary width | New persistence-path verification (§`TKT-019.12` §10.4's own caveat, unchanged) | Needs a trustworthy entropy/monotonic source at boot — a new dependency, unverified | New handshake protocol at reset time — smaller surface than a full per-transaction handshake (§3.5), paid rarely |
| **Latency cost** | Large, paid once per reset (not per-transaction) | Low, paid once per reset | None | None | None | One round-trip, paid once per reset |

**Not assumed: a wider modulo counter does not solve reset aliasing**,
independently re-confirmed by this section's own inspection of the
reset branches, consistent with `TKT-019.12` §9's conclusion. **The
reset-generation marker / persisted-generation / boot nonce family is
the only group of candidates here that removes the dependency on the
unproven `T_stale_max` number entirely** — worth flagging because it
changes what "the next ticket" should prioritize (see §9/Recommended
next action).

## 6. FIFO depth / identity-space relationship

### Re-deriving the condition, not assuming one

Define:

* `D` = per-lane FIFO depth (`MAX_SKEW_CYCLES`).
* `I` = identity-space size (`2^EPOCH_W`).
* The RTL fact, confirmed by inspection of `gcb_dwdm_deskew_cdc.sv`:
  `expected_epoch`, `wait_cnt`, and every `rd_en[c]` decision are all
  registered in the **same** `always_ff @(posedge rd_clk ...)` block —
  i.e. at most **one** epoch advance and at most **one** discard-pop
  per lane can occur per `rd_clk` cycle. Call this the **single-edge
  rate bound**: both the epoch-advance rate and any one lane's
  drain rate are bounded above by 1/cycle, on the same clock.

**The race `TKT-019.12` §6 flagged, re-derived precisely:** a word
sitting at queue position `k` (0 = head, so a maximally-full lane's
deepest word is at `k = D-1`) is not even examined for a discard
decision until the `k` words ahead of it have each been popped — in
the fastest possible drain (continuous mismatch, `channel_enable`
held), that takes exactly `k` cycles. During those `k` cycles, by the
single-edge rate bound, `expected_epoch` can advance by **at most
`k`** (not more — it is on the identical clock, gated by the identical
edge). The word's own tag aliases `expected_epoch` again only if the
counter completes one or more full laps during that wait — i.e. only
if the total advance during the wait is a nonzero multiple of `I`.
Since the maximum achievable advance in `k` cycles is `k` itself, the
race is reachable **only if `k ≥ I`**, and since `k ≤ D-1`:

```
This specific race is reachable  ⟺  (D - 1) ≥ I  ⟺  D > I
Safety against this specific race  ⟺  D ≤ I
```

**Correction to `TKT-019.12`'s own wording:** that ticket flagged
`DEPTH == 2^EPOCH_W` at the bring-up geometry (`D = 16, I = 16`) as "a
red flag, not a margin" and "razor-thin/insufficient." Worked through
precisely here: `D = I` satisfies `D ≤ I`, the derived safety
condition — the bring-up geometry is, by this specific mechanism,
**marginally safe, with literally zero cycles of slack** (one
additional queued word, or any off-by-one in exactly which cycle a
comparison is evaluated relative to a pop that this desk analysis has
not independently simulated, would flip it). "Insufficient margin" was
the right instinct; "razor-thin, not insufficient" is the more
precise statement this ticket is able to derive. Neither ticket claims
this boundary case has been independently falsification-tested — it is
`MEASURED / DERIVED` from the RTL's own structural rate bound, not
`PROVEN — DIGITAL SIMULATION, TESTED CONDITIONS`.

### Explicit dependencies this condition carries

`D ≤ I` (equivalently `2^EPOCH_W ≥ MAX_SKEW_CYCLES`) is the condition
for **this one mechanism** (a word buried behind an entire lane's own
maximal, single-lane, single-burst backlog). It explicitly does
**not** cover, and this ticket does not claim it covers:

* **Transaction issue rate / retirement rate exceeding the
  single-edge bound's own assumption of "one advance per cycle,
  sustained."** The bound already assumes the *worst case* (fastest
  conceivable advance rate); it cannot be violated by a *faster* rate
  since 1/cycle is the RTL's own hard ceiling — but a SUSTAINED high
  rate (not a one-shot burst) changes which word is "deepest" over
  time in ways this one-shot derivation does not model (§6 note
  below).
* **Timeout (`ALIGN_TIMEOUT`) interaction.** A `txn_void`-driven
  advance requires `ALIGN_TIMEOUT` cycles of waiting first — this
  *slows* the advance path, working in the safe direction, but
  `ALIGN_TIMEOUT` is itself `TKT-019.3`'s own unvalidated placeholder
  (`TKT-019.12` §7.C) and cannot be relied on as a proof input without
  re-flagging that reliance.
* **Queue occupancy over time, under continuous (not one-shot)
  traffic.** A word does not merely need to survive "the time to drain
  the CURRENT backlog" — it needs to survive from the moment **it
  personally** was written until it personally reaches the head,
  which, under sustained traffic where new writes keep arriving while
  old ones drain from the head, can exceed the simple `D-1`-cycle
  bound used above. **This ticket has not derived a tight bound for
  the sustained-traffic case** — only the single-burst, one-shot-fill
  case above. Labeled `OPEN`, not resolved here, and flagged as the
  natural target of a future adversarial-simulation ticket (in
  `TKT-019.11`'s own style) rather than further desk analysis.

## 7. Is `N_reuse_max` actually finite?

| quantity | status | basis |
|---|---|---|
| `T_stale_max` | **UNPROVEN / structurally circular** | `TKT-019.12` §7.H's finding stands, independently re-confirmed here: discard depends on *further* epoch advances, which is the quantity being bounded — a genuine circularity, not merely a missing measurement |
| `T_txn_min` | **UNPROVEN**, two un-reconciled paths | The mux's own `S_IDLE`/`S_EMIT` pacing bounds the *completion* path only (`TKT-019.12` §7.J); the `txn_void` path runs on the receiver's independent clock, gated by the equally-unproven `ALIGN_TIMEOUT`. No single number covers both. |
