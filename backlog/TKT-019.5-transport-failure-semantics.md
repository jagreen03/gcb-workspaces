# Objective

[[TKT-019.4]] found the digital transport contract survives its happy paths
but has no integrity detection and no transaction identity. This story does
**not** fix either finding. It determines — from observed RTL behaviour
only, never from what would be convenient to assume — the **minimum
transport contract** required to prevent two specific classes of harm:

1. **Epoch contamination** — a late-arriving word from a failed or
   abandoned transaction being silently folded into a *different*,
   subsequent transaction's reconstruction ("Ghost Payload").
2. **Undetected corruption** — a bit flip in the payload, header, or
   control fields producing a *plausible-looking* wrong result with no
   fault indication.

**Orange-Team mandate for this story, stated explicitly: do not select or
implement a fix.** Section D enumerates candidate mitigations and their
tradeoffs; it does not rank or choose one. No RTL is modified. Every
requirement in Section C must trace to an observed failure in Section A or
B — nothing is derived from what a mitigation would need to exist to
justify itself.

## Required work

Write and execute, in `gcb-wdm-transceiver`, a new test against the

1. Start transaction **N**. Withhold one lane's data long enough to force

3. Determine **definitively**: does any transaction-N data (queued,
   unpopped, sitting in a lane FIFO when N+1 begins) end up inside a
   `payload_valid` pulse reported as transaction N+1's result?

to be.

### Section B — Framing/control integrity, exact state-machine reaction

For each of the four corruption categories below, record the DUT's exact
observable reaction — accepted or not, `payload_valid` fired or not,
recovered length correct or not, bytes bit-exact or not, any fault
indication (`txn_void`/`stuck`) or none:

* early `is_tile_final` corruption (a non-final word marked final)
* suppressed `is_tile_final` (the true final word's flag cleared)
* corrupted length/header field
* payload-body bit corruption

## Section A — Late-data / epoch-contamination findings

**The literal question — does any transaction-N data end up inside a
transaction-N+1 `payload_valid` pulse — is answered: yes, definitively,
confirmed empirically.**

Test sequence executed exactly as scoped: transaction **N** (Mode B,
1024 B payload `A`) had lane 30 permanently withheld, forcing `txn_void`
(`stuck = 0x40000000`, naming lane 30 alone — consistent with [[TKT-019.4]]
V4). Transaction **N+1** (Mode B, a *different* 1024 B payload `B`) was then
started on the identical lane set, with `channel_enable` never cleared or
re-asserted between the two — the realistic case, since nothing in the RTL
forces a boundary here and this test did not manufacture one either.

**Result:** `payload_valid` fired once, reporting `mode_b_out=True`,
`payload_len_out=1024` — a fully successful-looking reconstruction. Byte-
level comparison against both source payloads found **1008 of 1024 bytes
match A, 16 bytes match B (and not A), 0 bytes match neither.** The 16
ghost bytes form exactly one contiguous window, byte range **477-492** —
precisely one `CHUNK_BYTES=16` lane-word's worth, which is exactly what lane
30 alone can contribute per barrier pop.

**Mechanism, traced and confirmed, not just observed:** lane 30's FIFO was
still empty when N+1 started (it never got any of N's data — that's *why*
N voided). The other 59 lanes' FIFOs still held N's own two unpopped words
each (payload `A`'s data, queued since N's own window, since the barrier
never fired even once during N — `aligned_valid` requires every enabled
lane non-empty, and lane 30 never was). The moment lane 30 received its
*first* word of transaction **N+1**, all 60 lanes were simultaneously
non-empty for the first time since N began — the barrier fired, popping
each lane's FIFO **head**: for 59 lanes, that head is still N's own word
(`A`); for lane 30, it's the fresh word from N+1 (`B`). The header (mode,
length) is decoded from lane 0's contribution, which is one of the 59
"still holding A" lanes — hence the reported header is entirely A's own,
correct-looking values. The transaction only finalizes once a pop includes
lane 59's *second* word carrying `is_tile_final`, which is also still A's
own data (A's second-cycle word on lane 59) — so the reconstruction is
overwhelmingly A, except for lane 30's one contributing chunk, which is B's.
(Lane 30's *second* word, from N+1's second emission cycle, would also have
been B's — but it lands at global word index 90, which is beyond the real
65-word payload+header range for a 1024 B transaction and is pure zero
padding for both A and B alike, so it produces no *visible* second ghost
window; this is explained, not merely observed as a lone coincidence.)

**What this means, stated plainly:** a control-plane consumer sees one
`payload_valid` pulse, a correct-looking header claiming full success, and
no fault indication of any kind (`txn_void`/`stuck` fired earlier, for
transaction N — nothing fires again for this pulse). It has no way to know
that ~1.6% of what it just received belongs to an entirely different,
later transaction. **The "Ghost Payload" hypothesis holds.**

**Also confirmed as a direct consequence, not separately tested:** the 59
lanes still have B's own two words each queued behind A's now-consumed
words after this pop sequence completes — meaning a hypothetical
transaction N+2 sharing the same lane set would face the identical
contamination risk again, with B's leftover data instead of A's. This
compounds rather than self-clears.

## Section B — Framing/control integrity findings

Re-executed via the same already-built [[TKT-019.4]] test suite (the four
corruption categories below are the same RTL/test code; nothing new was
written for this section — the ticket asked what the exact reaction is,
and that reaction was already captured precisely enough to tabulate here).

| corruption | accepted (no fault signal)? | `payload_valid` fires? | length correct? | bytes bit-exact? | fault indication? |
|---|---|---|---|---|---|
| **payload-body bit** | yes | yes | yes (1024) | **no — 1 byte silently wrong** | none |
| **header mode bit** | yes | yes | yes (1024) | yes (mode_b_out wrong instead) | none |
| **header length bits** | yes | yes | **no — reports 1025, not 1024** | n/a (length itself is the corruption) | none |
| **early `is_tile_final`** (false-positive, non-final word) | yes | yes | yes (reports 1024 — **the header is untouched and correct**) | **no — diverges from byte 957 onward** | none |
| **suppressed `is_tile_final`** (true final word's flag cleared) | — | **never fires for this transaction** | n/a | n/a | `txn_void` fires **late**, `stuck` names **all 60 lanes** (not the corrupted one) |

**Every category is either silently accepted as a wrong result, or hangs
with a fault signal that misattributes the cause.** There is no category in
this table where the transport both (a) detects that something is wrong and
(b) correctly identifies what. The early-`is_tile_final` row is the most
consequential: the header is *correct* (1024, from the untouched word 0),
so a consumer checking "does the reported length match what I expected"
would see nothing wrong either — only a byte-level check against a known-
good copy (which a real receiver does not have) would catch it.

## Section C — Requirements extracted from observed failures

Every requirement below traces to a specific Section A or B (or [[TKT-019.4]])
finding — none is derived from what a candidate mitigation would need to
exist to justify itself.

**Transaction identity** (Section A: the Ghost Payload result)

* **REQ-TX-ID-001** — The transport SHALL provide a mechanism for the
  receiver to distinguish which transaction a given lane's queued data
  belongs to. *Currently: none exists — a lane's FIFO has no concept of
  "which transaction," only FIFO order.*
* **REQ-TX-ID-002** — On a declared transaction failure, the transport
  SHALL provide a mechanism to invalidate or flush any lane data still
  associated with that failed transaction before the same lanes are reused
  by a subsequent transaction. *Currently: `txn_void` performs no flush of
  any kind — confirmed directly in Section A's mechanism trace.*

**Integrity detection** ([[TKT-019.4]] V5 / Section B rows 1-3)

* **REQ-TX-INT-001** — The transport SHALL provide a mechanism to detect
  corruption of the payload body. *Currently: none — Section B row 1, a
  single bit flip is silently reconstructed as wrong data.*
* **REQ-TX-INT-002** — The transport SHALL provide a mechanism to detect
  corruption of the in-band header fields (mode, length), independent of
  payload-body integrity checking. *Currently: none — Section B rows 2-3,
  a corrupted header field is used as-is with no cross-check.*

**Framing protection** (Section B rows 4-5, the structural-field findings —
kept explicitly separate from INT-001/002 because `is_tile_final` is a
per-word control signal, not payload or header content, and failed in a
qualitatively different way: a shape change, not a content change)

* **REQ-TX-FRM-001** — The transaction-termination signal SHALL be
  protected against single-bit corruption independently of payload/header
  integrity, OR the receiver SHALL cross-check the number of words actually
  accumulated against the already-decoded declared length before treating
  a termination as valid. *Currently: neither exists — Section B row 4,
  a false-early termination is accepted with a correct-looking header
  despite representing only 60 of the required 65 real words.*
* **REQ-TX-FRM-002** — The transport SHALL define and bound the receiver's
  behaviour when a declared-final word is never received, and that bound
  SHALL produce a fault indication attributable to the actual cause.
  *Currently: the demux hangs indefinitely (no bound of its own), and the
  CDC's unrelated bounded-wait timeout eventually fires instead, naming
  every lane stuck — Section B row 5, a misattributed signal, not an
  absent one, which may be worse for a control-plane consumer trying to
  diagnose the fault.*

**Recovery semantics** (Section A's compounding-contamination note, and the
[[TKT-019.4]] analytical finding about `word_base` never resetting outside
the finalize path)

* **REQ-TX-REC-001** — A transaction that has been declared void SHALL NOT
  be able to later produce a `payload_valid` completion using data that
  arrives after the void declaration. *Currently: it can — [[TKT-019.4]]'s
  V3 finding that every voided case in its skew scan still completed late,
  and this story's Section A finding that the late data can belong to a
  *different* transaction entirely.*
* **REQ-TX-REC-002** — A reassembly stage that fails to observe a
  transaction's termination signal SHALL have a bounded path back to a
  clean state before the next transaction begins. *Currently: `word_base`
  in `gcb_dwdm_payload_demux` only resets inside the `finalize_pending`
  branch — a transaction that never finalizes leaves it wherever it
  stopped, and Section A's own mechanism (once channel_enable and lane
  reuse are already established as unprotected) demonstrates the general
  class of risk this creates for whatever transaction comes next.*

## Section D — Candidate mitigations (no selection made)

Six candidates, mapped against what they prevent (stops the failure from
occurring) vs. detect (flags it after the fact) vs. bound (limits its
consequence without addressing the cause), with a qualitative relative
cost. **None is selected, ranked, or recommended here — that decision is
explicitly out of scope for this story.**

| # | mitigation | prevents | detects | bounds | addresses | relative cost |
|---|---|---|---|---|---|---|
| 1 | **CRC/checksum** over the framed payload | — | INT-001, INT-002 (after the fact) | — | payload-body and header corruption | moderate — a shift-register/tree in the mux, a comparator in the demux, small wire-format overhead (tens of bits per transaction) |
| 2 | **Duplicated/redundant framing** (header + termination flag replicated across ≥2 independent lanes, compared or majority-voted at the receiver) | FRM-001 (a single-bit flip on one copy is outvoted) | — | — | structural-field corruption specifically | low for just the 3-byte header + flag; does not scale to protecting the full payload body without becoming expensive |
| 3 | **Sequence IDs / transaction epoch counters** (an in-band ID in the header, checked against an expected running count at the receiver) | ID-001, ID-002 (a stale-epoch word is recognisable and can be discarded before use) | — | — | transaction identity | low wire cost (a few header bits), moderate control cost (receiver must track and validate expected-epoch state — a new stateful mechanism) |
| 4 | **Watchdog-driven flush on `txn_void`** (an explicit drain/invalidate of every lane's FIFO when a transaction is declared void, before the next one may begin) | ID-002, REC-001 (stale data physically cannot remain queued) | — | — | epoch contamination at its root | moderate — needs a flush/discard path added to `gcb_dwdm_async_skew_fifo` (none exists today; only a full reset, which is heavier and more disruptive than a per-transaction flush) |
| 5 | **Length-received cross-check** at the demux (compare accumulated word count against the already-decoded declared length before accepting a termination as valid) | — | FRM-001 (a false-early termination no longer matches the length it claims) | — | structural early-termination specifically | low — one comparator, using data the demux already has |
| 6 | **Bounded receiver-side finalize timeout** (a demux-local watchdog, distinct from the CDC's own `ALIGN_TIMEOUT`, that forces a clean reset if no termination is seen within N cycles of a transaction's first word) | — | — | FRM-002, REC-002 (bounds the hang and the resulting wedge, with a correctly-attributed fault) | suppressed-termination hangs and the resulting demux state corruption | low — one more counter+comparator, mirroring a pattern the CDC already uses for its own barrier |

No combination is proposed either — a future story may find that closing
all eight requirements needs more than one of these, or that some are
redundant once combined. That analysis is not performed here.
