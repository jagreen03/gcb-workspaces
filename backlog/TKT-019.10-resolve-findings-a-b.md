# Objective

Actually close [[TKT-019.8]]'s Finding A (the completion path does not
implement the full M3/M4 invariant) and Finding B (`channel_enable`
hold-between-transactions can desynchronize `expected_epoch` from
`tx_epoch`). This is the ticket [[TKT-019.9]] explicitly said assumes both
findings are "eventually resolved" — this is that resolution attempt. Like
[[TKT-019.8]] itself, the Ghost Payload regression and the idle-gap
adversarial condition are **falsification attempts, not tests whose
expected answer is "pass."** A fix that merely makes the existing limited
regression pass again, without being re-run under the specific condition
each finding was found in, proves nothing. `gcb-wiki/14`'s epistemic labels
apply here too: nothing in this ticket may be marked PROVEN except against
the specific adversarial condition that produced it.

This is a **design-and-plan ticket, matching the [[TKT-019.6]]/[[TKT-019.7]]
convention that preceded [[TKT-019.8]]'s own implementation**: it proposes
concrete RTL changes and the required proof for each, but does not land RTL.
`status: open | pending`, no PBG grade — same reasoning as every other
architecture-only ticket in this epic.

## Finding A — proposed fix: an explicit, deterministic length-count gate

**Root cause (recap, not re-derived — see [[TKT-019.8]] and `gcb-wiki/14`
§6):** `gcb_dwdm_payload_demux`'s `finalize_pending` is driven by
`is_tile_final` alone. CRC catches a wrong length only indirectly
(byte-range mismatch), never by deterministic count.

**Proposed mechanism:**

1. Decode `payload_len` from the header **as soon as word 0 is available**
   (the first pop of a transaction, `word_base == 0`), not lazily at
   finalize as today — register it (`decoded_len_i`) for the rest of the
   transaction.
2. From `decoded_len_i`, compute `expected_final_word_base` the same way
   the mux computes its own `words_padded` (`HDR_BYTES + decoded_len_i +
   CRC_BYTES`, rounded up to `CHUNK_BYTES`, then to a whole multiple of the
   active lane count) — this is arithmetic already proven correct on the
   mux side; the demux needs the identical formula, not a new one.
3. On every pop where `is_tile_final` is asserted on any enabled lane,
   compare the **post-pop** `word_base` against `expected_final_word_base`.
   Match → proceed to the existing CRC check (M4's second leg). Mismatch →
   a **new, distinctly-named fault** (`length_mismatch` or
   `framing_violation` — naming TBD at implementation, but it must be
   distinct from both `integrity_fail` and `reassembly_timeout`, per this
   epic's standing rule that a fault signal must never misattribute its
   cause).
4. `payload_valid` must require **all three** to agree:
   `is_tile_final` (already true by construction, since that's what
   triggers the check) **and** the length-count match **and** the CRC
   match. Today only the latter two are checked (Finding A). This makes
   M4 an actual three-way agreement, not two-out-of-three renamed as three.

**What this does NOT change:** the CRC computation, the epoch mechanism,
or the watchdog — this is additive, a new independent gate in the
completion path, not a rework of the existing checks.

**Open question for the Architect, not resolved here:** should a length
mismatch also fire `integrity_fail` (treat it as a subclass of the existing
signal, simpler consumer logic) or a genuinely new signal (cleaner fault
attribution, more consumer-visible states)? [[TKT-019.6]]'s M3/M4 language
implies a distinct signal is closer to the spirit of "no single bit is ever
the sole arbiter" being *legible*, not just enforced — but this ticket does
not ratify that choice; it is flagged for sign-off before implementation.

## Finding B — proposed fix: two candidates, not yet chosen

**Root cause (recap):** `gcb_dwdm_payload_mux.lane_enable_q` never
deasserts between transactions; an idle gap longer than `ALIGN_TIMEOUT`
fires a spurious `txn_void`, which (since `TKT-019.8`) also advances
`expected_epoch`, desynchronizing it from `tx_epoch`.

**A deeper ambiguity found while drafting this fix, not previously
surfaced:** `gcb_dwdm_deskew_cdc`'s own header describes `channel_enable`
as **"quasi-static control-plane state (CSR-sourced, as in
`gcb_dwdm_deskew`)"** — implying an intended usage model where a control
plane sets it once and holds it across *many* transactions (a lane-routing
policy), not a per-transaction pulse. `gcb_dwdm_payload_mux`'s
`lane_enable_q`, by contrast, is dynamically mux-driven, one mask per
transaction. Both wire into the same `channel_enable` input. **The CDC was
built generically enough to serve either semantic, and the two ingress
paths (the older `gcb_dwdm_tx_packager`'s CSR-driven model vs. the mux's
per-transaction model) may not actually agree on what `channel_enable`
means.** This ticket does not resolve that ambiguity for the whole
transport — only for the mux/CDC pairing Findings A/B were found in.

**Candidate 1 (recommended for this ticket's scope) — deassert at the
source.** `gcb_dwdm_payload_mux`: `lane_enable_q <= '0` on the `done`→
`S_IDLE` transition, not only overwritten at the next `start`. Directly
fixes the traced mechanism, smallest footprint, no CDC change. Risk: if any
future consumer *relies on* `lane_enable` holding between transactions
(matching the CSR-quasi-static model above), this would break it — no such
consumer exists today (checked: only `gcb_dwdm_deskew_cdc` in the
integration path consumes it, and only through the bug this fixes).

**Candidate 2 — decouple "idle" from "stalled" at the CDC.** Add a
per-epoch `epoch_touched` bit in `gcb_dwdm_deskew_cdc`, set on the first
non-empty lane seen since the last `expected_epoch` advance; `txn_void`'s
epoch-advance (and the `txn_void` pulse itself) fires only if
`epoch_touched` was set when `ALIGN_TIMEOUT` elapsed — a channel that has
seen *nothing at all* for the whole window resets the wait counter
silently instead. More invasive (new CDC state), but fixes the failure
mode even if Candidate 1 turns out to be wrong about "no consumer relies on
the hold," and is robust to a *different* future ingress module
reintroducing the same hold pattern.

**Not proposed:** a third interface-level fix (a dedicated
"transaction-start" pulse decoupling channel_enable's *lane* meaning from a
*this-epoch-is-real* meaning) was considered and set aside as
out-of-proportion to what Findings A/B require — noted here so a future
ticket doesn't have to rediscover it, not because it was evaluated in
depth.

**This ticket recommends Candidate 1**, on the grounds that it fixes the
exact traced mechanism with the smallest, most auditable change, and
`gcb_dwdm_payload_mux` is a single-writer module (only one thing drives
`lane_enable_q`) — but flags Candidate 2 as the more defensively-robust
choice if the Architect weighs the channel_enable semantic ambiguity above
as a live risk, not a closed question.

## Required proof

Both fixes' pass criteria are the exact adversarial condition that found
each finding — not the previously-passing limited-condition regression:

1. **Finding A**: a targeted test that forces `is_tile_final` early (as
   [[TKT-019.5]]'s `structural_early_final` category does) but arranges the
   truncated+padding byte content to *coincidentally* satisfy the CRC
   recompute (constructible directly, since the test controls both the
   payload content and can compute what CRC the truncated range would
   produce) — under the CURRENT (Finding A) RTL this must be shown to slip
   through as an undetected success; under the FIXED RTL it must be caught
   by the new length-count gate specifically, with the fault signal
   distinguishable from a CRC-caused rejection. Passing only the existing
   (CRC-catches-it-anyway) corruption categories again is not sufficient
   proof — those never exercised M3's absence in the first place.
2. **Finding B**: the exact Ghost Payload sequence, re-run with a
   genuine idle gap (`> ALIGN_TIMEOUT` cycles, `channel_enable` held at the
   prior transaction's mask, no new data offered) inserted between
   transaction N's resolution and transaction N+1's start — the specific
   condition [[TKT-019.9]] and `gcb-wiki/14` both listed as UNPROVEN.
   Success requires: no spurious `txn_void`/epoch-advance during genuine
   idle (Candidate 2) or `channel_enable` correctly deasserted so `waiting`
   is never true while idle (Candidate 1); transaction N+1, arriving after
   the gap, must align and complete byte-exact.
3. Both re-run at `NUM_COLORS=60` (the Mode B ceiling), not only the
   cocotb bring-up geometry — [[TKT-019.8]]'s own Execution Log never
   confirmed the Ghost Payload sequence at 60 lanes end-to-end either.
4. Epoch rollover: force enough idle-driven or genuine `txn_void` events to
   wrap `EPOCH_W`'s mod-16 space at least once, confirm no false match/miss
   across the wrap, for both candidates if both are prototyped.
5. Regression floor, unchanged: `sim/lint.sh` 38/38; the full
   `test_wdm_link_integration.py`, `test_wdm_deskew_cdc.py`, and
   `test_wdm_payload_mux.py` suites must remain green — a fix for A/B that
   breaks an already-passing test is not a net improvement.

## Execution Log

### Finding A — RESOLVED (digital simulation, tested conditions), regression-confirmed

Implemented exactly as proposed: `gcb_dwdm_payload_demux` now decodes
`{mode_b, payload_len}` at finalize time (unchanged timing - still lazily,
from the landed header bytes), independently recomputes
`expected_words_padded` via the identical formula `gcb_dwdm_payload_mux`
uses for its own `words_padded`, and compares it against the actual
accumulated `word_base`. A mismatch fires a new, distinctly-named
`length_mismatch` output - never folded into `integrity_fail` - checked in
priority order BEFORE CRC (`if (!length_ok) length_mismatch; else if
(crc mismatch) integrity_fail; else payload_valid;`), so no single check is
ever the sole arbiter. The open question flagged in the draft (fold a
length mismatch into `integrity_fail` or give it its own signal) was
resolved in favour of a distinct signal, matching [[TKT-019.6]] M4's
"legible, not just enforced" spirit.

**Regression**: `test_wdm_link_integration.py`'s `test_bit_corruption_header_mode_bit`
and `test_bit_corruption_structural_early_final` now correctly report
`length_mismatch` (not `integrity_fail`) - both categories happen to change
the lane count or truncate the accumulation relative to the declared
length, so the new deterministic gate catches them before CRC is even
consulted. The other three corruption categories (`payload_body`,
`header_length_bits`, `structural_suppressed_final`) are unaffected -
traced and explained in each test's updated docstring, not merely patched
to pass. Full suite: `TESTS=10 PASS=10` (the pre-existing 10; see Finding B
below for the 11th, new test). `sim/lint.sh` 38/38.

### Finding B, Candidate 1 — IMPLEMENTED, then FOUND TO HAVE A NEW, MORE SEVERE REGRESSION. NOT RESOLVED.

Implemented as specified in the draft: `lane_enable_q` deasserts one cycle
after `done` (in the same `if (done)` block that already advances
`tx_epoch`, for the identical same-edge-race reason - an earlier revision
that cleared it on the SAME edge as `done` was caught and fixed before this
was even regression-tested, by re-tracing the final-word timing by hand:
clearing on the same edge as `done` means `channel_enable` already reads 0
in the exact cycle window the final word's own `tx_color`/`tx_valid` are
presented, so the CDC's `wr_en = in_valid & channel_enable` would drop the
final word itself, independent of any testbench delay).

**A NEW test was written to prove the actual fix** (per this ticket's own
Required Proof #2): `test_idle_gap_lane_enable_deasserts`, using a genuine
real-time, zero-skew passthrough of the ENTIRE mux-to-CDC connection
(`_mirror_mux_to_cdc` - channel_enable, color, valid, and epoch, every
cycle, unconditionally) rather than the Channel class's capture-then-relay
idiom every other test in this file uses - deliberately, because that
idiom sets `channel_enable` to a static, Python-held value once per
transaction, completely decoupled from the mux's own `lane_enable` output,
which is exactly why Finding B was never caught by any existing test in the
first place.

**Building and debugging that test surfaced a new, more severe problem
with Candidate 1 itself - not a testbench bug.** `gcb_dwdm_async_skew_fifo`'s
write-pointer-to-read-domain crossing is a 2-flop gray-code synchronizer:
a write at write-clock cycle T is not visible on the read side (`empty`
clearing) until approximately T+2 read-clock cycles, even under a
perfectly phase-aligned shared clock (no skew at all). `gcb_dwdm_deskew`'s
plain synchronous FIFO (`gcb_dwdm_skew_fifo`) has a smaller but still
nonzero version of the same problem: `count`/`empty` are registered, so a
write is not visible until the cycle AFTER it happens. Candidate 1 holds
`channel_enable` asserted for only ONE cycle after `done` - less than or
equal to both of these inherent latencies. The result, confirmed by
direct observation in both the new CDC-integration test (`NUM_COLORS=60`,
async FIFOs) and, independently, a full re-run of the ALREADY-LOCKED
[[TKT-019.2]] standalone regression (`test_wdm_payload_mux.py`, the plain
synchronous `gcb_dwdm_deskew` pairing, wired directly with no test
abstraction at all): **`channel_enable` can drop to 0 before the barrier
ever sees the final word as available.** `aligned_valid` is gated
combinationally on `channel_enable` being asserted AT THE MOMENT of
alignment (`(|channel_enable) & ...`), not merely having been asserted at
some point in the past - once it drops, the barrier simply never pops the
already-correctly-written data sitting in the FIFOs. Worse: `waiting` (=
`|channel_enable & ~aligned_valid`) ALSO goes false the instant
`channel_enable` drops, so the bounded-wait `txn_void`/`ALIGN_TIMEOUT`
mechanism never engages either - there is no recovery path at all for this
stall, not even the existing watchdog (a demux-level mechanism, orthogonal
to this CDC/deskew-level one). `expected_epoch` never advances (neither a
real `transaction_done` nor a real `txn_void` ever fires), permanently
misaligning every subsequent transaction too.

**This is a regression Candidate 1 introduces into ordinary, successful
completion - not merely a gap in closing the idle-gap scenario it was
written for.** Confirmed by full regression:

found - not reverted, not silently patched with a second guess at the

### Finding B, Candidate 2 — IMPLEMENTED in `gcb_dwdm_deskew_cdc.sv`, RESOLVED (digital simulation, tested conditions), regression-confirmed

**Exact `CDC_IDLE`/`CDC_ACTIVE` semantics** (a new two-state
watchdog-arming FSM, entirely internal - no port changes):

- **`CDC_IDLE`** (reset state): the bounded-wait counter (`wait_cnt`) is
  held at 0 and cannot fire `txn_void`, REGARDLESS of `channel_enable`'s
  value or how long it has been asserted. The only way out is a REAL,
  epoch-matched word: `any_matched_activity = |(lane_ready & channel_enable)`
  - `lane_ready` already requires both `~fifo_empty` and `epoch_match`, so a
    stale- or future-epoch head at any lane's FIFO can NEVER satisfy this,
    by construction - it is popped and discarded by the existing (unchanged)
    `epoch_discard` path instead, and can neither move the FSM out of
    `CDC_IDLE` nor touch `wait_cnt`. A full alignment (`aligned_valid`) can
    also fire directly from `CDC_IDLE` (e.g. every enabled lane's first word
    arrives simultaneously) - handled the same as from `CDC_ACTIVE`.
- **`CDC_ACTIVE`**: entered the cycle a real epoch-matched word is
  observed (`wait_cnt` arms to 1 that same cycle) or the cycle a non-final
  `aligned_valid` pop completes (more words expected for this same epoch).
  From here, the ORIGINAL TKT-019.3 bounded-wait semantics apply completely
  unchanged: `wait_cnt` increments every cycle `aligned_valid` is false,
  and `txn_void` fires (naming `stuck` lanes, advancing `expected_epoch`,
  returning to `CDC_IDLE`) if it reaches `ALIGN_TIMEOUT`.
- Both states return to `CDC_IDLE` on a `transaction_done` aligned pop
  (this epoch is genuinely over) or on `txn_void` (abandoned) - identical
  to the pre-existing `expected_epoch`-advance triggers, just now also
  resetting the watchdog-arming gate for the next epoch's first real word.

**`channel_enable` is never required to change.** It keeps its
architecturally-intended, quasi-static, CSR-like character (per this
module's own long-standing header comment) throughout - Candidate 2 fixes
the RECEIVER's interpretation of idle silence, not the sender's signalling.
