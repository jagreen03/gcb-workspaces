# Objective

`TKT-019.20` confirmed (Cases 2/3/4) that independent, non-simultaneous
per-lane reset timing lets the write domain of
`gcb_dwdm_async_skew_fifo` advance its pointer past address 0 before the
read domain's own reset/`expected_epoch` has settled — breaking the
overwrite-before-read property that makes *simultaneous* reset safe. This
ticket implements a hardware fundamental fix — a hardened, cross-coupled
reset synchronizer — rather than an in-band wire-format widening
(Candidate A, `TKT-019.19`) or a bloated handshake FSM. No PBG grade
assigned, consistent with every `TKT-019.x` ticket of this kind.

---

## 1. RTL change

`rtl/gcb_dwdm_async_skew_fifo.sv`: every write-domain register (both
pointers and the `do_wr` write gate) is now held in reset by a new,
internally-derived `wr_rst_n_hardened` signal, not the raw `wr_rst_n`
input directly.

- **Local synchronizers** (async-assert / sync-deassert, standard
  glitch-free CDC reset pattern): `wr_rst_n_loc` (write domain) and
  `rd_rst_n_loc` (read domain) each 2-flop-shift their own raw reset
  input before it is treated as deasserted.
- **Cross-coupling**: the read domain's own settled status is produced
  as a SECOND, independent local synchronizer copy (`rd_rst_n_loc_cdc`
  — structurally identical to `rd_rst_n_loc`, same async-reset source,
  so both settle on the same `rd_clk` edge) and crossed into the write
  clock domain through its own dedicated 2-flop synchronizer
  (`rd_rst_n_sync1_w`/`rd_rst_n_synced_w`, clocked by `wr_clk`).
- **`wr_rst_n_hardened = wr_rst_n_loc & rd_rst_n_synced_w`** — both
  operands are themselves registered on `wr_clk`, so their AND is
  glitch-free from the write domain's own point of view. It asserts
  immediately on either raw reset; it deasserts only once BOTH the
  write domain's own reset has settled AND the read domain's settled
  status has propagated across.
- `do_wr = wr_en & ~full & wr_rst_n_hardened` — no write, and therefore
  no `wr_ptr_bin` advance and no `mem[]` write, can occur until the
  cross-coupled condition holds. By the time the first write after
  reset is possible, `rd_ptr_bin` is already guaranteed to be sitting
  at 0 — the simultaneous-reset safety property, reconstructed via
  gating instead of via simultaneity.

**Deliberately one-directional** (write waits on read, not the
reverse): `TKT-019.20` Case 1 (read-domain-first) was already PROVEN
safe under the prior, uncoupled design — only the write-waits-on-read
direction was a confirmed hazard, so only that direction is hardened.

**Two genuine lint findings during implementation** (both resolved
structurally, no waiver used):
1. First draft crossed `rd_rst_n_loc` itself into the write domain —
   Verilator's `SYNCASYNCNET` check correctly flagged one net used
   both as an async-reset condition (read-domain pointer logic) and as
   plain synchronous data (the crossing synchronizer's first stage).
2. Buffering that same net through one extra register did not resolve
   it — the check flags ANY synchronous read of a net also used as an
   async reset, regardless of how many stages follow downstream.
   **Resolved** by driving two independent, structurally-identical
   synchronizer copies from the same raw `rd_rst_n` source instead of
   fanning one copy out to two roles — each net now has exactly one
   role, which is what the check is actually asking for.

**New architectural property, stated explicitly, not hidden**: the
write domain can now never become ready while the read domain is held
in reset, even for otherwise-unrelated traffic — a deliberate coupling,
consistent with this FIFO always being used as one half of one
system-level reset domain pair in every test since `TKT-019.3`. Not
assumed safe for a use case where the two domains are meant to free-run
independently of one another's reset lifecycle.

**Lint**: clean, 36/36 tops, no waivers.

## 2. Adversarial matrix re-run (`test_wdm_link_integration.py`)

Re-ran the exact `TKT-019.20` 5-case suite against the hardened RTL, no
other changes. Reproduced identically across 2 independent full runs.

| # | Case | TKT-019.20 (pre-fix) | TKT-019.21 (post-fix) |
|---|------|----|----|
| 1 | Read-domain-first | PASS (clean) | PASS (clean) |
| 2 | Write-domain-first | **FINDING — `integrity_fail`** | **PASS — clean, byte-exact** |
| 3 | Staggered lanes (60-lane ceiling) | **FINDING — `length_mismatch`** | **PASS — clean, byte-exact** |
| 4 | Clock-absent during reset | **FINDING — `integrity_fail`** | **PASS — clean, byte-exact** |
| 5 | Reset reassertion mid-skew | PASS (clean) | PASS (clean) |

`TESTS=22 PASS=22 FAIL=0`, both runs. Cases 2, 3, and 4 now report the
clean "RESULT: PASSED" branch (byte-exact `N+1` reconstruction), not
the "FINDING (CONFIRMED...)" branch their own test bodies print when
contamination is detected — i.e., the predicted hazard did not
manifest, not merely that something downstream caught it after the
fact. The cross-coupled reset gate physically prevents the write
pointer from racing the read side, for all three previously-confirmed
constructions.

Standalone `Makefile.wdm_payload_mux` regression: unaffected
(unchanged, touches only the mux, not the skew FIFO).

## 3. Known regression — reset-to-ready latency, NOT data corruption

Running the separate, pre-existing `Makefile.wdm_deskew_cdc` suite
(`test_wdm_deskew_cdc.py`, `TKT-019.3`/`.11`'s own async-FIFO
correctness tests) against the hardened RTL: **6/6 tests now fail**
(previously 6/6 passing against the same test file and the pre-.21
RTL — confirmed by temporarily stashing only the RTL change and
re-running, isolating this as a genuine consequence of this ticket's
own fix, not a pre-existing issue).

**Root cause, confirmed by experiment**: these tests assert
simultaneous reset release and proceed to write within ~1 clock edge
per domain afterward. The new `wr_rst_n_hardened` requires roughly
4-5 edges to settle (two 2-flop synchronizer stages in series, across
two domains) before the write side becomes ready — a real, intentional
cost of the glitch-free cross-coupled design, not a correctness
defect. Confirmed directly: temporarily padding
`test_async_fifo_correctness`'s own post-release settle-wait to 10
edges per domain (a throwaway, unstaged experiment, not committed)
made it pass cleanly again. The same mechanism explains the other 5
failures in that suite.

**This ticket does not fix or touch `test_wdm_deskew_cdc.py`** — it
was already in an unrelated, uncommitted (`TKT-019.11`) state, out of
this ticket's scope, and is not part of today's commits in either
repo.

**Separate operational incident, disclosed in full**: while
diagnosing the above, a scratch edit to `test_wdm_deskew_cdc.py` was
reverted with `git checkout --`, which — because the file had never
been `git add`ed — restored it all the way to the last **committed**
version, discarding the entire pre-existing, uncommitted `TKT-019.11`
testbench diff (~641 lines) that was sitting in the working tree
before this ticket's work began. No recovery path exists (checked git
reflog, stash, and VS Code local history — none hold this content).
**That `TKT-019.11` testbench hardening work must be redone from
scratch in a future ticket.** The Architect was informed of this
directly, in-session, before any commit in this ticket was made, and
chose to proceed with `TKT-019.21`'s own (unaffected) deliverables now
and address the lost file separately.

**Disposition**: flagged for a follow-up ticket — either pad
`test_wdm_deskew_cdc.py`'s settle-wait margins to account for the new
latency (once its lost `TKT-019.11` content is reconstructed), or
decide the settle-time cost is acceptable as a standing contract for
any consumer of `gcb_dwdm_async_skew_fifo`. Not decided here.
