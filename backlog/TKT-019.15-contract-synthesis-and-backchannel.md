# Objective

`TKT-019.14` proposed a formal transaction lifecycle and flagged a
`fifo_empty[c]`-based physical drain, composed with a bounded
backchannel, as the strongest *direction* for a retirement barrier —
**explicitly not proven, not selected**. This ticket's job, taken on
with an adversarial-safety-review posture rather than a constructive
one, is to **attempt to falsify that direction before treating any part
of it as established**, then synthesize the actual minimum contract
set required before RTL implementation of retirement, identity
synchronization, reset handling, or a backchannel is authorized.

**Explicitly not assumed true by this ticket:** `fifo_empty`-based
draining, a session nonce, any specific `EPOCH_W`, or "a drain barrier"
as a settled mechanism. Each is re-examined here as a **candidate**,
not a fact. **No RTL is modified, staged, or committed.** No PBG grade
is assigned, consistent with `TKT-019.6`/`.7`/`.12`/`.13`/`.14`'s own
precedent.

### Evidence classes used throughout

* **A — PROVEN (digital simulation, tested conditions):** an actual
  cocotb/Yosys result from `TKT-019.9`/`.11`.
* **B — DIGITAL-SIMULATION FINDING:** a result derived from reading
  the RTL's own structure/logic, not independently re-run in this
  ticket, but not merely asserted either.
* **C — PROPOSED MECHANISM:** a candidate this or a prior ticket has
  named, with no claim it is correct or selected.
* **D — UNRESOLVED CONTRACT:** a decision or number that must exist
  before implementation, and currently does not.
* **E — PHYSICALLY UNVALIDATED ASSUMPTION:** a quantity that would
  require silicon/optical measurement to validate, never claimed as
  validated here.

## 3. Identity authority — re-evaluated, not re-selected

Extended per this ticket's own required fields. No model is selected;
each is tested against delay/duplication/loss/independent-reset,
which none of the four candidates carrying a new mechanism (2-5) have
previously been stressed against explicitly.

### 3.1 Sender-authoritative

| field | answer |
|---|---|
| Creates N | Sender |
| Declares ACTIVE | Sender (implicitly, by starting `S_EMIT`) |
| Declares SUCCESS | Sender (`done`) — receiver only infers |
| Declares ABORTED | **Nobody, authoritatively** — the receiver can locally decide N is void, but has no standing to tell the sender so under this model |
| Declares RETIRED | Undefined — retirement requires knowing both "aborted or succeeded" *and* "physically drained," and this model gives the receiver no channel to declare either back |
| Who may advance identity | Sender only |
| Other endpoint learns transition | Never, structurally, for the abort case |
| Delayed control message | N/A — no control message exists in this model |
| Duplicated | N/A |
| Lost | N/A |
| Independent reset | Receiver's reset is invisible to the sender; sender continues issuing values the receiver may now be misaligned against |

### 3.2 Receiver-authoritative

| field | answer |
|---|---|
| Creates N | Receiver decides *when* N is current; sender must be told the value |
| Declares ACTIVE | Receiver |
| Declares SUCCESS | Receiver, propagated to sender via the (currently nonexistent) new port |
| Declares ABORTED | Receiver |
| Declares RETIRED | Receiver — but "retired" still requires the drain proof this ticket is trying to establish (§4); authority to *declare* is not the same as evidence to *back* the declaration |
| Who may advance identity | Receiver dictates; sender complies |
| Other endpoint learns transition | Via the new port — **delay in this path directly reopens the aliasing window** (§5's `T_prop_fwd`) |
| Delayed control message | Sender could stamp a transaction with a value the receiver has already moved past — the model's own core vulnerability if the propagation delay isn't bounded |
| Duplicated | A duplicate "current identity" message is likely benign (idempotent — same value reapplied) **only if** the sender always fully overwrites its local copy rather than incrementing from it |
| Lost | Sender retains a stale value indefinitely, silently diverging from the receiver — no self-correcting property in this model alone |
| Independent reset | If the sender resets independently, it loses its copy of the receiver's dictated value and reverts to some local default — undefined interaction unless a reset handshake (§7) also exists |

### 3.3 Explicit synchronized/shared identity

| field | answer |
|---|---|
| Creates N | Neither side alone — a third, shared resource |
| Declares ACTIVE/SUCCESS/ABORTED | Whichever side updates the shared resource — ambiguous unless the model also specifies write ownership per event type (not specified by "shared" alone) |
| Declares RETIRED | Same ambiguity — "shared" describes where the *value* lives, not who has authority to *change* it for which reason |
| Who may advance identity | **Undefined unless additionally specified** — this is the model the task's own framing warns against: two counters that happen to read the same shared register are not automatically a valid model unless a reconciliation/write-arbitration rule is also given |
| Other endpoint learns transition | Immediately, by construction, for the *value* — but the shared resource itself must cross into every clock domain involved, and that crossing is unspecified |
| Delayed control message | Reframed as "delayed pointer/value crossing" — the same CDC-latency class of risk as everything else in this epic, not eliminated by calling the register "shared" |
| Duplicated / Lost | Not meaningful concepts for a shared register in the way they are for a message — but the underlying **crossing** can still be delayed or (if implemented via a message-passing update rather than a true shared memory) lost, in which case this degrades to model 3.2 or 3.5's failure modes depending on implementation |
| Independent reset | The shared resource's own reset domain is now a **third** domain requiring reconciliation with both sender and receiver resets — a new three-way reset-ordering problem, strictly harder than the two-way problem `TKT-019.13`/`.14` already found unresolved |

### 3.4 Receiver NACK/ABORT causing sender advancement

| field | answer |
|---|---|
| Creates N | Sender, unchanged |
| Declares ACTIVE | Sender, unchanged |
| Declares SUCCESS | Sender, unchanged (`done`) — **this model still does not give the receiver a way to confirm success to the sender**, only abort |
| Declares ABORTED | Receiver, via the new signal |
| Declares RETIRED | **Neither, currently** — the NACK declares abort; nothing in this model separately declares drain-complete (§4 applies in full) |
| Who may advance identity | Sender, gated additionally on having processed a pending NACK first |
| Other endpoint learns transition | Sender learns of abort via the NACK; delay reopens the window exactly as in 3.2 |
| Delayed control message | **If the NACK is untagged, it can be misapplied to a later, unrelated generation** — the specific risk `TKT-019.14` §8 named and this ticket's §6 formalizes into a required contract |
| Duplicated | A duplicate NACK for an already-processed abort should be idempotent **only if** the sender checks "have I already advanced past this?" before acting — not automatic, must be designed in |
| Lost | Sender never learns to skip the aborted value; **will eventually reuse the exact tag for a legitimate later transaction** — `TKT-019.14` §8's already-identified failure mode, restated as confirmed still true here |
| Independent reset | If the receiver resets after sending a NACK but before the sender processes it, and the sender then also independently resets, **both sides may end up in inconsistent states with no shared record of what happened** — a genuinely new race this ticket surfaces, not previously named |

### 3.5 Explicit transaction-start/end handshake

| field | answer |
|---|---|
| Creates N | Negotiated |
| Declares ACTIVE | Both, by virtue of having completed the start-handshake |
| Declares SUCCESS | Both, via an end-handshake — **this is the one model that closes the "receiver can't confirm success" gap 3.1-3.4 all share** |
| Declares ABORTED | Either side can initiate; the other confirms |
| Declares RETIRED | Closest of the five to a genuine answer — RETIRED can be defined as "the end-handshake (success or abort) has been mutually confirmed," **but this still does not by itself prove physical drain** (§4) — agreement on status is not the same as evidence of emptiness |
| Who may advance identity | Whichever side proposes the next transaction, but only after the prior end-handshake is mutually confirmed |
| Other endpoint learns transition | By construction — the transaction cannot exist without it |
| Delayed control message | Blocks progress (the next transaction cannot start) rather than silently aliasing — the strongest property of the five on this specific axis |
| Duplicated | Needs its own dedup logic (a repeated confirm should not restart or re-trigger anything) — not free, but a well-understood protocol-design problem, not a novel one |
| Lost | **Blocks forward progress entirely** until resolved (a liveness cost, not a correctness violation) — the opposite failure mode from 3.1-3.4, where loss causes silent divergence rather than a stall |
| Independent reset | Detectable — a handshake that never completes because one side reset is observably different from ordinary progress, **provided** a timeout exists on the handshake itself (otherwise: indefinite stall, an availability defect, not a safety one) |

**No selection.** 3.5 is the only model that gives a receiver-visible
success confirmation and turns most failure classes into stalls
(observable, safe) rather than silent divergence (unobservable,
unsafe) — but at the cost this epic has repeatedly noted: mandatory
round-trip latency on every transaction, and it still does not, by
itself, discharge §4's retirement-drain proof obligation. That
trade-off is the Architect's to weigh, not this ticket's to resolve.

## 4. Retirement proof obligation

> After transaction N becomes RETIRED, no word, control message, FIFO
> state, synchronizer state, or other representation originating from
> N may subsequently reach any acceptance point as transaction N or as
> any later transaction.

### Candidate retirement barriers, examined against all seven required questions

For each candidate: (1) what state is observed, (2) where, (3) what
prevents *more* N-data arriving after the observation, (4) what
prevents synchronizer/pipeline state arriving later, (5) what prevents
an in-progress sender transmission, (6) what prevents stale control
messages, (7) what proves the condition across all lanes globally.

**Sender quiescence + FIFO drain (the `TKT-019.14` §6/§11.C direction):**

1. Observed: `fifo_empty[c]` for every enabled lane, in the read
   domain.
2. Where: at the CDC, read-domain logic, per lane.
3. **Nothing, currently** — no signal stops the sender from writing a
   new word for N immediately after an empty observation; this is
   exactly the "sender quiescence" half of the name, and **no
   mechanism enforcing it exists in the RTL today** (confirmed: the
   mux has no abort/stop input at all, port-list-confirmed in
   `TKT-019.13`/`.14`).
4. **Nothing, currently — this is the falsifying case, below.**
5. **Nothing, currently and structurally worse than assumed** — see
   the new finding below.
6. Not addressed by this candidate alone; requires §6's anti-aliasing
   contract on top.
7. Requires an aggregation protocol across `NUM_COLORS` independent
   per-lane observations that does not currently exist — see below.

### Falsifying `∀c: fifo_empty[c]==1 ⟹ N_stale==0`

**This implication is FALSE under the actual CDC architecture, for
three independent, compounding reasons — not merely "unproven."**

**Reason 1 — synchronizer lag (a genuine but bounded effect).**
`gcb_dwdm_async_skew_fifo`'s `empty = (rd_ptr_bin ==
wr_ptr_bin_rdomain)` is computed against a **2-flop-synchronized,
necessarily-stale copy** of the write pointer (`TKT-019.7`'s own
"staleness gap" finding, previously applied only to a *flush* pulse —
it applies with identical force to an *empty observation*, since both
read the same synchronized pointer). A write can be fully committed in
the `wr_clk[c]` domain — the word physically sits in `mem[]` — while
`wr_ptr_bin_rdomain` still reflects the pre-write value, because the
gray-code update has not yet crossed. **`fifo_empty[c]` can read `1` in
the read domain at the exact instant a word has already been
irrevocably written and is only cycles away from becoming visible.**
Holding the observation across the synchronizer's own latency (a
handful of cycles) narrows, but by itself does not close, this
specific window.

**Reason 2 — no sender-side interrupt exists (dominant, not
bounded by anything this epic has previously characterized).**
`gcb_dwdm_payload_mux`'s complete port list (confirmed, `TKT-019.13`
§3 preamble, re-confirmed here) has **no abort/stop input of any
kind**. Its `state_e {S_IDLE, S_EMIT}` FSM runs `S_EMIT` to completion
against its own internal `cycle_idx`/`cycles_total_q` counters once
`start` is latched, with **no external signal capable of interrupting
it mid-transaction.** Consequently: **even a hypothetically perfect,
instantaneous, zero-latency backchannel cannot stop the sender from
continuing to emit words for a generation the receiver has already
decided to retire, if that generation's `S_EMIT` sequence is still
in progress at the moment of the retirement decision.** The sender
will keep emitting, tagged with the *same* (now-being-retired) epoch
value, until its own emission naturally completes. This bound is
**structurally derivable** (a function of the transaction's own
`payload_len`, bounded above by `MAX_PAYLOAD_BYTES`/`MODE_B_LANES`/
`CHUNK_BYTES`, computable from the mux's own `WORDS_MAX` localparam
shape) rather than physically unknown — **but it has not been
computed to a specific cycle count in this desk-analysis-only
ticket**, and it is a materially **larger** window than the FIFO's own
`MAX_SKEW_CYCLES` depth for any transaction long enough that
`WORDS_MAX / MODE_B_LANES` exceeds `D` — plausible at the default
geometries this epic has used throughout (a Mode B transaction's
emit-cycle count is not bounded by `D` at all; the two are unrelated
parameters).

**Reason 3 — no barrier-aggregation protocol exists across lanes.**
Combining `NUM_COLORS` independent, asynchronously-updated
`fifo_empty[c]` observations into one atomic "the whole group is
retired" conclusion is a genuine distributed-agreement problem this
epic has not designed: lanes can be independently refilled by a still-
transmitting sender (Reason 2) at different times, so "I saw lane 3
empty a moment ago" does not compose with "I saw lane 47 empty a
moment later" into a single valid instant at which *all* were
simultaneously, verifiably empty, without additional protocol
machinery (e.g. a barrier/rendezvous construct) that is not specified
anywhere in this repo.

**Conclusion: the implication cannot currently be proven, and is
actively falsified as a single-snapshot criterion by Reason 1 (a
narrow, closeable timing gap) and, dominantly, by Reason 2 (a
structural absence of sender interruptibility that no snapshot timing
fix addresses at all).** `TKT-019.14`'s framing of physical drain as
"the strongest available direction" is **withdrawn as a claim of
sufficiency** by this analysis — it remains a real, reusable-signal
*ingredient*, but is not, by itself, a retirement barrier, and was
never independently tested as one.

## 5. Retirement latency

```
T_retire = T_prop_fwd + T_quiesce + T_drain + T_prop_back + T_accept_guard
```

| term | status | basis |
|---|---|---|
| `T_prop_fwd` (receiver's abort decision reaching the sender) | **D — unresolved contract** | Depends entirely on a backchannel medium not yet chosen (§6) |
| `T_quiesce` (time for the sender to actually stop emitting N-tagged words after learning of retirement) | **B — digital-simulation-adjacent finding, structurally bounded but not computed** | §4 Reason 2: bounded above by the sender's own residual `S_EMIT` length, a function of `MAX_PAYLOAD_BYTES`/`MODE_B_LANES`/`CHUNK_BYTES` — a real, parameter-derivable ceiling, **not computed to a specific cycle count here**, and **not** bounded by `MAX_SKEW_CYCLES`/`ALIGN_TIMEOUT` at all — a materially different, and generally larger, quantity than this epic has previously treated as the drain window |
| `T_drain` (FIFO-side drain of whatever queued up before/during quiescence) | **A (partial) + E (partial)** | The `D`-cycle cap on queue depth itself is `PROVEN — DIGITAL SIMULATION, TESTED CONDITIONS` (`TKT-019.11`); the synchronizer settling margin layered on top is a simulation-level abstraction of a physical metastability process and is `E` for its *exact physical* duration |
| `T_prop_back` (confirmation returning to the receiver that the sender has quiesced) | **D — unresolved contract** | Same dependency as `T_prop_fwd` |
| `T_accept_guard` (residual safety margin the receiver holds beyond the other terms) | **D — unresolved, and currently unsizable** | Its entire purpose is to absorb whatever uncertainty the other four terms leave; with four of five terms open or partially open, this term cannot be sized either |

**A finite upper bound for `T_retire` cannot currently be established.**
Not because any one term is merely inconvenient to measure, but
because: (a) two of five terms depend on a backchannel medium this
ticket does not select (§6); (b) the one term this ticket newly
bounds structurally (`T_quiesce`) reveals the relevant drain window is
**larger than this epic's prior working assumption** (bounded by
transaction length, not `MAX_SKEW_CYCLES`); and (c) the residual-margin
term is, by construction, unsizable while the others remain open. This
is stated as the exact reason, per the task's own instruction, not as
a generic "more work needed."

## 6. Backchannel

### Candidate physical mechanisms

| | A. Reverse optical wavelength | B. Out-of-band electrical sideband | C. Time-multiplexed reverse frame | D. Host/control-plane mediated |
|---|---|---|---|---|
| **Mechanism** | A dedicated λ (existing or newly added to the comb) carrying receiver→sender traffic | A separate electrical bus/wire alongside the optical link | Reverse traffic interleaved in time on the *same* forward wavelength/fiber | Route retirement/fault signals to whatever external host/control-plane entity already issues `start` and reads `done`/`payload_valid` (implicitly assumed to exist, since something external drives those ports today, though it is unmodeled in this repo) |
| **Latency** | Bounded by short-reach optical propagation (fast in absolute terms), **plus** a new CDR/receive chain at the sender this epic has never designed | Likely lower/more predictable (electrical, short-reach), protocol-dependent, unspecified | Worst of the three — shares capacity with forward traffic, needs its own scheduling/arbitration | Unbounded by hardware standards — depends entirely on host software responsiveness, unmodeled |
| **Ordering** | Naturally in-order on a single dedicated channel | Depends on the chosen bus protocol | Manageable only if the TDM schedule is deterministic | Depends on host software's own queueing discipline, unmodeled |
| **Reliability** | Inherits the same unmodeled optical BER as the main link (`TKT-019.6`'s own deferral applies identically here) | More mature/understood electrical practice, still needs its own error detection | Same unmodeled optical BER as the main link | Depends on host interconnect, unmodeled |
| **Loss behavior** | No recovery unless composed with an ack layer | Same | Same | Host software can more readily implement ack/retry/timeout than a hardware FSM can |
| **Reset behavior** | New receive path at the sender needs its own CDC crossing into the sender's `clk` — a **new instance** of this epic's core recurring hazard | Simpler crossing class than optical CDR, but still a new domain crossing | Most complex of the three — bidirectional sharing of infrastructure this epic characterized as unidirectional-per-λ (`TKT-019.3`) | Host-side reset/reboot semantics are entirely outside this RTL's scope |
| **Generation tagging** | Not automatic — must be designed into the message format, any of A-D | Same | Same | Same |
| **Bandwidth** | Consumes a physical λ from the same budget `TKT-019.3` characterized (≈60λ) — a real resource cost | Additive, separate physical resource — an advantage over A specifically | Steals capacity directly from forward payload — a direct, quantifiable tradeoff against the transport this epic protects | No RTL-side bandwidth cost; cost is entirely in host-interconnect terms, unmodeled |
| **Physical implementation burden** | High — new laser/receiver pair, unbuilt, uncosted | Moderate — new connector/trace/bus, reuses conventional electrical design practice | Highest — likely needs optical circulators/isolators not previously in scope | Low RTL-side burden, but the host/control-plane layer itself is entirely unspecified in this repo, so "low" is conditional on that layer already existing in a form capable of this role |
| **Needs its own retirement barrier?** | Yes, symmetrically — its own receive FIFO/CDC needs the identical safety treatment this whole epic chain has been giving the forward path | Yes, same reasoning, likely lower-risk crossing | Yes, same reasoning | The barrier problem shifts to host software, which this ticket cannot evaluate |
| **Delayed-message aliasing risk?** | Yes — same for all four; addressed only by the anti-aliasing contract below, not by medium choice |

**No medium is selected — the evidence available in this repo is
insufficient to choose among them,** per the task's own instruction:
none has a specified physical spec, a measured latency/BER, or an
existing receive-chain design to evaluate against. D is flagged as
materially different (it reuses an *already-implicitly-assumed*
external actor rather than inventing new inter-block RTL or new
physical media) but is equally unevaluable without a description of
that external control plane, which does not exist in this repo.

### Control-plane anti-aliasing contract

**A control message MUST NOT be trusted solely because it contains a
transaction number** — confirmed necessary by direct construction
(§3.4's delayed-NACK case; §7's delayed-pre-reset-control-message
case). The minimum required content, all five items, not a subset:

* **Session/generation identity** — distinct from the per-transaction
  epoch; required so a message referencing "transaction 3" cannot be
  confused across a reset boundary with a *different* session's
  "transaction 3."
* **Message type** — an untyped signal is inherently ambiguous between
  abort/success-ack/reset-ack/etc.; `TKT-019.14` §8 already found the
  CDC's two distinct watchdogs (`ALIGN_TIMEOUT` vs.
  `REASSEMBLY_TIMEOUT`) need to be individually distinguishable, which
  requires typing at minimum.
* **Transaction identity** — the per-generation tag itself, the
  "obvious" field the task explicitly warns is *not* sufficient alone.
* **Sequence/order information**, distinct from the transaction tag —
  needed to detect duplicate or reordered delivery of *control*
  messages, independent of whatever the *data*-plane tag is doing.
* **Sender-state and receiver-state validation** — each endpoint must
  check an incoming control message against its **own** locally-
  tracked expected state before acting on it, not apply it blindly
  because the fields parse — e.g. a retirement message for a
  generation the recipient believes is *already* retired is itself a
  signal something is wrong, not something to silently re-apply.

**This is a nontrivial reliable-transport-protocol design problem in
its own right** — composing it correctly is not "add a wire and a
tag"; a control-plane tag that is *itself* finite-width and wraps
inherits the identical `I`-vs-`N_reuse_max` question this entire
ticket chain has been chasing in the data plane, one level up.

## 7. Reset/session boundary

### Why widening `EPOCH_W` does not solve reset-to-zero aliasing — demonstrated again, precisely

`expected_epoch <= '0` and `tx_epoch <= '0` are **unconditional**
assignments on reset, independent of `EPOCH_W`'s value. A 4-bit and a
64-bit counter both restart at the **identical** value 0. `EPOCH_W`
only bounds how long *continuous, in-session* counting takes to repeat
a value; it has **zero** effect on what value is assigned **at** a
reset boundary. A delayed pre-reset word tagged 0 aliases the first
post-reset transaction with equal certainty at any width. This is a
logical demonstration from the reset branches' own unconditional
assignment, not an empirical result, and is not weakened by any
`EPOCH_W` choice whatsoever.

### Candidate mechanisms, re-examined against all eight required conditions

| | A. Physical drain/quiescence after reset | B. Persistent/nonvolatile session generation | C. Protocol-level reset/session handshake |
|---|---|---|---|
| **One-sided reset** | **Fails** — protects nothing if only the receiver resets; a sender that never stopped continues transmitting through the receiver's quiescence window | Helps for the *value* namespace, but the two sides' markers can only be known to agree if a cross-notification also exists (reduces to needing C anyway for this case) | **This is the case C is built for** — the reset side notifies the other explicitly |
| **Simultaneous reset** | Helps only if genuinely simultaneous (`TKT-019.13` §9.1's own conditional finding, unresolved) and the quiescence duration is correctly sized (§5 — currently not) | Both sides incrementing independently on the *same* physical event does not guarantee they land on the *same* new value without a shared reference — an accumulating-drift risk over many resets, not previously examined | Needs a defined initiator/tie-break rule — a genuinely symmetric negotiation is harder than a one-sided notify |
| **Delayed pre-reset data** | The exact risk this mechanism exists to close, contingent on an unproven duration | Solved for the *tag-aliasing* question specifically, provided the wider (prefix+epoch) comparison is correctly implemented (not designed here) | Establishes agreement on the new value, but does **not** by itself guarantee physical drain of old contents — needs composing with A, not substituting for it |
| **Delayed pre-reset control messages** | Not addressed by this mechanism at all | Helps if the message itself carries the session prefix (ties to §6's anti-aliasing tuple) | Same — requires the anti-aliasing tuple regardless of mechanism |
| **Generation rollover** | Orthogonal — ordinary in-session wraparound, unaffected | The *coarse* counter has its own, much-longer-period wraparound — "practically eliminated," not structurally, restated not resolved | Orthogonal |
| **Storage failure** | N/A | **The central risk**, restated: if the persisted value is lost or corrupted, the system reverts silently to today's exact unsafe default, with no indication anything changed | N/A directly, unless composed with B |
| **Initialization races** | Presumably manageable, unverified | A genuinely fresh device (first-ever boot) needs a defined bootstrap value; a field reset that *erases* the persisted marker reproduces a previously-used value via an unrelated maintenance path — a new failure class this analysis surfaces, not previously named | A freshly-reset endpoint must initialize far enough to *participate* in a handshake before it can complete one — a bootstrapping race |
| **First post-reset transaction** | Highest-risk moment either way; safe only if the (unproven) quiescence bound genuinely covers the worst case | Safe, provided persistence genuinely worked; identical risk to A if it did not | Safe once handshake and drain are both satisfied — **not** by the handshake alone |

**On the explicit instruction not to assume a nonce is safe merely
because its collision probability is small:** a session nonce
provides a **probabilistic**, not a deterministic, guarantee — a
fundamentally different epistemic category from every structural
argument this ticket chain otherwise relies on (`TKT-019.12`/`.13`/
`.14`'s own recurring caution against mixing probabilistic and
structural safety claims, restated here for the reset case
specifically). A larger bit width lowers the collision probability; it
does not convert the guarantee into a proof. Mixing a probabilistic
reset-safety argument into a system whose other invariants are meant
to be provable-by-construction is an explicit epistemic downgrade,
which must be stated plainly if ever adopted, not obscured by a large
number.

**Can reset safety be made deterministic? Yes, in principle — not yet,
in this architecture.** A composition of C (handshake, for
cross-notification and value agreement) with A (drain/quiescence, held
across the handshake, for physical safety), optionally layered with B
for the across-power-cycle case specifically (since a live handshake
state does not survive a genuine power loss), is the reasoned
direction — **flagged, not selected**, mirroring this ticket chain's
consistent posture, and explicitly incomplete: none of A, B, or C
alone closes every row of the table above, and no combination has been
designed to RTL detail or verified.

## 8. Identity-space sizing — revisited, not re-derived from scratch

### `D ≤ I`, restated with its assumptions explicit

`TKT-019.12`/`.13` derived `D ≤ I` under these assumptions,
made explicit here for the first time as a checklist:

1. The **only** mechanism protecting against reuse is passive tag
   comparison (a word is safe once its tag numerically mismatches
   `expected_epoch`) — **no active retirement barrier exists.**
2. The relevant "drain window" for a buried word is bounded by the
   FIFO's own depth `D` (`MAX_SKEW_CYCLES`) — i.e. no larger source of
   delay contributes to how long a word can remain live.
3. Single-burst traffic — one backlog fills, then drains; not
   sustained, concurrent arrival-and-drain.
4. A single lane's own backlog, not compounded across lanes (shown
   in `TKT-019.14` §9 not to need a stronger condition on its own).

### Does the retirement mechanism analyzed in §4 remove any of these assumptions?

**No — because §4 falsified the only retirement mechanism this ticket
chain has proposed.** Assumption 1 is **not** removed: no active,
proven barrier exists, so passive tag comparison remains the
**operative** (not merely fallback) safety mechanism today. Assumption
2 is **directly contradicted, in the unsafe direction**, by §4/§5's
new finding: the sender's non-interruptibility means the real drain
window is bounded by the transaction's own residual emission length,
not by `D` — a **materially larger** quantity for any transaction
whose `WORDS_MAX / MODE_B_LANES` exceeds `D`, which is not a corner
case at this epic's own default geometries. Assumptions 3-4 are
unchanged, still open per `TKT-019.14` §9.

### Which of the task's five possible conclusions applies

**A combination of (3) and (5), not a single clean answer, is the
honest synthesis:**

* **(3) 4 bits is demonstrably insufficient — and this is now
  derivable, not merely suspected.** `TKT-019.13`'s own finding that
  `D = I = 16` was "marginally safe, zero slack" **is superseded** by
  §4/§5's finding here: the *effective* drain window that must fit
  within `I` is no longer `D` (16) but `D` plus the sender's residual
  emission length — a quantity this ticket shows is structurally
  larger for realistic transaction sizes, **without needing to invoke
  sustained traffic, a backchannel, or reset at all.** `TKT-019.13`'s
  "zero slack" framing is hereby corrected to "already exceeded" for
  any transaction long enough to matter, pending only the exact cycle
  count `TKT-019.14`/`.15` deliberately did not compute (desk analysis,
  not simulation).
* **(5) The precise sufficient width still cannot be computed.**
  `T_prop_fwd`, `T_prop_back`, and `T_accept_guard` remain fully open
  (§5), and no retirement barrier has been proven that would make
  width secondary (§4). A number cannot be derived from three open
  terms.
* **Conclusion (4) — identity width becomes secondary because
  retirement prevents reuse while stale state exists — is explicitly
  NOT available today.** It remains the eventual *goal* if a future
  ticket successfully designs and proves the composed barrier this
  ticket's §4/§6/§7 sections gesture toward (drain + backchannel +
  handshake), but nothing analyzed in this ticket chain has built or
  verified that barrier. Naming it as achieved now would be exactly
  the "manufactured bound" the task instructs against.

**`EPOCH_W` is not selected, widened, or otherwise numerically
recommended by this ticket.**
