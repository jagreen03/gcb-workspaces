# Objective

**Requirement ≠ implementation.** [[TKT-019.6]] specified *what* the
transport must guarantee (the eight `REQ-TX-*` requirements) and sketched
candidate mechanisms (M1-M6) to guarantee it — but in doing so, it framed
M2 (hard FIFO flush) as the *primary* Ghost Payload fix and M1 (epoch
tagging) as a mere backstop. The Architect's review is correct to flag
that as a premature solution-lock: nothing in [[TKT-019.5]]'s evidence
actually ranks those two mechanisms against each other, and "physically
flushing 60 async FIFOs" carries a specific, non-obvious CDC risk this
story surfaces properly instead of assuming away.

This story evaluates candidate RTL mechanisms against [[TKT-019.6]]'s
invariants along three axes — **Failure Coverage**, **Area/Latency Cost**,
**Optical Bandwidth Overhead** (bits added to the wire format; a digital,
countable property, not a BER claim — the [[TKT-019.4]] epistemic boundary
still holds and is not touched by this story) — and arrives at a reasoned
recommendation per axis. **No RTL is written.** The ticket stays
`open | pending`: a recommendation is not a ratified decision, and a build
story does not start from this ticket alone.

## The Trade Matrix

### Axis 1 — Ghost Payload Prevention: Hard Async FIFO Flush vs. Epoch Tagging/Quarantine

**The non-obvious finding that reframes this whole axis:** a "hard flush"
of `gcb_dwdm_async_skew_fifo` is not the clean, instant operation
[[TKT-019.6]]'s M2 described. That module's read domain only ever holds a
**gray-code-synchronised copy** of the write pointer — by the construction
TKT-019.3 built specifically to avoid metastability, that copy is *always*
one-to-a-few write-clock cycles **stale** relative to the true, current
write pointer. A single-pulse "jump the read pointer to the synced copy"
flush therefore only discards what had *already* crossed the synchroniser
at the instant of the pulse — any write-domain data in flight through the
2-flop crossing at that moment survives the flush and reappears afterward,
indistinguishable from fresh data. A *correct* hard flush is not a single
pulse; it must be held (or re-sampled) across the synchroniser's full
latency to guarantee catching a truly-current pointer — which is exactly
the kind of implementation subtlety a specification should not paper over.

| | Hard Async FIFO Flush | Epoch Tagging + discard-on-mismatch pop |
|---|---|---|
| **Mechanism** | A `flush` input per lane; read pointer jumps to the synchronised write-pointer copy, held/re-sampled across the sync latency to be correct | Every word tagged with a small epoch counter; the barrier treats a head-of-FIFO epoch mismatch as "not ready" (same as empty); a mismatched head is popped and discarded (not forwarded) by the read domain's own ordinary `rd_en` path, never presented to the barrier |
| **Failure coverage** | Prevents the mix outright, **once correctly held across sync latency** — the naive single-pulse version has the staleness gap above and would not fully prevent it | Prevents the mix outright at the barrier (a stale-epoch head can never align with fresh-epoch heads on other lanes); bounded by how many stale words are queued, not by synchroniser latency |
| **New CDC risk introduced** | A **new** control primitive (`flush`) manipulating the read pointer outside the pattern the async FIFO was designed and verified for — TKT-019.3's verification does not cover this path at all | **None new** — "pop without forwarding" reuses the exact `rd_en` pop operation already proven correct; the only addition is a comparator gating what happens to an *already-verified* operation |
| **Verification cost** | High: 60 replicated instances of a genuinely new CDC-adjacent control path, each needing its own corner-case coverage (flush racing a live write, flush pulse width vs. sync latency, flush-during-partial-sync) | Lower: the tag-compare logic is ordinary same-domain combinational logic; the pop path it gates is already verified |
| **Area/latency cost** | Low gate cost per instance nominally, but the *correct* (latency-held) version adds a counter per lane (60×) to time the hold | Low-moderate: a tag register + comparator per lane (60×), plus the barrier's alignment condition grows from "non-empty" to "non-empty AND epoch-matched" |
| **Data-path footprint** | None — purely a control-plane addition, `color_word_t` unchanged | Touches the data path: the epoch tag must ride in every word (the barrier needs it per-pop, not just at the end), which means `color_word_t` or an equivalent per-lane side-channel grows by the tag width, rippling into the mux, the async FIFO's `DW`, the CDC, and the demux |
| **Optical bandwidth overhead** | Zero | Small but nonzero — proposed 4-8 bits per word (not per transaction — every word needs it for the barrier's per-pop check), against a 136 b word that's a ~3-6% sideband increase, not a payload-bytes increase |
| **Residual risk if implemented alone** | The staleness gap, if the hold duration is ever under-specified or mis-implemented in a future change | Tagging *without* the discard-on-mismatch pop is actively dangerous, not merely incomplete: a stale-epoch head that is never removed permanently blocks alignment for that lane — converting a one-time silent-contamination risk into a **permanent stall** for every future transaction sharing that lane, recoverable only by a full reset. Tagging and discard-pop are not independently optional; they are one mechanism. |

**Recommendation (reasoned, not ratified):** epoch tagging with
discard-on-mismatch pop, not a dedicated flush primitive. The deciding
factor is not cost — it is that the flush path is *novel and unverified*
against this specific async FIFO's CDC structure, while the discard path
*reuses an already-proven operation* and only adds ordinary same-domain
comparison logic around it. [[TKT-019.6]]'s M2 should be read as
superseded by this finding, not merely reprioritised — a standalone hard
flush is not recommended as a fallback either, given the staleness gap.

### Axis 2 — Integrity/Framing Protection: CRC32 vs. Checksum vs. Duplicated Control Bits

| | CRC32 | Checksum (additive/XOR, 8-16 b) | Duplicated control bits |
|---|---|---|---|
| **Failure coverage** | Strong — catches all single-bit and the large majority of multi-bit/burst error patterns up to its polynomial's guaranteed window (industry-standard class, comparable to Ethernet FCS) | Weaker — an additive or XOR checksum misses many multi-bit patterns a CRC would catch (e.g. compensating flips); adequate only as a cheap "probably fine" signal, not a strong guarantee | Strong **for the specific bits duplicated**, zero coverage for anything not duplicated |
| **What it protects** | The framed payload body (and, if deliberately included in its covered range, the header and control fields) | Same scope as CRC, weaker guarantee | Whatever specific fields are chosen — practically, only the handful of header/control bits (mode, length, `is_tile_final`), never the bulk payload |
| **Area/latency cost** | Moderate — a 32-bit CRC compute/compare (shift-register or pipelined tree), well-understood, low incremental latency if pipelined | Low — an adder/XOR tree, cheaper and faster than CRC | Very low — replicate a few bits, one comparator |
| **Optical bandwidth overhead** | 4 B/transaction — ≈1.5% of a 271 B Mode A payload, ≈0.4% of a 1024 B Mode B payload (well inside the 10-12% framing/FEC margin [[GCB-035]]/[[GCB-036]] already budgeted) | 1-2 B/transaction, smaller than CRC32 but the coverage gap is the real cost, not the bandwidth | A few bytes (covering only 3-4 control bytes, not the payload) — negligible in isolation, but does **not** substitute for payload coverage at any bandwidth cost, since duplicating the *payload itself* would double bandwidth (100% overhead) and is not what this candidate means |
| **Explicit limitation** | Does not guarantee detection of every conceivable corruption pattern — a cheap, well-characterised detector for the single/few-bit-flip class [[TKT-019.5]]'s tests actually exercised, not a cryptographic guarantee. Sizing against a real bit-error *distribution* is optical-channel territory, explicitly deferred per [[TKT-019.6]] | Same limitation, worse coverage | Protects only what it duplicates — `is_tile_final` corruption is **not** automatically caught by a payload CRC unless the flag is deliberately folded into the CRC's own covered range, which is an implementation choice, not a given |

**Recommendation (reasoned, not ratified):** these three are not mutually
exclusive alternatives — they protect different things and [[TKT-019.6]]'s
M4 (Protected Completion) already implicitly depends on combining two of
them. CRC32 is recommended for the payload body (INT-001/002) on failure-
coverage grounds over a cheaper checksum, at a bandwidth cost small enough
to fit inside existing framing margin. Duplicated/protected encoding is
recommended specifically for `is_tile_final` (closing the structural half
of FRM-001) because a payload CRC does not automatically cover a sideband
control bit unless deliberately arranged to — treating CRC32 as sufficient
for *everything* would leave exactly the gap [[TKT-019.5]] found hardest
to detect (the early/suppressed `is_tile_final` cases).

### Axis 3 — Timeout Recovery: Watchdog Timer vs. Explicit Abort Signaling

| | Watchdog Timer | Explicit Abort Signaling |
|---|---|---|
| **Mechanism** | Receiver-local counter, self-bounding; forces a clean reset and a distinctly-named fault if reassembly hasn't completed within N cycles of the first word | A control-plane-issued abort pulse the receiver obeys on command |
| **Failure coverage** | Self-contained — bounds the hang **even if nothing else in the system ever notices** anything is wrong | Depends entirely on the control plane correctly detecting the fault and issuing the abort in time. [[TKT-019.5]] Section B's suppressed-`is_tile_final` finding is the direct counter-example: the signal the control plane would naturally watch (`stuck`) fires **late and misattributed** (names all 60 lanes, looks like "everything failed," not "the flag is missing") — a control-plane-only mechanism inherits that misattribution with no independent backstop |
| **Area/latency cost** | Low — one more counter+comparator, the exact pattern the CDC barrier's own `ALIGN_TIMEOUT` already uses | Low RTL cost (a handshake input), but a real integration/control-software cost — something external must implement correct fault detection and timing, which is a dependency this story cannot verify or bound |
| **Optical bandwidth overhead** | Zero | Zero |
| **What it cannot do alone** | Cannot be deliberately triggered early by the control plane for reasons other than a genuine hang (e.g. a planned reconfiguration) | Cannot guarantee *any* bound if the control plane itself is fooled or slow — which is the exact failure class observed |

**Recommendation (reasoned, not ratified):** Watchdog Timer as the
mandatory baseline — it is the only one of the two that provides a bound
independent of whether anything else in the system correctly diagnoses the
fault, which is precisely the property [[TKT-019.5]] showed is currently
missing. Explicit Abort Signaling is recommended as an **additive**
fast-path for deliberate, control-plane-initiated aborts (not fault
recovery), never as a substitute for the watchdog — a system that
implements only explicit abort inherits the exact misattribution risk this
story exists to close.

## What this story does not do

No RTL. No ratified decision — every recommendation above is reasoned and
traced to a specific [[TKT-019.5]] finding or a mechanistic property
derived in this story (the flush-staleness gap, the tag-without-discard
stall risk), but ratifying it is the Architect's call, made against this
document, not inside it. [[TKT-019.6]]'s M1/M2 framing is superseded by
Axis 1's finding above; [[TKT-019.6]]'s other invariants (M3-M6) are
unaffected by this story and are not re-opened here.
