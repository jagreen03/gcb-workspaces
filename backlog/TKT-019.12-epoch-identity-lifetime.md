# Objective

`TKT-019.11` proved, empirically, that the invariant

```
word.epoch == expected_epoch
```

is **necessary but not sufficient**: a word whose epoch tag numerically
*coincides* with `expected_epoch` after a full `EPOCH_W`-bit wrap is
structurally indistinguishable from genuinely current data, and the RTL
accepted it. The Architect's framing is exact — this is an **identity
reuse** problem, not a comparator bug, and the fix is not "make the
counter wider" until a specific width has actually been shown sufficient.

This ticket does **not** patch RTL. It is architecture-first work: define
the invariant that is actually mathematically sufficient, derive whether
any of the numbers needed to evaluate it currently exist anywhere in this
epic's own contract, and — if they do not — say so exactly rather than
inventing them. **No RTL is modified, staged, or committed by this
ticket.** No PBG telemetry grade is assigned (architecture/trade-study
ticket, consistent with `TKT-019.6`/`TKT-019.7`'s own precedent).

---

## 1. Problem statement

`gcb_dwdm_deskew_cdc`'s barrier treats a lane as "ready" only if its
head-of-FIFO word's epoch tag equals `expected_epoch` (`epoch_match`), and
discards (pops without forwarding) any head word that does not
(`epoch_discard`). This makes the barrier's *comparison* logic sound —
two values are either equal or they are not — but the comparison is only
as trustworthy as the assumption that **two different pieces of data
sharing the same tag value are never both reachable at the same time.**
`TKT-019.11` disproved that assumption under one specific, constructed
condition (a full `EPOCH_W=4` wrap with a straggler still resident). The
question this ticket answers: under what conditions, precisely, does that
assumption hold, and does this architecture currently establish those
conditions for *any* value of `EPOCH_W`?

## 2. Current invariant (as implemented, `TKT-019.8`/`TKT-019.10`)

```
accept(word) ⟺ word.epoch == expected_epoch
```

with `expected_epoch` a free-running `EPOCH_W`-bit counter, incremented
by exactly 1 (mod `2^EPOCH_W`) on either (a) a completed aligned pop
carrying `is_tile_final`, or (b) a `txn_void` timeout. No flush, no
quarantine, no generation marker beyond the raw tag value itself
(`TKT-019.7`'s ratified choice of epoch-tag-plus-discard-pop over a hard
FIFO flush — see §7 for why that choice is not re-litigated here but
*is* incomplete).

## 3. Why `TKT-019.11` disproves this invariant's sufficiency

The invariant above is **pure value equality with no generation
memory**. It cannot distinguish "this tag value was assigned to the
transaction I am currently assembling" from "this tag value was assigned
to some *earlier* transaction that happens to have the same numeric
value because the counter wrapped." `TKT-019.11`'s
`test_deskew_cdc_epoch_rollover_aliasing` constructed exactly this case
(16 forced wraps, then a straggler tagged epoch 0 delivered alongside a
genuine epoch-0 transaction) and observed acceptance of the straggler.
The RTL behaved **exactly as specified** — `epoch_match` was correctly
`1`, because the tag values were, in fact, equal. The defect is not in
the comparator; it is in treating tag equality as a *proxy* for
transaction identity without ever establishing that the proxy is unique
over the relevant time window.

## 4. Formal identity-safety invariant

Let a "word" become **live** at the moment it is first written into a
lane's FIFO carrying epoch tag `V`, and remain live until the last
instant it is structurally reachable by any accept-path logic (queued,
un-popped, un-discarded). Let **generation `g(V)`** denote a specific
*assignment* of value `V` to a specific transaction attempt — the same
numeric `V` can be assigned to generation `g_0`, then later (after wrap)
to a different generation `g_k`.

**The safety invariant is not "no two live words ever have equal `V`."**
It is:

```
∀ words w1, w2 with w1.V == w2.V:
    live(w1) ∩ live(w2) == ∅   OR   g(w1.V at issue) == g(w2.V at issue)
```

i.e. two words may only ever share a numeric tag while both are live if
they were **assigned that tag by the same generation** (ordinary,
same-transaction duplication — e.g. multiple words of one transaction
all correctly carrying that transaction's own epoch — which is
intended and safe). The unsafe case, exactly the one `TKT-019.11`
constructed, is two words from **different** generations, both live,
sharing `V`. The comparator as implemented cannot tell these apart —
it only ever evaluates `word.V == expected_epoch`, which is silent on
*which* generation `expected_epoch` currently denotes.

## 5. Definitions

* **`I` — identity-space size.** `I = 2^EPOCH_W`. The number of distinct
  numeric tag values the counter can hold. **MEASURED / DERIVED** —
  this is arithmetic, not a claim about the system.

* **`T_stale_max` — maximum physical residence time of stale data.**
  The longest interval, from the moment a word becomes live, during
  which it remains structurally reachable by the accept path (queued
  and not yet popped by either an aligned pop or an `epoch_discard`
  pop). **Not a fixed constant this architecture currently defines** —
  see §6.A-K. Where a number is quoted below it is explicitly labeled
  by its actual epistemic status (`ARCHITECTURAL ASSUMPTION`,
  `UNPROVEN`, or `OPEN`) — none is `PROVEN`.

* **`N_reuse_max` — maximum number of transaction identities
  (generations) that can be issued or reused while a given piece of
  stale data remains live.** If generations are issued at their fastest
  possible rate (minimum inter-generation period `T_txn_min`), then

  ```
  N_reuse_max = ceil( T_stale_max / T_txn_min )
  ```

  This is the number of times the epoch counter can increment during
  one stale word's worst-case lifetime. **DERIVED, conditional on
  `T_stale_max` and `T_txn_min` both being proven finite bounds** —
  which, per §6/§7, they currently are not.

## 6. Is `I > N_reuse_max` the necessary condition, or a stronger one?

**`I > N_reuse_max` is necessary, but on its own it is not sufficient
for THIS architecture** — a strictly stronger condition is required
because the identity comparison here is **not** a simple single-word,
single-slot register (the textbook sequence-number case, e.g. TCP/RFC
1982-style serial-number safety, where "half the space" arguments
apply to a *single* in-flight value). It is a **`DEPTH`-deep FIFO per
lane**, and `epoch_discard` only examines the **head** of that FIFO,
one pop per qualifying read-domain cycle. A lane can legitimately hold
up to `DEPTH` (`MAX_SKEW_CYCLES`) queued stale words simultaneously
(`TKT-019.11`'s own `test_deskew_cdc_skew_exceeds_fifo_capacity`
demonstrated `DEPTH`-deep backlogs are a real, reachable state, and
`test_deskew_cdc_multi_lane_stale_and_future_epoch` demonstrated
multi-deep backlogs specifically composed of *different* stale
generations). A word buried behind `k` other queued words is not even
*examined* for discard until the `k` words ahead of it have each been
popped, at one pop per cycle in the worst case (`channel_enable`
staying asserted, no interruption).

This produces a **second, independent race**, distinct from simple
wraparound: if the epoch counter can complete a full `2^EPOCH_W`-value
lap in **fewer read-domain cycles than it takes to drain a
maximally-full backlog (`DEPTH` cycles)**, a word sitting near the tail
of that backlog can have its tag numerically **lapped** by
`expected_epoch` before it is ever examined for discard — at which
point, instead of mismatching (and being discarded) on its first
check, it *matches* on its first check and is treated as fresh. This
is structurally the same failure `TKT-019.11` found, but reachable
through FIFO depth instead of pure idle waiting, and it means the
necessary-and-sufficient condition is closer to:

```
2^EPOCH_W  >  N_reuse_max  +  (worst-case number of epoch advances
                                that can occur while any single lane's
                                backlog fully drains)
```

which, given a backlog can be up to `DEPTH` words deep and each
requires at least one read-domain cycle to examine/discard, further
requires establishing a bound on **how many epoch advances can occur
per `DEPTH` read-domain cycles** — itself dependent on `T_txn_min`
measured in the *same* units. **At the cocotb bring-up geometry,
`DEPTH (MAX_SKEW_CYCLES) = 16` and `2^EPOCH_W = 16` are numerically
equal** — meaning, by this stronger criterion, the margin is not just
"unproven," it is **zero or negative** even setting aside sender/
receiver desynchronization and reset (§8/§9 below). This is a derived
structural observation from the RTL as written, not a new test result
— it has not been separately falsified by simulation in this ticket,
and is labeled accordingly.

**What assumptions would make `I > N_reuse_max` (the simpler form)
constitute an actual proof, if `T_stale_max`/`T_txn_min` existed:**

1. `T_stale_max` is a **proven, finite** upper bound on how long any
   word can remain live, independent of what the rest of the system
   does afterward (not "however long it takes for enough further
   transactions to occur" — see §7's circularity finding).
2. `T_txn_min` is a proven **lower** bound on the time between any two
   successive generation-identity assignments, accounting for **every**
   path that can advance the counter (both the completion path and the
   `txn_void` path), not just the slower of the two.
3. The counter increments by exactly 1 per generation, with no skips
   and no double-assignment of one value to two different generations
   under any interleaving.
4. The backlog-drain race in this section does not apply, or is
   separately bounded (i.e. `DEPTH` cycles of drain time is itself
   `≤` the time it takes to exhaust the margin above).
5. The **sender's** and **receiver's** notions of "the current
   generation" are proven to stay in lockstep for the entire analysis
   (§8 shows this is currently false, independent of `EPOCH_W`).
6. Reset does not reintroduce an aliasing opportunity outside the
   ordinary wraparound analysis (§9 shows this is currently false too).

**Given §7-§9's findings: assumptions 1, 2, 5, and 6 are not currently
met by this architecture, independent of `EPOCH_W`'s value.**

> **No finite `EPOCH_W` can currently be proven sufficient from the
> existing contract.** Widening the counter only enlarges `I`; it does
> nothing to establish `T_stale_max`, `T_txn_min`, the backlog-drain
> bound, sender/receiver lockstep, or reset safety — all four of which
> are either unproven or actively false today. `I > N_reuse_max` cannot
> be evaluated when `N_reuse_max` is not itself a proven finite number.
> This is not a hedge; it is the literal conclusion of §7-§9.

## 7. Deriving stale-word lifetime from the actual architecture

Each item below is inspected against the current RTL and the cited
tickets, not assumed.

**A. FIFO residence.** `gcb_dwdm_async_skew_fifo`'s `rd_en[c] =
(aligned_valid & channel_enable[c]) | epoch_discard[c]`. A word's own
residence ends only when one of these two conditions fires *for its own
FIFO slot reaching the head*. There is no third, independent eviction
path (no timer local to the FIFO itself, no forced-pop-after-N-cycles).
**A word whose epoch still equals `expected_epoch` can sit at the head
indefinitely if nothing else in the system changes `expected_epoch`** —
this is not a bug (a currently-valid word *should* wait for its barrier
partners), but it means residence for a *matching* word is genuinely
**unbounded** absent external progress. `MEASURED / DERIVED` from the
RTL directly.

**B. CDC synchronization latency.** The gray-code write→read pointer
crossing is a fixed, small number of cycles (2-flop synchronizer,
per-crossing) — this bounds how long *pointer visibility* lags, not how
long a *word* stays live. `TKT-019.10`'s Candidate 1 post-mortem is the
concrete precedent for how this latency, if raced, causes real defects;
it is a real, small, roughly-constant term, not the dominant one in
this analysis.

**C. Deskew waiting.** Bounded by `ALIGN_TIMEOUT` — **but
`ALIGN_TIMEOUT`'s own value (32 at bring-up, 256 at the ceiling) is
inherited unchanged from `TKT-019.3`'s own header comment, which
states it is a "validated-on-paper placeholder... pending the PIC
receiver spec, not a measured number."** `UNPROVEN` as a physical
bound; treated as authoritative by the RTL's own control flow (it IS
what the hardware does), but not something this ticket may promote to
a proof input without re-flagging that promotion.

**D. Transaction timeout / `txn_void`.** Retires the current generation
and advances `expected_epoch` by exactly 1 — see §8 for the full
mechanics. It does **not** touch queued data at all (`TKT-019.5`
already established, and this epic's own design choice in `TKT-019.7`
confirms, that no flush exists — discard is lazy, one word per cycle,
gated on the head reaching a mismatch).

**E. Downstream backpressure / absence of consumption.** There is no
modeled backpressure signal into `gcb_dwdm_deskew_cdc` at all in the
current RTL — `aligned_valid`'s pop is unconditional once all enabled
lanes are ready. What is *not* bounded is the **inverse**: nothing
prevents a lane from simply never being enabled, or never receiving
further traffic, which (per A) leaves any currently-matching word
resident forever. This is an **absence of a bound**, not a bound.

**F. Multiple queued stale words.** Bounded above by `DEPTH`
(`MAX_SKEW_CYCLES`) per lane — `TKT-019.11`'s
`test_deskew_cdc_skew_exceeds_fifo_capacity` and
`test_deskew_cdc_multi_lane_stale_and_future_epoch` both confirmed this
empirically (writes past `DEPTH` are silently dropped, not queued
further). This is the one sub-bound that **is** `PROVEN — DIGITAL
SIMULATION, TESTED CONDITIONS`: no lane can hold more than `DEPTH`
words. It feeds directly into §6's backlog-drain-race derivation.

**G. Stale words distributed across multiple lanes.** Each lane's
discard path is fully independent (`epoch_discard[c]` per lane,
per-lane FIFO) — `TKT-019.11` confirmed multiple lanes can
simultaneously carry independent stale backlogs without interfering
with each other's discard timing. Does not change the per-lane bound
derived in F; does mean the *aggregate* number of live stale words
across the whole module scales with `NUM_COLORS × DEPTH`, relevant to
§10's area comparisons but not to the per-lane timing bound itself.

**H. Channel idle periods.** By design (`TKT-019.10` Candidate 2),
**idle silence never advances `expected_epoch`** — `any_matched_activity`
requires a real epoch-matched word, so pure idle cannot arm the
watchdog or produce a `txn_void`. This is correct and intentional
(closes `TKT-019.8` Finding B), but it has a direct consequence for
this ticket: **idle time does not "use up" any of the epoch-advance
budget**, so `T_stale_max`/`N_reuse_max` are not meaningfully
wall-clock quantities at all — they are **generation-count**
quantities (how many further *generations* get issued/retired), not
time quantities, precisely because arbitrary idle gaps are free and
do not move the counter. §5's definitions are written to reflect this
(`T_stale_max` should be read as "however long until enough further
generations resolve to advance past this word," which is itself
circular against the very quantity it's meant to bound — see the next
paragraph).

**This is the central finding of this section: `T_stale_max`, as
actually realized by this RTL, is defined in terms of "number of
further epoch advances," and the number of further epoch advances a
system will experience before a given stale word is discarded is
*exactly* `N_reuse_max`'s own defining question.** The architecture
provides no independent, epoch-count-free mechanism (a real-time
clock, a hard cycle-count watchdog local to each FIFO slot, anything
not itself gated by `expected_epoch`'s own progress) that forces
discard. This is a structural circularity, not merely a missing
number — labeled `OPEN`.

**I. Reset/restart.** See §9 in full — reset does not consume any of
the identity space and is a *separate* aliasing mechanism from
ordinary wraparound.

**J. Transaction rate.** The mux's `state_e {S_IDLE, S_EMIT}` FSM only
samples a new `start` from `S_IDLE`, so the **sender's own** completion
path cannot issue two generations without at least one full `S_EMIT`
sequence between them — a genuine, derivable lower bound on *that one
path's* issue rate. **It says nothing about the `txn_void` path**,
which runs on the receiver's own clock, gated only by
`ALIGN_TIMEOUT` (itself `UNPROVEN`, per C) and can advance
`expected_epoch` **independently of whether the sender has completed,
started, or even exists** for that cycle. Any `T_txn_min` derived from
the mux alone is not authoritative for `expected_epoch`'s actual
increment rate.

**K. Epoch rollover.** `TKT-019.11`'s own confirmed result: real,
reachable, under tested conditions, at `EPOCH_W=4`. Nothing in this
section's analysis suggests a larger `EPOCH_W` removes the underlying
mechanism — it only requires more generations to reach the same
condition, and per §6, "more generations" is not obviously large
relative to `DEPTH`-driven backlog drain time.

**Conclusion of this section:** the only sub-bound that is actually
`PROVEN` is F (`DEPTH` caps queued words per lane). Every other
input needed to compute `T_stale_max` or `T_txn_min` is either
`UNPROVEN` (`ALIGN_TIMEOUT`/`MAX_SKEW_CYCLES` as physical numbers), an
`ARCHITECTURAL ASSUMPTION` not yet stated as a contract (mux-side
issue pacing), or structurally circular / `OPEN` (H's finding).

## 8. Reset as a separate identity-namespace problem

Reset is analyzed against the four listed possibilities, from the RTL
directly (`gcb_dwdm_deskew_cdc.sv`'s `always_ff @(posedge rd_clk or
negedge rd_rst_n)` reset branch; `gcb_dwdm_payload_mux.sv`'s equivalent
for `tx_epoch`; `gcb_dwdm_async_skew_fifo.sv`'s independent
`wr_rst_n`/`rd_rst_n` reset branches):

1. **Does reset drain all stale state? Partially, under an unstated
   assumption.** `wr_ptr_bin`/`wr_ptr_gray` and their read-domain
   synced copies, and the mirror-image read-side pointers, all reset to
   `'0`. `empty = (rd_ptr_bin == wr_ptr_bin_rdomain)` is therefore true
   immediately after a *consistent* reset, and the FIFO reports itself
   empty regardless of leftover `mem[]` contents (the module's own
   comment: "RAM intentionally carries no reset... correctness comes
   from the pointers, not from zeroing memory contents"). **This
   reachability argument is only valid if every lane's `wr_rst_n[c]`
   and the shared `rd_rst_n` are asserted with enough mutual overlap to
   also flush the 2-flop cross-domain synchronizer registers on both
   sides to zero.** Nothing in the current RTL or its verification
   (this epic's own cocotb suites always reset every domain
   simultaneously in the testbench) establishes that this overlap is
   guaranteed in a real system where each lane's `wr_rst_n[c]` derives
   from an **independently recovered per-λ clock domain**. `PROVEN —
   DIGITAL SIMULATION, TESTED CONDITIONS` only for the simultaneous-
   reset case actually exercised; `ARCHITECTURAL ASSUMPTION` for
   independent/skewed per-lane reset timing, never tested.

2. **Does reset quarantine stale state? No.** There is no intermediate
   state between reset de-assertion and normal operation resuming at
   `expected_epoch = 0`. No delay, no drain-confirmation gate.

3. **Does reset invalidate the previous identity namespace? No.** The
   "namespace" is the integer range `[0, 2^EPOCH_W)`. Reset does not
   retire, skip, or mark any prior value as spent — it restarts
   counting from the **same fixed value, 0, every time**, on both the
   receiver (`expected_epoch <= '0`) and the sender (`tx_epoch <=
   '0`), independently.

4. **Does reset guarantee a new generation cannot alias old in-flight
   data? No — for two separate reasons.** First, (1) above is
   conditional, not unconditional. Second, and more fundamentally:
   **even a perfectly clean, fully-overlapping reset does not help**,
   because both counters restart at the identical value 0 every time.
   Any word that is "in flight" *outside* the reset domain's own
   pointer-tracked state at the instant of reset — physically still
   propagating on the optical channel, sitting in an upstream buffer
   this module does not own, or simply delayed by a slow independent
   `wr_clk[c]` domain that has not yet processed its own reset — and
   that happens to carry (or will carry, from a pre-reset `tx_epoch`
   assignment) tag value 0, is **numerically indistinguishable from
   the very first transaction issued after reset.** This requires
   **zero** further wraps, not up to `2^EPOCH_W - 1` of them — it is
   strictly worse than ordinary rollover, and is not mitigated at all
   by widening `EPOCH_W`.

**Sequence requested explicitly — "old epoch N data in flight → reset
→ new transaction generation → eventual reuse of identity N → delayed
old data arrives":** for the common and most dangerous case `N = 0`,
"eventual reuse" is not eventual at all — it is the **very first**
post-reset transaction. For `N ≠ 0`, reuse follows the same ordinary
wraparound timeline as §6/§7 analyzed, now measured from the reset
instant instead of from system power-on — no new invariant currently
prevents acceptance in either case; the same, already-shown-
insufficient `word.epoch == expected_epoch` comparison is the only
gate.

**If ordinary epoch width cannot solve reset aliasing — stated
explicitly: it cannot, for any width.** Widening `EPOCH_W` does not
change what value reset restarts at. Solving this requires a mechanism
oriented around *reset events*, not tag width — e.g. a reset-surviving
(non-volatile or externally-maintained) generation marker, or a
mandatory post-reset quiescence contract (do not accept new traffic
for at least `T_stale_max` after reset de-asserts) — both of which
this architecture currently has neither, and the latter of which is
itself blocked on `T_stale_max` being a proven number (§7 shows it is
not).

## 9. `txn_void` analysis

From `gcb_dwdm_deskew_cdc.sv`'s reset/timeout branch, read directly:

* **Queued stale words:** untouched. `txn_void` performs no flush —
  confirmed both by direct RTL inspection and by `TKT-019.5`/`TKT-019.7`'s
  own prior findings (flush was considered and explicitly **not**
  chosen, in favor of lazy discard-on-mismatch). Words remain queued
  and become eligible for discard only once `expected_epoch` no longer
  equals their tag.
* **`expected_epoch`:** advances by exactly `+1 mod 2^EPOCH_W` in the
  same clock edge `txn_void` pulses.
* **`tx_epoch` (sender):** **unchanged.** `gcb_dwdm_payload_mux` has no
  input connected to the CDC's `txn_void` output at all — the two
  modules are additive and explicitly **not wired into
  `gcb_dwdm_transceiver_top`** by either `TKT-019.3` or `TKT-019.8`'s
  own header comments. `tx_epoch` advances only on the sender's own
  `done`. **This means a receiver-side `txn_void` desynchronizes the
  two counters by exactly one generation, silently, with no signal
  path for the sender to ever learn it happened or to compensate.**
  This is a correctness gap **independent of `EPOCH_W`** — no width
  fixes a missing wire.
* **CDC `ACTIVE`/`IDLE` state:** returns to `CDC_IDLE`
  (`state <= CDC_IDLE`) — ready to re-arm on the next matched
  activity, exactly as `TKT-019.10` specified.
* **Watchdog state:** `wait_cnt <= '0`; `stuck <= channel_enable &
  fifo_empty` (sticky until the next `aligned_valid`); `txn_void`
  itself is a one-cycle pulse (`txn_void <= 1'b0` unconditionally at
  the top of the next cycle's else-branch, then conditionally
  re-asserted only if a *new* timeout fires).
* **Late-arriving words** (tagged with the just-retired epoch value):
  mismatch `expected_epoch` immediately, so `lane_ready` is false and
  they can never satisfy `aligned_valid`; they are popped via
  `epoch_discard`, at the FIFO-head rate described in §6/§7.F — unless
  §6's backlog-drain race or §8's reset case cause a lap before they
  are ever examined.

**Does `txn_void` create a new generation, merely retire the current
one, or something else?** **Both, atomically, in the same register
update, with no observable window between them.** There is no
intermediate "generation V is retired, generation V+1 has not yet
begun" state a verification harness or a control plane could observe
and act on — `TKT-019.6`'s original M2 (explicit quarantine) would
have created exactly such a window; `TKT-019.7`'s ratified alternative
(tag + lazy discard) does not, and this ticket finds that absence is
part of why §6's race is possible at all.

**Can the architecture currently prove "voided epoch data cannot
become valid data for a later transaction"? No.** `TKT-019.11`
falsified the unqualified version of this claim directly. The
qualified version — "cannot become valid data for a later transaction
**within `N_reuse_max` further generations**" — cannot currently be
evaluated either, because `N_reuse_max` is not a proven finite number
(§6/§7). The claim is therefore `OPEN`, not `PROVEN`, at any
`EPOCH_W`.

## 10. Candidate architecture trade study

No candidate is selected or ratified here — per this epic's standing
discipline (`TKT-019.6`/`TKT-019.7` precedent), a trade study informs,
it does not decide.

### 10.1 Wider modulo epoch (8 / 12 / 16-bit)

| | 8-bit | 12-bit | 16-bit |
|---|---:|---:|---:|
| Per-lane metadata (bring-up, `NUM_COLORS=4, DEPTH=16`) | 512 b (64 B) | 768 b (96 B) | 1024 b (128 B) |
| Per-lane metadata (ceiling, `NUM_COLORS=60, DEPTH=128`) | 61,440 b (7.5 KB) | 92,160 b (11.25 KB) | 122,880 b (15 KB) |

(`MEASURED / DERIVED`: `bits = NUM_COLORS × DEPTH × EPOCH_W`, the same
formula `TKT-019.9` used for the 4-bit case at the ceiling — 60×128×4 =
30,720 b, which matches `TKT-019.9`'s own reported ceiling figure. Its
*bring-up* figure of "+64 bits" does not match this formula at 4-bit,
256 b — `4 lanes × 4 bits × DEPTH=16 = 256`, not 64; flagged here as a
likely arithmetic slip in `TKT-019.9`'s own text, not re-derived from
a different formula, and not load-bearing for that ticket's own
conclusion.)

* **Correctness invariant:** identical in kind to the current 4-bit
  case — pure value equality, no generation memory. Does **not**
  change the class of failure `TKT-019.11` found; only changes how
  many generations it takes to reach it.
* **Required assumptions:** all of §6's six assumptions, unchanged.
  Assumptions 1, 2, 5, 6 remain unmet regardless of width.
* **Area (logic):** per this epic's own Yosys methodology
  (`TKT-019.9`/`TKT-019.11`), a wider equality comparator does **not**
  meaningfully add cells — Yosys's `stat` counts one `$eq` cell per
  comparison regardless of operand width (`TKT-019.11`'s own Task 4
  finding, that `any_matched_activity`'s wide OR-reduction added zero
  new `$reduce_or` cells for the identical reason). The cost of a
  wider epoch is **overwhelmingly memory bits (the table above), not
  logic cells** — consistent with `TKT-019.9`'s finding that the
  4-bit case's own cost was "memory bits, not logic cells."
* **Per-lane metadata / optical bandwidth:** see the unresolved
  tension flagged in §11 — `TKT-019.9` characterizes epoch cost as
  zero optical bandwidth ("never leaves the CDC"), while `TKT-019.7`
  characterizes it as riding in every word with a nonzero,
  width-proportional sideband cost. Both cannot be the ratified
  design; whichever is intended, a wider tag scales that cost
  linearly with `EPOCH_W` if `TKT-019.7`'s framing is the one that
  actually holds physically.
* **Latency:** none added — same zero-latency clean path as today.
* **Reset behavior:** **unchanged and unsolved** — §9 shows width does
  not touch the reset-aliasing mechanism at all.
* **Verification risk:** low incremental risk over the existing 4-bit
  suite (same comparator shape, same test structure), but does
  **not** retire the backlog-drain race (§6) unless `2^EPOCH_W` is
  also shown large relative to `DEPTH` at whatever geometry is
  chosen — untested at any width in this ticket.
* **Ability to prove non-aliasing:** **cannot be shown sufficient at
  any of these widths** while assumptions 1, 2, 5, 6 remain unmet —
  same conclusion as §6's boxed statement, independent of 8 vs. 12 vs.
  16 bits.

### 10.2 Epoch + explicit generation/quarantine state

A new FSM state entered on retirement (`txn_void` or completion)
during which no new generation's identity is considered "current" for
the barrier until a drain-completion condition is observed.

* **Correctness invariant:** closes §6's backlog-drain race directly —
  generation `V+1` cannot begin until generation `V`'s backlog is
  provably empty, removing the "lapped before examined" race
  entirely, for any `EPOCH_W ≥ 1`.
* **Required assumptions:** the drain-completion condition itself must
  be correctly derived (e.g. "every enabled lane has reported
  `fifo_empty` or `DEPTH` consecutive discard pulses since retirement")
  — a new, currently unproven correctness obligation, but a
  **removable** one (provable by construction, not by hoping the
  numbers happen to work out).
* **Area:** one more FSM state plus a drain-tracking
  counter/comparator per the module (state-machine-class addition —
  by `TKT-019.11`'s own Task 4 precedent for `CDC_IDLE`/`CDC_ACTIVE`,
  likely a small, roughly fixed cost, not `O(NUM_COLORS)`, though this
  is an expectation from analogy, not a measurement — labeled
  `UNPROVEN` until actually built and blessed).
* **Per-lane metadata:** unchanged from whatever `EPOCH_W` is paired
  with this — this candidate is additive to 10.1, not a substitute.
* **Optical bandwidth:** unchanged from the paired `EPOCH_W`.
* **Latency:** **adds latency** — the next generation's first word
  cannot be accepted as "current" until quarantine/drain completes,
  a new cost this epic has not had to pay since `TKT-019.10`
  specifically avoided adding a mandatory recovery-path delay.
* **Reset behavior:** orthogonal — still needs §9's separate fix
  regardless.
* **Verification risk:** genuinely new state machine, new race
  conditions to prove (quarantine window vs. live incoming traffic on
  a *different*, not-yet-retired lane) — real, not yet characterized.
* **Ability to prove non-aliasing:** **strong**, if the drain
  condition is correctly specified and independently verified —
  converts an implicit race into an explicit, checkable serialization.

### 10.3 Epoch + mandatory retirement/drain/flush before reuse

Distinct from 10.2 in **mechanism**, not goal: rather than a new FSM
state, treat "may the barrier consider a new generation current" as
gated on the *existing*, already-proven `rd_en`/discard pop path
having been observed to run to completion on every enabled lane since
the last retirement — reusing `TKT-019.7`'s own preferred mechanism
(no new CDC-adjacent control primitive) instead of `TKT-019.6`'s
original M2 flush-pointer proposal, which `TKT-019.7` specifically
rejected on verification-cost and staleness-gap grounds.

* **Correctness invariant:** same as 10.2's — reuse cannot occur until
  physical emptiness (or an equivalent proven-complete drain) is
  observed, for **any** `EPOCH_W`, including very small ones (in the
  limit, a 1-2 bit "which of the two most-recent generations"
  ping-pong scheme becomes sufficient once reuse is serialized against
  drain, since aliasing requires *concurrent* liveness, and mandatory
  drain removes concurrency by construction).
* **Required assumptions:** that "observed drain" is itself correctly
  and completely specified — must cover **every** enabled lane, not
  just the lane(s) that caused the retirement, and must be immune to
  a lane's own `channel_enable` changing mid-drain.
* **Area / per-lane metadata / optical bandwidth:** same order as
  10.2 — this is primarily a control-sequencing change, not a
  datapath-width change; could in principle **reduce** `EPOCH_W`
  requirements relative to 10.1 for the same safety margin, per the
  correctness-invariant note above.
* **Latency:** same cost class as 10.2 — adds a mandatory delay before
  the next generation may begin, sized to the drain time, not to
  `ALIGN_TIMEOUT`.
* **Reset behavior:** orthogonal, same as 10.2.
* **Verification risk:** moderate — reuses proven pop mechanics
  (lower risk than a literal flush primitive, per `TKT-019.7`'s own
  reasoning), but the *gating* logic (when is "every lane" considered
  drained) is new and needs its own adversarial test suite, directly
  modeled on `TKT-019.11`'s own multi-lane/backlog scenarios.
* **Ability to prove non-aliasing:** **strong**, same class as 10.2,
  reached via a lower-verification-risk path per `TKT-019.7`'s own
  stated preference for reusing proven mechanisms over new ones.

### 10.4 Non-wrapping generation with reset/reinitialization semantics

A wide (e.g. 32/64-bit), practically-non-wrapping counter, plus an
explicit mechanism that prevents reset from reusing value 0 — e.g. a
persisted (non-volatile or externally-maintained) generation marker
incremented once per reset/boot, or a mandatory post-reset quiescence
contract of at least `T_stale_max` before new traffic is accepted.

* **Correctness invariant:** for wraparound, practically eliminates
  §6's race by making `I` astronomically larger than any credible
  `N_reuse_max` — but this is a **practical**, not a **structural**,
  argument (the counter still wraps in principle; it is asserted, not
  proven, that operational lifetime never reaches that point). For
  reset specifically, **only** the persisted-marker or mandatory-
  quiescence half of this candidate actually helps — width alone,
  however large, does not (§9's conclusion is width-independent).
* **Required assumptions:** a persistence mechanism across reset is a
  **new dependency** this epic has not previously required — either
  non-volatile storage (new hardware requirement) or an externally
  maintained monotonic value (new interface requirement, with its own
  unproven "does the external source ever repeat a value" obligation).
* **Area / per-lane metadata:** significantly larger than 10.1 — 32-64
  bits/word instead of 4-16, scaling the same `NUM_COLORS × DEPTH`
  memory-bit cost proportionally larger (e.g. 32-bit at the ceiling:
  60×128×32 = 245,760 b ≈ 30 KB, roughly 8× the current 4-bit cost).
* **Optical bandwidth:** same unresolved-tension caveat as 10.1, at a
  proportionally larger cost if `TKT-019.7`'s "rides in every word"
  framing is the one that holds.
* **Latency:** none added on the clean path (same as 10.1), **unless**
  paired with a mandatory post-reset quiescence delay, which does add
  a one-time cost at every reset (not per-transaction).
* **Reset behavior:** **solves §9's finding, but only if the
  persistence/marker mechanism is actually implemented and itself
  verified** — introduces its own new proof obligation (marker
  uniqueness across power cycles) this epic has not begun to analyze.
* **Verification risk:** new persistence-path verification burden,
  orthogonal to (and in addition to) anything already built.
* **Ability to prove non-aliasing:** strong for wraparound (practical,
  not absolute); strong for reset **only if** the persistence
  mechanism is real and correct — otherwise no better than 10.1 on
  the reset axis specifically.

### 10.5 Other — sender/receiver identity synchronization (a materially different, and arguably prerequisite, axis)

None of 10.1-10.4 address §9's finding that `tx_epoch` (sender) and
`expected_epoch` (receiver) are two **independently free-running**
counters with **no wired coupling** — a `txn_void` on the receiver is
currently invisible to the sender. This is a correctness gap **at
`EPOCH_W` of any width**, closeable only by (a) wiring `txn_void`
(or an equivalent retirement signal) back to the sender so `tx_epoch`
can skip in lockstep, or (b) an explicit periodic handshake/heartbeat
that lets both sides re-synchronize their notion of "current
generation" independent of either side's own local event history.
This is flagged as a **materially different proof obligation** from
identity-space sizing — it is entirely possible to pick a
provably-sufficient `EPOCH_W`/quarantine scheme per 10.1-10.4 and
**still** have the sender and receiver silently disagree about which
generation is current, which would reintroduce exactly `TKT-019.5`'s
original Ghost Payload mechanism through a different door. Not
evaluated on the same area/latency/etc. axes as 10.1-10.4 because it
is not a substitute for them — it is an **additional**, currently
entirely-missing mechanism.

## 11. Exact unresolved contract gaps (Task 7)

Listed as the specific, missing pieces of contract — not invented
values — that must exist before any `EPOCH_W` (or any of §10's
candidates) can be declared mathematically sufficient:

1. **A proven, finite `T_stale_max`.** Currently `ALIGN_TIMEOUT`/
   `MAX_SKEW_CYCLES` are stated, unmeasured placeholders
   (`TKT-019.3`), and §7.H shows the RTL's own discard mechanism makes
   "when is a stale word finally gone" a function of *subsequent*
   system activity, not a fixed clock — a structural circularity, not
   just a missing measurement.
2. **A proven `T_txn_min` covering every path that can advance the
   epoch counter**, not just the sender's own `S_IDLE`/`S_EMIT` pacing
   (§7.J) — the `txn_void` path runs on the receiver's clock, gated by
   the unproven `ALIGN_TIMEOUT`, independent of the sender.
3. **A proven relationship between `DEPTH` and `EPOCH_W`** sufficient
   to rule out §6's backlog-drain race — currently absent; the bring-
   up geometry's `DEPTH == 2^EPOCH_W` numeric coincidence is a red
   flag, not a validated margin.
4. **An explicit sender-receiver identity-synchronization contract**
   (§10.5) — currently absent; `tx_epoch` and `expected_epoch` are
   unwired, independently-incrementing counters.
5. **A reset-generation semantics contract** (§9) — currently absent;
   both counters unconditionally restart at the fixed value 0 on every
   reset, with no persisted memory, no mandated post-reset quiescence,
   and no proven cross-domain reset-ordering guarantee between the
   mux's `rst_n`, the CDC's `rd_rst_n`, and each lane's independent
   `wr_rst_n[c]`.
6. **A specified physical/transport path for the epoch tag itself.**
   `TKT-019.9` ("never leaves the CDC, zero optical bandwidth") and
   `TKT-019.7` ("rides in every word... rippling into the mux...
   nonzero sideband overhead") describe two different physical
   designs. Neither has been ratified as *the* design; this needs
   resolving before any of §10's per-width bandwidth costs can be
   trusted as anything but conditional arithmetic.

None of these gaps is closed by choosing a wider `EPOCH_W` alone.

## Recommended next action

Per §11, the two gaps that are **prerequisite to evaluating any
`EPOCH_W`** at all — because they are the ones an epoch-width choice
cannot address regardless of value — are **(4) sender/receiver
identity synchronization** and **(5) reset-generation semantics**.
Recommend a follow-on architecture ticket (`TKT-019.13`, not drafted
here) scoped narrowly to those two, before any ticket attempts to
ratify an `EPOCH_W` value or a §10 candidate: widening the counter or
adding quarantine logic while the sender and receiver can silently
disagree about the current generation, or while reset can alias
generation 0 unconditionally, would be sizing a fix against only part
of the disproven invariant.
