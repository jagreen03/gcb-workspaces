# Objective

Prove the **digital transport contract survives composition** —
[[TKT-019.2]]'s payload mux/demux, chained through [[TKT-019.3]]'s CDC-capable
deskew, as one link — rather than each piece only ever having been verified
in isolation. This is the first time `gcb_dwdm_payload_mux`,
`gcb_dwdm_deskew_cdc`, and `gcb_dwdm_payload_demux` will run together in the
same testbench.

## The chain under test (stated precisely, not assumed)

**`gcb_dwdm_payload_mux` → [channel] → `gcb_dwdm_deskew_cdc` → `gcb_dwdm_payload_demux`.**

`gcb_wavelength_router` ([[TKT-019.1]]) does **not** sit in this chain.
Reading the RTL (not assumed): the router permutes flat INT4 operand lanes
for the photonic-MAC operand-broadcast datapath — a different logical use of
the same physical colour count, and a different port shape entirely
(`lane_i`/`lane_q` INT4 vectors, not `color_word_t`). Wiring it into this
chain would not reflect the system's actual architecture, and this story
does not pretend otherwise. `gcb_dwdm_tx_packager` and the plain single-clock
`gcb_dwdm_deskew` are likewise **not** in this chain — this story exercises
the CDC-capable sibling specifically, because independent-clock behaviour and
bounded-wait failure handling are exactly what the five required vectors
below stress.

## Orange-Team epistemic boundary — read before running or reporting anything

**This ticket validates a digital contract, not an optical link.** Every
result below is a claim about RTL behaviour under controlled digital stimuli
in a testbench. None of it is evidence about:

* **Optical device BER** — no laser, modulator, photodetector, or fibre
  model exists in this chain. "Bit corruption" here means an XOR flip
  applied to a `color_word_t` bit by the testbench's channel model, in
  Python, between the mux's egress and the CDC-deskew's per-lane ingress —
  not a measured or modelled optical impairment.
* **Physical link budget** — [[GCB-037]] already did that analysis
  (separately, numerically, from the link-budget equations) and is not
  re-derived, re-used, or re-validated by anything in this ticket.
* **FEC** — no forward-error-correction exists anywhere in this repo. This
  story does **not** design one, assume one, or credit the transport with
  recovering from an error it cannot actually recover from. Where a result
  below shows silent corruption, that is reported as silent corruption, not
  softened.
* **BER-to-hit-rate arithmetic** — 1e-12 / 1e-6 are the requested target
  rates, but at this transaction's bit count (~8-9 Kb), a real per-trial flip
  probability at either rate would need in the range of 10^8-10^11 simulated
  transactions to see a single hit — not a practical cocotb run. Section
  "Bit corruption" below explains the actual methodology: deterministic
  single-bit injection (to observe the *consequence* of a hit, which is a
  digital question this story can answer) decoupled from the *frequency*
  question (which stays link-budget territory this story does not touch).

**Any wording in the results below that could be misread as an optical-link
or BER claim is a drafting defect, not a finding** — flag it for correction
rather than repeating it.

## Required validations — 5 vectors

### V1. Mode A — single-lane serialisation + boundary preservation

`MODE_B_LANES` irrelevant (Mode A always uses 1 lane). Sweep payload length
across boundary cases, not just one nominal size: `1` B (minimum), `13` B
(not a multiple of `CHUNK_BYTES=16`, exercises the zero-pad tail), `16` B
(exactly one chunk), `271` B (the GCB-035/036 INT8 `q_tile`+`q_scale`
reference size), `1024` B (`MAX_PAYLOAD_BYTES` ceiling). Assert byte-for-byte
reconstruction, correct `mode_b`/`payload_len` recovery, and correct
`is_tile_final` placement (last lane of the last cycle) at every length.

### V2. Mode B — ~60 active wavelengths, independent lane clocks

`NUM_COLORS = MODE_B_LANES = 60` (the GCB-034 Mode B ceiling), the full
1024 B `acc_tile` payload. Each of the 60 lanes gets **its own,
incommensurate `wr_clk` period** — genuinely independent clock domains, not
60 copies of the same clock — to exercise `gcb_dwdm_async_skew_fifo`'s
gray-code pointer crossing for real, at the scale the contract requires.
Assert byte-for-byte reconstruction.

### V3. Lane skew — sweep against the bounded-wait boundary

Isolates the barrier's bounded-wait logic specifically (held on a shared
clock across lanes so the *only* variable is injected delay, not genuine CDC
— V2 already covers genuine independent clocks). One lane's data is
deliberately delayed by the testbench's channel model before it reaches the
CDC-deskew's ingress. `gcb_dwdm_deskew_cdc`'s own barrier
(`gcb_dwdm_deskew_cdc.sv`) waits up to `ALIGN_TIMEOUT` cycles
(`wait_cnt` reaches `ALIGN_TIMEOUT` before `txn_void` fires) — that register
count, not `MAX_SKEW_CYCLES` (FIFO depth, a separate and much larger
concern this story does not stress), is the boundary under test here.

| label | injected delay | expected outcome |
|---|---:|---|
| zero | 0 cycles | `aligned_valid`, reconstructs exactly |
| small | a few cycles | `aligned_valid`, reconstructs exactly |
| nominal | `ALIGN_TIMEOUT / 2` | `aligned_valid`, reconstructs exactly |
| large-but-valid | `ALIGN_TIMEOUT - 1` | `aligned_valid`, reconstructs exactly |
| deskew-boundary | `ALIGN_TIMEOUT` | `aligned_valid`, reconstructs exactly — the very edge of the window, still inside it |
| one-cycle-over-limit | `ALIGN_TIMEOUT + 1` | `txn_void` fires, `stuck` names the delayed lane, `aligned_valid` never asserts for this transaction |

### V4. Lane loss — kill one λ

At the `NUM_COLORS = MODE_B_LANES = 60` geometry, one lane's data is
**never** presented to the CDC-deskew (not delayed — permanently withheld),
while `channel_enable` still marks it enabled (the fabric still expects it;
this is the fault, not a reconfiguration). Required assertions: (a)
`aligned_valid` never asserts for this transaction — no partial or
substitute result is ever produced; (b) `txn_void` fires exactly once, at
the `ALIGN_TIMEOUT` boundary; (c) `stuck` names **exactly** the killed lane,
none of the other 59; (d) the demux never emits a `payload_valid` pulse for
this transaction. "No silent corrupted result" is the falsifiable claim —
this validation exists to falsify it if it's wrong, not to confirm a
foregone conclusion.

### V5. Bit corruption — consequence, not frequency

**Methodology, stated up front:** this story tests what happens *if* a bit
is corrupted, using deterministic single-bit injection at chosen positions,
repeated across many trials with the position/timing randomised within each
target category. It does **not** attempt to simulate the 1e-12 / 1e-6 target
rates literally (see the epistemic-boundary section above for why that's not
practically simulatable, and why it would be a category error against this
ticket anyway — that question belongs to a channel/BER model, not this
digital contract test).

Target categories, each injected via the testbench's channel model (an XOR
flip on the `color_word_t` bit stream between mux egress and CDC-deskew
ingress — never inside synthesizable RTL):

1. **Payload-body bit** (a bit inside `packed_a`/`packed_b` that maps to an
   actual payload byte, not header or padding).
2. **Header mode-bit** (byte 0, bit 0 of the framed stream).
3. **Header length bits** (bytes 1-2 of the framed stream).
4. **Structural field** (`is_tile_final`, the barrier-termination flag
   itself — not a payload bit at all).

For each category: does the transport **detect** the corruption (any signal
distinguishing a corrupted reconstruction from a clean one)? Does it
**silently reconstruct wrong data** instead? Does a structural-field flip
change the transaction's *shape* (early/late termination, wrong lane count)
rather than just its content? Report the honest answer per category — do not
assume a detection mechanism exists before checking, and do not credit
`payload_valid` firing as "success" if the bytes underneath are wrong.

### Results — restated with the Orange-Team boundary explicit at every line

**V1 (Mode A boundary):** byte-exact reconstruction, correct `mode_b`/
`payload_len` recovery, at all five boundary lengths (1, 13, 16, 271,
1024 B) — including the sub-`CHUNK_BYTES` tail (13 B) and the exact-chunk
case (16 B) that a naive implementation could get wrong at the edges.

**V2 (Mode B, independent clocks):** byte-exact reconstruction across
**60 genuinely independent clock periods** (0.8-1.4 ns range, not 60 copies
of one clock) — the gray-code pointer-crossing protocol TKT-019.3 validated
in isolation holds up composed with the mux and demux, at the full ceiling
lane count.

**V3 (lane skew):** monotonic success→void transition across a full 72-point
scan; the *qualitative* bounded-wait behaviour matches the RTL exactly
(succeeds up to a threshold, `txn_void` beyond it, `stuck` correctly names
the delayed lane every time). The *exact* threshold measured (delay=56/57)
sits ~8 cycles below the RTL's own `ALIGN_TIMEOUT=64` — that gap is a
**testbench-overhead property** (capture + relay bookkeeping time), not an
RTL property, and is reported as such rather than mislabelled as an RTL
finding. **A result worth flagging plainly**: every voided case in the scan
still completed *late*, once the delayed word actually arrived — the CDC
barrier restarts its wait immediately after `txn_void` fires rather than
permanently rejecting the transaction, so `txn_void` is a bounded-wait
*alarm*, not proof the data was lost. A control-plane consumer that treats
`txn_void` as terminal (discards state, retries) could still receive a late,
unsolicited completion afterward — this is a real digital-contract gap this
story surfaces, not a claim about how often it would matter physically.

**V4 (lane loss):** exactly the claim the ticket set out to falsify —
**it did not falsify.** `payload_valid` never fired for the transaction with
one of 60 lanes permanently withheld; `txn_void` fired once, at the
`ALIGN_TIMEOUT` boundary; `stuck` named exactly the killed lane, none of the
other 59. No silent partial or substitute result was produced.

**V5 (bit corruption — consequence, not frequency, see the Objective's
methodology note): every one of the five categories tested is silent and
undetected**, because there is no CRC/checksum anywhere in this transport:

| category | outcome |
|---|---|
| payload-body bit | `payload_valid` fires, 1 byte silently wrong, no detection |
| header mode bit | `payload_valid` fires, `mode_b_out` silently wrong, data/length otherwise correct |
| header length bits | `payload_valid` fires, `payload_len_out=1025` instead of 1024, no detection |
| early false `is_tile_final` | `payload_valid` fires **reporting the full correct length**, but data silently diverges from byte 957 onward (premature finalize; the rest reads as never-written storage) — **the worst case: a confidently-wrong reported success** |
| suppressed true `is_tile_final` | the demux hangs (no `payload_valid`, ever, for this transaction); the CDC's own barrier separately times out once its FIFOs drain, `stuck` naming **all 60 lanes** — indistinguishable, from `stuck` alone, from "every lane failed simultaneously," even though every lane's data genuinely arrived correctly and on time |

**Analytical note, explicitly not empirically re-run this story** (flagged
as reasoning from the RTL, not a test result): in the early-false-final
case, `gcb_dwdm_payload_demux`'s `word_base` register only resets inside the
`finalize_pending` branch. A transaction that is never seen as final (the
suppressed-final case) leaves `word_base` wherever it stopped — a
**subsequent, uncorrupted transaction would start accumulating on top of
that stale offset**, not from zero, which for a full-capacity Mode B
transaction could walk `word_base + l` past the `WORDS_MAX`-sized array
bound. This is a plausible further consequence of the same finding, reasoned
from the RTL directly; it was not run as a second-transaction test in this
story and should not be read as a confirmed result.

  producing passing-but-wrong results, and a recurrence of the TKT-019.3

  labelled, is a gap this story could have closed with one more test.
* **Emergence (0.7):** several findings beyond the ticket's own ask: (1) a
  passing-but-silently-wrong test result is a distinct, more dangerous
  failure mode than a hang or a timeout, and was only caught by independently
  re-deriving an expected value rather than trusting a weak assertion — a
  methodology lesson for every future integration test in this repo, not
  just this one; (2) `txn_void` is a bounded-wait alarm, not a terminal
  failure state — a late, unsolicited completion after a declared failure is
  a real digital-contract property worth designing around; (3) `stuck`'s
  fault signature is ambiguous between "one lane never arrived" and "every
  lane's FIFO drained with nothing left to wait for" (a completely different
  root cause) — a control-plane consumer cannot currently tell these apart;
  (4) confirmed, empirically, that this transport has zero error detection
  across every corruption category tested, with the single most damaging
  category (a structural flag flip) producing a confidently-wrong *reported
  success* rather than any visible failure at all.
